# Milestone 3 prototype: the host survey and the bubblewrap sandbox

Throwaway scripts that answer the milestone 3 questions in `docs/design.md` §14 (issue #102). Nothing here is enclos code. The first part, M3-01, surveys the target hosts: Landlock and its ABI, unprivileged user namespaces and AppArmor, the bubblewrap each distribution packages, the cgroup controllers delegated to the user, and `systemd --user` at logout. The second, M3-02, builds a bubblewrap sandbox as the backend would and probes it: see [M3-02: the bubblewrap prototype](#m3-02-the-bubblewrap-prototype) below.

## Files (M3-01)

| File | What it does |
| --- | --- |
| `survey.sh` | Prints one `key: value` line per fact. **Read-only**: it reads `/sys`, `/proc`, the kernel's build configuration, package versions and logind's properties; it runs no bubblewrap, creates no namespace and changes nothing, so it is safe on any host. The Landlock ABI comes from `landlock_create_ruleset(NULL, 0, VERSION)`, which returns a number and restricts nothing. |
| `bwrap-check.sh` | Runs bubblewrap as the user as installed, then with an AppArmor profile that lets `/usr/bin/bwrap` alone make user namespaces, then with AppArmor's restriction off, restoring each setting. **Acts on the host**: refuses to run outside a GitHub-hosted runner. |
| `logout-check.sh` | Logs in over ssh to localhost, starts a `systemd --user` unit, logs out, and checks the unit and the user manager past logind's stop delay, without then with lingering. **Acts on the host** (installs sshd, changes lingering): refuses to run outside a GitHub-hosted runner. |
| `.github/workflows/host-survey.yml` | Runs the three on `ubuntu-latest` and `ubuntu-24.04-arm`, on a pull request that touches this folder or by hand, and writes their output to the job summary. It does not gate merges. |

### What this shows

- **Landlock is not in Raspberry Pi OS's kernel.** It is not active, and not even built: `CONFIG_SECURITY_LANDLOCK` is unset in every Raspberry Pi kernel installed (6.12 and 6.18, the `-v8` and `-2712` builds), so no `lsm=` boot option can turn it on. ADR 0004 asked for this check before the backend is built. Under ADR 0004 as written, the bubblewrap backend could not run on a stock Raspberry Pi OS. Proposed in [ADR 0037](../../docs/adr/0037-landlock-where-the-kernel-has-it.md) (proposed): Landlock is applied wherever the kernel has it, and where it is missing the backend still runs, its writes held by bubblewrap's mounts alone and the intended seccomp filter retained (not exercised by the survey); its capabilities declare the weaker execute control, a policy with an `[exec]` section is accepted there only with an explicit, audited acceptance and not applied, and `doctor` gives what is not enforced, the risk and the fix (design §5, Degraded controls on Linux). The same holds for a Landlock ABI older than the backend's rules need. That the mounts alone hold the writes is still to show (design §14).
- **The memory controller is off on Raspberry Pi OS** by the firmware's own boot arguments, so a session's cgroup cannot hold a `memory` limit there; `cpu` and `pids` are delegated. Proposed in [ADR 0038](../../docs/adr/0038-a-memory-limit-the-host-cannot-hold-runs-unapplied-once-accepted.md) (proposed), amending ADR 0033: there a policy that sets `memory` is accepted only with an explicit, audited acceptance, runs with the limit not applied, and every start says so; `doctor` gives the fix.
- **The fix for the memory controller, checked against the kernel's source, untried.** `cgroup_disable=memory` comes from the firmware's device-tree boot arguments (`/proc/device-tree/chosen/bootargs`), not from `/boot/firmware/cmdline.txt`, whose contents follow them in `/proc/cmdline` (measured (Raspberry Pi OS arm64)), so there is nothing to remove from `cmdline.txt`. Raspberry Pi OS's kernels define `cgroup_enable=`, which turns a subsystem back on (`static_branch_enable` in `kernel/cgroup/cgroup.c`, on `rpi-6.12.y` at `5bd564aa` and `rpi-6.18.y` at `b3495ea4`; added by [12]), and parse it after the firmware's arguments, so adding `cgroup_enable=memory` to `cmdline.txt` and rebooting should bring the controller back. `cgroup_memory=1`, often suggested, is not a parameter of either kernel: the only one near it is `cgroup.memory=` in `mm/memcontrol.c`, which takes `nosocket`, `nokmem` and `nobpf` [18]. Where the controller is there but not delegated, a `Delegate=` drop-in for `user@.service` is the fix, needed only where its `Delegate=` leaves `memory` out; Debian 13's (measured (Raspberry Pi OS arm64), trixie's systemd package) and Ubuntu 24.04's [13] already delegate `pids memory cpu`.
- **Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor and ships no rule for bubblewrap**, so bubblewrap is expected to fail there as installed; whether a profile naming `/usr/bin/bwrap` is enough is what `bwrap-check.sh` tries on the runners. Debian turns neither the restriction nor a bwrap rule on.
- **The oldest bubblewrap among the targets is Debian 12's 0.8.0**, then Ubuntu 24.04's 0.9.0. Whether each has every option the backend uses waits for M3-02's list of options.

## M3-02: the bubblewrap prototype

A bubblewrap sandbox built as the backend would build it (design §5, ADR 0004, ADR 0037), and probed: broad reads with the deny list not mounted, writes to the home and a workspace only, Landlock and seccomp applied by a small program run first inside, the relay from `127.0.0.1:<port>` to a proxy on a Unix socket, the host's Unix sockets, Hermes's installer and Chromium. Nothing here is enclos code; the compile step, the program run inside and the relay are drafts of M3-13, M3-14 and M3-09.

**Where it runs.** Every check acts on the host (it runs bubblewrap, makes user namespaces, plants files in the home, installs packages, changes an AppArmor setting), so `lib.sh` refuses to run anywhere but a GitHub-hosted runner, or a VM for the manual steps below: there `ENCLOS_PROTO_DISPOSABLE_VM=1` must be set and `systemd-detect-virt --vm` must name a hypervisor, so a machine that is not a VM is refused either way. The `bwrap-prototype` workflow runs the checks on `ubuntu-latest` (x86_64) and `ubuntu-24.04-arm` (arm64), on a pull request that touches this folder or by hand. Each check writes a Markdown result to `m3-results/`; the job shows them in its summary and uploads the folder as the artifact `m3-results-<runner>`.

### What this shows, and what it does not

- **The sandbox holds on both runners.** Broad reads with the deny list not mounted (ENOENT), writes refused everywhere but the home and workspace, an empty network with no DNS, the host's sockets out of reach (all of a server install's, and those a runner can start of a desktop's), abstract sockets closed, processes outside hidden. All of it holds with bubblewrap alone; Landlock and seccomp are not needed for any of it. This is shown on Ubuntu 24.04 runners with an Azure kernel only.
- **What Landlock adds** in these probes is the execute control: a program in the workspace is refused with it and runs without it (ADR 0037). Writes get EROFS from the mounts before Landlock is reached, so these probes do not show Landlock's write rules refusing anything by themselves.
- **What seccomp adds** is `keyctl`, `bpf`, `perf_event_open`, `userfaultfd`, io_uring, a user namespace and TIOCSTI's ioctl. Which of these matter beyond what the runner's own sysctls refuse depends on the host.
- **Chromium runs in the sandbox with its own sandbox off**, on both runners, in every mode: a page loads over the DevTools protocol, as browser tools drive it. Its own sandbox cannot start there. `--dump-dom` hangs on the host too, so its failures were the check's, not the sandbox's.
- **Sockets in the home are reached**, as §5 says, so each needs a deny-list entry (M3-07).
- **Surprises.**
  - The `--no-sandbox` Chromium left running by `--dump-dom` reached Google's update, Safe Browsing, GCM and component services through the proxy (`update.googleapis.com`, `safebrowsing.googleapis.com` about 8 MB, `android.clients.google.com`, `edgedl.me.gvt1.com`, `redirector.gvt1.com`, `www.google.com`). An allowlist sandbox would refuse them, and a public-mode one lets them through.
  - Hermes's installer took its Chromium from a different host on each architecture (above).
  - Inside the sandbox, Chromium tried the system bus at `/run/dbus/system_bus_socket` and found no socket there (ENOENT), which shows the masking against a real program.
- **Still open:**
  - Hermes's browser tool itself driving Chromium in the sandbox (agent-browser's flags, real pages, clicks and forms), and Chromium under memory pressure without its OOM-score adjustments, in a VM;
  - why the runner's host refuses to read a same-user process's environment (not AppArmor, not `hidepid`); the sandbox, for its part, does not see the process;
  - TIOCSTI with `--new-session` alone;
  - a real desktop session's sockets;
  - a kernel without Landlock;
  - the login and a model call;
  - what a refusal leaves for the user to read.

### Manual steps for a VM: the login and a model call

These need an account, so they cannot run in CI. In a disposable VM (Ubuntu 24.04 or Debian 13, x86_64 or arm64), with this repository checked out:

1. `export ENCLOS_PROTO_DISPOSABLE_VM=1`, then `bash prototype/m3/setup-runner.sh`, which installs the packages and finds the AppArmor setting, and `bash prototype/m3/hermes-check.sh`, which installs Hermes in the sandbox's home (`~/.enclos/sandboxes/proto/home`).
2. Start the proxy in `--learn` mode on the sandbox's socket: `python3 -I prototype/m3/unix-proxy.py --socket ~/.enclos/sandboxes/proto/run/proxy.sock --learn --log login.jsonl &`
3. Open a shell in the sandbox, full mode, with the relay: `SBX_RELAY=1 prototype/m3/sbx.sh -- /bin/bash`. Its first lines say what `inside.py` applied.
4. In it, `export PATH="$HOME/.local/bin:$PATH"`, then the device-code login, as the milestone 1 prototype ran it: `hermes auth add openai-codex --no-browser`. Open the URL it prints on another machine and enter the code.
5. A model call: `hermes -z "Reply with exactly one word: ok" --provider openai-codex -m <a model the account offers>`.
6. Record, in the results table above: whether each step worked, the endpoints from `login.jsonl` (host, port, verdict), and whatever refused, never the code or a token.
7. Then the same in the mode without Landlock (`SBX_LANDLOCK=off`), and, for a desktop install, `bash prototype/m3/sockets-check.sh` from a graphical login.

## M3-03: namespaces per session or per sandbox

Design §15's row on network and PID namespaces, and its §14 item on the runtime's own service: a session with a network namespace of its own reaches neither its runtime's service port ([ADR 0028](../../docs/adr/0028-a-runtime-listens-and-its-sessions-reach-its-service.md)) nor anything another session of its sandbox listens on. The first recommendation was one network and PID namespace per sandbox, held while its proxy service runs and joined by every session, if bubblewrap can be started inside a network namespace enclos entered first. bubblewrap joins an existing user namespace (`--userns`) and PID namespace (`--pidns`) but has no option to join a network namespace, and entering one needs a capability in the user namespace that owns it. So the experiment tries each way of joining, and records what sharing changes. It runs only in CI, as M3-02's checks do (`lib.sh`'s guard).

**The holder.** `ns-holder.py`, started by bubblewrap in a new user, PID and network namespace, stands for what enclos would run per sandbox (in its proxy service, for instance). It opens its own namespaces and hands them as file descriptors to whoever connects to its Unix socket, in a folder of the sandbox's that no session mounts, so the host needs no access to `/proc/<pid>/ns`. It also serves the sandbox's one relay on `127.0.0.1` in that network namespace. Since the third run it is started without `--dev /dev`: with that option bubblewrap makes a second, nested user namespace for the program it runs, so the holder handed out the inner user namespace while its network and PID namespaces belonged to the outer one.

**The ways a session joins** (`nsjoin.py`; the descriptors arrive as 10, 11 and 12 through `ns-fds.py`):

### What this shows, and what it does not

- **Shown:** with a network namespace per session, a session reaches nothing another session of its sandbox listens on, and Hermes's chat fails to reach its gateway in another session (`Gateway connection failed; no local fallback`). A listener in a sandbox's network namespace is not reachable from the host either, on 127.0.0.1 or on every address. A holder in bubblewrap can make a sandbox's namespaces and hand them out over a socket.
- **Corrected by the third run:** the first two runs seemed to show that no session can join a network namespace enclos made first. Each was refused with EPERM, by `nsenter` entering the network namespace and by bubblewrap's `--pidns`, but only because the holder's `--dev /dev` gave it a nested user namespace. The corrected holder is joined in every way but `nsenter-userns`.
- **Tried since:** bubblewrap given the holder's user namespace (`--userns`) without `--pidns`, then `inside.py` entering the network namespace (`userns-net`), and a namespace per session with the service's port relayed through a Unix socket (`relay`), both in the second run.
- **Not tried, and no longer needed:** `nsenter` under an AppArmor `userns` profile of its own, which the third run shows is not what refused it; the holder itself starting each session's bubblewrap from inside its namespaces.
- **Answered for Hermes:** its clients find a gateway in another PID namespace, and a chat that reaches the gateway starts none of its own (second and third runs). A chat started with no gateway running does start one (fourth run).
