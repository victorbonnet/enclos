# Milestone 3 prototype: the host survey

Throwaway scripts that answer the milestone 3 questions in `docs/design.md` §14 (issue #102). Nothing here is enclos code. This first part, M3-01, surveys the target hosts: Landlock and its ABI, unprivileged user namespaces and AppArmor, the bubblewrap each distribution packages, the cgroup controllers delegated to the user, and `systemd --user` at logout.

## Files

| File | What it does |
| --- | --- |
| `survey.sh` | Prints one `key: value` line per fact. **Read-only**: it reads `/sys`, `/proc`, the kernel's build configuration, package versions and logind's properties; it runs no bubblewrap, creates no namespace and changes nothing, so it is safe on the user's own host. The Landlock ABI comes from `landlock_create_ruleset(NULL, 0, VERSION)`, which returns a number and restricts nothing. |
| `bwrap-check.sh` | Runs bubblewrap as the user as installed, then with an AppArmor profile that lets `/usr/bin/bwrap` alone make user namespaces, then with AppArmor's restriction off, restoring each setting. **Acts on the host**: refuses to run outside a GitHub-hosted runner. |
| `logout-check.sh` | Logs in over ssh to localhost, starts a `systemd --user` unit, logs out, and checks the unit and the user manager past logind's stop delay, without then with lingering. **Acts on the host** (installs sshd, changes lingering): refuses to run outside a GitHub-hosted runner. |
| `.github/workflows/host-survey.yml` | Runs the three on `ubuntu-latest` and `ubuntu-24.04-arm`, on a pull request that touches this folder or by hand, and writes their output to the job summary. It does not gate merges. |

### What this shows

- **Landlock is not in Raspberry Pi OS's kernel.** It is not active, and not even built: `CONFIG_SECURITY_LANDLOCK` is unset in every Raspberry Pi kernel installed (6.12 and 6.18, Pi 4 and Pi 5 builds), so no `lsm=` boot option can turn it on. ADR 0004 asked for this check before the backend is built. Under ADR 0004 as written, the bubblewrap backend could not run on a stock Raspberry Pi OS. Decided since, in [ADR 0037](../../docs/adr/0037-landlock-where-the-kernel-has-it.md) (proposed): Landlock is applied wherever the kernel has it, and where it is missing the backend still runs, its writes held by bubblewrap's mounts alone and the seccomp filter unchanged; its capabilities declare the weaker execute control, a policy with an `[exec]` section is accepted there only with the user's audited acceptance and not applied, and `doctor` gives what is not enforced, the risk and the fix (design §5, Degraded controls on Linux). The same holds for a Landlock ABI older than the backend's rules need. That the mounts alone hold the writes is still to show (design §14).
- **The memory controller is off on the Pi** by the firmware's own boot arguments, so a session's cgroup cannot hold a `memory` limit there; `cpu` and `pids` are delegated. Decided since, in [ADR 0038](../../docs/adr/0038-a-memory-limit-the-host-cannot-hold-runs-unapplied-once-accepted.md) (proposed), amending ADR 0033: there a policy that sets `memory` is accepted only with the user's audited acceptance, runs with the limit not applied, and every start says so; `doctor` gives the fix.
- **The fix for the memory controller, checked against the kernel's source, untried.** `cgroup_disable=memory` comes from the firmware's device-tree boot arguments (`/proc/device-tree/chosen/bootargs`), not from `/boot/firmware/cmdline.txt`, whose contents follow them in `/proc/cmdline` (measured here), so there is nothing to remove from `cmdline.txt`. Raspberry Pi's kernels define `cgroup_enable=`, which turns a subsystem back on (`static_branch_enable` in `kernel/cgroup/cgroup.c`, on `rpi-6.12.y` at `5bd564aa` and `rpi-6.18.y` at `b3495ea4`; added by [12]), and parse it after the firmware's arguments, so adding `cgroup_enable=memory` to `cmdline.txt` and rebooting should bring the controller back. `cgroup_memory=1`, often suggested, is not a parameter of either kernel: the only one near it is `cgroup.memory=` in `mm/memcontrol.c`, which takes `nosocket`, `nokmem` and `nobpf` [18]. Where the controller is there but not delegated, a `Delegate=` drop-in for `user@.service` is the fix, needed only where its `Delegate=` leaves `memory` out; Debian 13's (measured here) and Ubuntu 24.04's [13] already delegate `pids memory cpu`.
- **Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor and ships no rule for bubblewrap**, so bubblewrap is expected to fail there as installed; whether a profile naming `/usr/bin/bwrap` is enough is what `bwrap-check.sh` tries on the runners. Debian turns neither the restriction nor a bwrap rule on.
- **The oldest bubblewrap among the targets is Debian 12's 0.8.0**, then Ubuntu 24.04's 0.9.0. Whether each has every option the backend uses waits for M3-02's list of options.

## To measure

- **In CI** (the `host-survey` workflow, both runners): every "to measure (CI)" cell. Its first run is the result for the runners, and the table and design §14 are updated from it.
- **In a VM** (Ubuntu 24.04 x86_64 and arm64, Debian 12 and 13): `survey.sh` for the "to measure (VM)" cells, then `bwrap-check.sh`'s steps by hand (it refuses outside a runner by design).
- **Without Landlock** (in a VM booted with Landlock left out of the active LSM list, then on the Pi with the user): that bubblewrap's mounts alone refuse every write outside the home and workspaces (ADR 0037, design §14).
- **`doctor`'s fixes** (design §14): `cgroup_enable=memory` on the Pi, with the user, since it reboots the Pi; the `Delegate=` drop-in and `lsm=landlock,…` in a VM.
- **On the Pi, with the user**: whether bubblewrap runs as the user, and a logout without lingering, both of which act on the user's host.
