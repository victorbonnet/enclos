# Milestone 3 prototype: the host survey and the bubblewrap sandbox

Throwaway scripts that answer the milestone 3 questions in `docs/design.md` §14 (issue #102). Nothing here is enclos code. The host survey reads, on each target host: Landlock and its ABI, unprivileged user namespaces and AppArmor, the bubblewrap each distribution packages, the cgroup controllers delegated to the user, and `systemd --user` at logout. The bubblewrap prototype builds a bubblewrap sandbox as the backend would and probes it: see [The bubblewrap prototype](#the-bubblewrap-prototype) below.

## Files of the host survey

| File | What it does |
| --- | --- |
| `survey.sh` | Prints one `key: value` line per fact. **Read-only**: it reads `/sys`, `/proc` (the kernel's seccomp actions and the process's `Seccomp` and `Seccomp_filters` included), the kernel's build configuration, package versions and logind's properties; it runs no bubblewrap, creates no namespace, installs no filter and changes nothing, so it is safe on any host. The Landlock ABI comes from `landlock_create_ruleset(NULL, 0, VERSION)`, which returns a number and restricts nothing. |
| `bwrap-check.sh` | Runs bubblewrap as the user as installed, then with an AppArmor profile that lets `/usr/bin/bwrap` alone make user namespaces, then with AppArmor's restriction off, restoring each setting. It names a profile for bubblewrap that was already there (`bwrap.with_userns_profile.shipped_profile`). In each of the three it also tries bubblewrap alone, `bwrap --ro-bind / / true`, then a write in the home that it must refuse. **Acts on the host**: refuses to run outside a GitHub-hosted runner. |
| `bwrap-profiles.sh` | Prints the AppArmor profiles named for bubblewrap, for the two scripts here that report them. **Read-only.** |
| `logout-check.sh` | Logs in over ssh to localhost, starts a `systemd --user` unit, logs out, and checks the unit and the user manager past logind's stop delay, without then with lingering. **Acts on the host** (installs sshd, changes lingering): refuses to run outside a GitHub-hosted runner. |
| `test_survey.sh` | Checks `survey.sh` with a stubbed `busctl`: the seccomp lines are printed, and `unknown` is reported when logind cannot be asked. Also starts `bwrap-check.sh` and `logout-check.sh` with the runner's variables unset, and checks that each stops at its guard (exit 2 and the guard's message), before acting. Safe on any host. |
| `.github/workflows/host-survey.yml` | Runs the three on `ubuntu-24.04`, `ubuntu-26.04` and `ubuntu-24.04-arm`, on a pull request that touches this folder or by hand, and writes their output to the job summary. It does not gate merges. |

### What this shows

- **Landlock is not in Raspberry Pi OS's kernel.** It is not active, and not even built: `CONFIG_SECURITY_LANDLOCK` is unset in every Raspberry Pi kernel installed (6.12 and 6.18, the `-v8` and `-2712` builds), so no `lsm=` boot option can turn it on. ADR 0004 asked for this check before the backend is built. Under ADR 0004 as written, the bubblewrap backend could not run on a stock Raspberry Pi OS. Proposed in [ADR 0037](../../docs/adr/0037-landlock-where-the-kernel-has-it.md) (proposed): Landlock is applied wherever the kernel has it, and where it is missing the backend still runs, its writes held by bubblewrap's mounts alone and the intended seccomp filter kept (shown by no run on such a kernel); its capabilities declare the weaker execute control, a policy with an `[exec]` section is accepted there only with an explicit, audited acceptance and not applied, and `doctor` gives what is not enforced, the risk and the fix (design §5, Degraded controls on Linux). A Landlock ABI older than the backend's rules need is a different case: the rights it has apply as a layer over the mounts and those it lacks rest on the mounts alone; whether execute rules apply there is open (design §15). That the mounts alone hold the writes is still to show (design §14).
- **The memory controller is off on Raspberry Pi OS** by the firmware's own boot arguments, so a session's cgroup cannot hold a `memory` limit there; `cpu` and `pids` are delegated. Proposed in [ADR 0038](../../docs/adr/0038-a-memory-limit-the-host-cannot-hold-runs-unapplied-once-accepted.md) (proposed), amending ADR 0033: there a policy that sets `memory` is accepted only with an explicit, audited acceptance, runs with the limit not applied, and every start says so; `doctor` gives the fix.
- **The fix for the memory controller, checked against the kernel's source, untried.** `cgroup_disable=memory` comes from the firmware's device-tree boot arguments (`/proc/device-tree/chosen/bootargs`), not from `/boot/firmware/cmdline.txt`, whose contents follow them in `/proc/cmdline` (measured (Raspberry Pi OS arm64)), so there is nothing to remove from `cmdline.txt`. Raspberry Pi OS's kernels define `cgroup_enable=`, which turns a subsystem back on (`static_branch_enable` in `kernel/cgroup/cgroup.c`, on `rpi-6.12.y` at `5bd564aa` and `rpi-6.18.y` at `b3495ea4`; added by [12]), and parse it after the firmware's arguments, so adding `cgroup_enable=memory` to `cmdline.txt` and rebooting should bring the controller back. `cgroup_memory=1`, often suggested, is not a parameter of either kernel: the only one near it is `cgroup.memory=` in `mm/memcontrol.c`, which takes `nosocket`, `nokmem` and `nobpf` [18]. Where the controller is there but not delegated, a `Delegate=` drop-in for `user@.service` is the fix, needed only where its `Delegate=` leaves `memory` out; Debian 13's (measured (Raspberry Pi OS arm64), trixie's systemd package) and Ubuntu 24.04's [13] already delegate `pids memory cpu`.
- **Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor and ships no rule for bubblewrap**, and on GitHub's Ubuntu 24.04 runners bubblewrap fails as installed: `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`, and even `bwrap --ro-bind / / true`, with no other option, fails with `setting up uid map: Permission denied`. A profile naming `/usr/bin/bwrap` alone is enough there, and so is turning the restriction off, on x86_64 and arm64 (measured (CI)). Ubuntu's own kernels are still to measure. Debian turns neither the restriction nor a bwrap rule on.
- **GitHub's Ubuntu 26.04 runner differs from 24.04 on bubblewrap.** The restriction is on there too, but `bwrap-userns-restrict` is present, bubblewrap runs as installed, and the profile that fixes 24.04 makes it fail, so that fix must not be carried to 26.04 (measured (CI): [41361921349](https://github.com/victorbonnet/enclos/actions/runs/41361921349)). The cause is not traced, and Ubuntu's own kernels are still to measure.
- **Without lingering, `systemd --user` does not outlive the last logout on GitHub's Ubuntu 24.04 runners; with it, a unit does**, 20 seconds after an ssh logout, with `KillUserProcesses` false, on x86_64 and arm64 (measured (CI)). Raspberry Pi OS and Debian have not been tried, and the question in design §15 stays open.
- **The oldest bubblewrap among the targets is Ubuntu 24.04's 0.9.0.** Debian 12's 0.8.0 is older, but Debian 12 is no longer a target: enclos needs systemd 254 or later and it ships 252 (design §5, Linux hosts); its column above stays as what the survey found. Whether each has every option the backend uses is still to check.

## To measure

Nothing is left for the runners' columns; the workflow keeps measuring them.

- **In a VM** (Ubuntu 24.04 x86_64 and arm64, Ubuntu 26.04 on Ubuntu's own kernel, Debian 13): `survey.sh` for the "to measure (VM)" cells, then `bwrap-check.sh`'s steps by hand (it refuses outside a runner by design).
- **A kernel without Landlock is unproven.** The no-Landlock mode has so far run only as Landlock switched off on a kernel that has it (the Azure runner kernel): nothing has shown that mode on a kernel without Landlock, such as Raspberry Pi OS's, where only bubblewrap's harmless start-up has run. What `survey.sh` reads on seccomp says what the kernel offers, not that the filter holds.
- **Without Landlock** (in a VM booted with Landlock left out of the active LSM list, then on Raspberry Pi OS): that bubblewrap's mounts alone refuse every write outside the home and workspaces (ADR 0037, design §14).
- **`doctor`'s fixes** (design §14): `cgroup_enable=memory` on Raspberry Pi OS, which needs a reboot; the `Delegate=` drop-in and `lsm=landlock,…` in a VM; on Ubuntu 24.04 in a VM, the narrower of `bwrap-check.sh`'s profile and `bwrap-userns-restrict`.
- **On Raspberry Pi OS** (they act on the host, so not on one in use): whether bubblewrap runs as an unprivileged user, and what a logout does to a unit, without and with lingering.

## The bubblewrap prototype

A bubblewrap sandbox built as the backend would build it (design §5, ADR 0004, ADR 0037), and probed: broad reads with the deny list not mounted, writes to the home and a workspace only, Landlock and seccomp applied by a small program run first inside, the relay from `127.0.0.1:<port>` to a proxy on a Unix socket, the host's Unix sockets, Hermes's installer and Chromium. Nothing here is enclos code; the compile step, the program run inside and the relay are drafts of the backend's.

**Where it runs.** Every check acts on the host (it runs bubblewrap, makes user namespaces, plants files in the home, installs packages, changes an AppArmor setting), so `lib.sh` refuses to run anywhere but a GitHub-hosted runner, or a VM for the manual steps below: there `ENCLOS_PROTO_DISPOSABLE_VM=1` must be set and `systemd-detect-virt --vm` must name a hypervisor, so a host that is not a VM is refused either way. The `bwrap-prototype` workflow runs the checks on `ubuntu-24.04` and `ubuntu-26.04` (x86_64) and `ubuntu-24.04-arm` (arm64), on a pull request that touches this folder or by hand. Each check writes a Markdown result to `m3-results/`; the job shows them in its summary and uploads the folder as the artifact `m3-results-<runner>`.

### Files

| File | What it does |
| --- | --- |
| `compile.py` | The compile step: the prototype's policy (the user's home, the sandbox's folder, a workspace, the deny list) becomes bubblewrap's arguments, the Landlock rules and the seccomp filter, in one JSON file. Pure: it reads nothing of the host, so its output can be cached per policy snapshot; what depends on the host is left to `wrap.py`. |
| `wrap.py` | The wrap step, at each session's start: `read_host()` resolves links, lists the home's folders above denied paths and their targets, and refuses a target it cannot hide, and `arguments()` turns the compiled policy and that listing into the final arguments, with `--ro-bind-try` for entries that may go before bubblewrap starts. |
| `test_compile.py` | Tests of `compile.py` and `wrap.py` on a temporary folder: denied paths not mounted, the folders that hide them read-only after every mount, a deny entry inside a workspace or a read-only grant still hidden with the grant as granted, a grant at or inside a deny entry refused, a deny entry that is a link hidden at its target, writes to the home and workspaces only, the namespaces, the seccomp list, a deny entry outside the home refused, and a refused wrap step stopping `sbx.sh` before bubblewrap. Runs anywhere (`python3 -I prototype/m3/test_compile.py`), and first in the workflow. |
| `inside.py` | The program bubblewrap runs first inside: applies the Landlock rules where the kernel has Landlock (through its system calls, with ctypes), then the seccomp filter (libseccomp's Python binding, `python3-seccomp`), then starts the relay and runs the command. `--landlock off` and `--seccomp off` leave either out, to show what each adds; `--proc-truncate` adds `TRUNCATE` to the `/proc` rule, for `oom-check.sh`. It stops the session on a failure it does not expect: Landlock counts as missing only on `ENOSYS` or `EOPNOTSUPP`, and only a fixed set of calls per architecture may be left out of the filter. enclos should take that rule, not the code. |
| `test_inside.py` | Tests of those failures, with a stand-in for the kernel's answer and for libseccomp, so nothing is applied to a process. Runs anywhere (`python3 -I prototype/m3/test_inside.py`). |
| `relay.py` | The relay: each TCP connection on `127.0.0.1:<port>` inside the sandbox forwarded to the proxy's Unix socket, and nothing else. One thread per direction; an EOF ends one direction only. |
| `test_oom.py` | Regression test of the `/proc` rule's `TRUNCATE`, first in the workflow. `ProcTruncateTest` applies the draft Landlock rules to one child process, which runs `echo 0 > /proc/self/oom_score_adj` on its own value: refused as drafted, passes with `TRUNCATE` on the `/proc` rule, and in both the rules applied report `TRUNCATE` handled. It runs only on a GitHub-hosted runner with `ENCLOS_PROTO_LANDLOCK=1`, and skips, saying why, elsewhere or below Landlock ABI 3. `GrantsTest` checks the grants without touching Landlock: `TRUNCATE` is left out of the `/proc` grant alone unless asked for, and stays handled. It runs anywhere (`python3 -I prototype/m3/test_oom.py GrantsTest`). |
| `test_probe.py` | Tests of the probes: the copied shell the exec probes run ends at once with stdin left open, it also runs through the loader and from a memfd, `connect-vsock` asks for the CID it is given (with a stand-in for the socket), no check copies a coreutils program, which on a multi-call coreutils would not run under a new name, and `unshare` runs in a process of its own. Runs anywhere (`python3 -I prototype/m3/test_probe.py`), but for one test that makes a namespace, which needs a GitHub-hosted runner with `ENCLOS_PROTO_NAMESPACES=1` and skips elsewhere. |
| `test_workflow.py` | Tests of the workflow's text: its runners are named by release, it runs every `test_*.py` here, and the Landlock regression comes before the checks with its variable set. Runs anywhere (`python3 -I prototype/m3/test_workflow.py`). |
| `test_relay.py` | Tests of `relay.py` over a loopback port and a Unix socket: 64 MB both ways at once through an echo that writes before it reads again, which hangs a relay that forwards both directions from one thread; a half-close from either end; a failed direction waking the other, stuck in `sendall`; a blocked direction holding up neither the other nor a second connection. Touches no namespace, so it runs anywhere (`python3 -I prototype/m3/test_relay.py`), and first in the workflow. |
| `unix-proxy.py` | The milestone 1 prototype's proxy (`../m1/proxy.py`) served on the sandbox's Unix socket: same allowlist, `--learn` mode and JSON log. |
| `sbx.sh` | Runs a command in the sandbox: compiles, runs bubblewrap, then `inside.py`. `SBX_LANDLOCK=off`, `SBX_SECCOMP=off`, `SBX_RELAY=1`, `SBX_NEW_SESSION=1`, `SBX_PROC_TRUNCATE=1`. |
| `probe.py` | The probes, each printing the probe, `ok` or the error's name, and a detail; run on the host as their control, then in the sandbox. Writes are undone, a ptrace attach is detached at once, `unshare` runs in a process of its own, and the only signal is signal 0. `exec-loader` and `exec-memfd` run a program in two ways that are not an exec of its path; `connect-vsock` tries the hypervisor and the local CID. |
| `pty-run.py`, `table.py`, `lib.sh` | A terminal of its own for the TIOCSTI probe; the result tables; what the scripts share, the guard included. |
| `setup-runner.sh` | Installs bubblewrap and what the checks use, and finds the least setting that lets bubblewrap run under AppArmor (none, a `userns` profile for `/usr/bin/bwrap`, or the restriction off). |
| `sandbox-check.sh` | Files, programs and system calls, in five modes: the host; bubblewrap only; with seccomp but no Landlock (what ADR 0037 runs where the kernel has none); with Landlock but no seccomp; full. TIOCSTI also with `--new-session`. |
| `oom-check.sh` | `echo 0 > /proc/self/oom_score_adj` in the sandbox with Landlock, with and without `TRUNCATE` on the `/proc` rule, with the host and no Landlock as controls and a write without `O_TRUNC` beside it. |
| `sockets-check.sh` | Every Unix socket the host lists (`/proc/net/unix`), named and abstract, connected to from the host and from the sandbox: the runner as it is, then with an X server (Xvfb), a session bus, GNOME Keyring, an ssh agent, a socket in the home and an abstract socket added. |
| `relay-check.sh` | curl, Python `urllib`, `httpx` and `requests`, pip, uv, git, Node `fetch` and npm through the relay, with no DNS in the sandbox, and a destination the allowlist leaves out. |
| `hermes-check.sh` | Hermes's installer in the sandbox through the relay and a proxy in `--learn` mode: endpoints, `sudo` or system packages, `hermes --version`. |
| `chromium-check.sh` | A headless Chromium (Hermes's, or Playwright's when Hermes left none) loading a page, with its own sandbox off: over the DevTools protocol (`cdp-load.py`) on the host as the control and in each sandbox mode through the relay; with `--dump-dom` on the host and in full mode, for comparison; and in full mode with its own sandbox on. |
| `cdp-load.py` | Loads one page over `--remote-debugging-pipe` (create a target, attach, navigate, wait for the load event, read the title), as browser tools drive Chromium. |
| `options-check.sh` | Whether Debian 12's, Ubuntu 24.04's and Debian 13's bubblewrap have every option the compiled arguments use, from each one's `bwrap --help` in a container of that distribution. |
| `.github/workflows/bwrap-prototype.yml` | Runs the above on the three Ubuntu runners and uploads `m3-results/`. It does not gate merges. |

### Results

From the `bwrap-prototype` workflow's runs on the Ubuntu 24.04 runners (Ubuntu 24.04.5, x86_64 and arm64), on kernel `7.0.0-1017-azure`, with bubblewrap 0.9.0, Landlock ABI 8, `python3-seccomp` 2.5.5 and Node 22.23.4; both jobs passed in each. Run [41120146313](https://github.com/victorbonnet/enclos/actions/runs/41120146313), at `df4a85e`, ran every check against the arguments as they are now (the wrap step, the masks in grants, the sandbox home's bind after them, the relay with a thread per direction); a row that does not name it gave the same result there as in the runs before it. Nothing below was measured on `ubuntu-26.04`. A job that passed means the scripts ran, not that every probe closed: each row says what the output shows. "Same" means the two runners gave the same result, apart from process ids and temporary names; "to measure" cells are still to run.

**Modes.** The probes ran on the host as their control, then in the sandbox with bubblewrap only, with seccomp but no Landlock (ADR 0037's path), with Landlock but no seccomp, and with both ("full"). `inside.py` reported `landlock=applied abi=8 handled=0xffff scoped=0x3` (17 rules on x86_64, 15 on arm64, where `/lib32` and `/libx32` do not exist) and `seccomp=applied deny=35` on x86_64, `deny=32` on arm64, naming the three calls arm64 lacks (`ioperm`, `iopl`, `uselib`).

**Not rerun: the host's column.** In every run quoted here all the probes ran in one process and `unshare user` changed it for good, so on the host `unshare mount`, `unshare net`, `mount`, `keyctl`, `bpf`, `perf_event_open`, `userfaultfd`, `io_uring`, `kill`, `ptrace` and the network probes ran from a new user namespace. The sandbox's columns are not affected, as `unshare user` is refused there. `probe.py` runs `unshare` in a process of its own, which no run quoted here did, so each row's host result below stands as the control it was, not as what the host does on its own.

**Not rerun: `TMPDIR`.** Every run quoted here set `TMPDIR=/tmp`, the sandbox's own tmpfs, where Landlock refuses execute. ADR 0015 and design §5 put it inside the home, and `compile.py` sets `<sandbox home>/tmp/`, which persists and can execute, a value no run quoted here used. So the rows on the installer, pip, uv and Chromium, and §14's `mktemp` question, were measured under a `TMPDIR` a real session will not have.

**Not run yet: three routes.** `sandbox-check.sh` also tries the workspace's program through the dynamic loader and from a `memfd`, and a vsock connection to the hypervisor (CID 2) and the local CID (1). Landlock's execute right is checked at exec, so the first two may run a program the rule refuses, and a network namespace does not hold vsock by default, so on a VM host a sandbox may reach the hypervisor around the proxy. Both are kernel behaviour, not observed: no run quoted here used these probes, and the filter here has no rule for either route.

### What this shows, and what it does not

- **The sandbox holds on both runners.** Broad reads with the deny list not mounted (ENOENT), writes refused everywhere but the home and workspace, an empty network with no DNS, the host's sockets out of reach (all of a server install's, and those a runner can start of a desktop's), abstract sockets closed, processes outside hidden. All of it holds with bubblewrap alone; Landlock and seccomp are not needed for any of it. This is shown on Ubuntu 24.04 runners with an Azure kernel only.
- **What Landlock adds** in these probes is the execute control on a direct exec: a program in the workspace, run by its path, is refused with it and runs without it (ADR 0037). Whether that holds through the dynamic loader or a `memfd` is not shown (above). Writes get EROFS from the mounts before Landlock is reached, so these probes do not show Landlock's write rules refusing anything by themselves.
- **What seccomp adds** is `keyctl`, `bpf`, `perf_event_open`, `userfaultfd`, io_uring, a user namespace and TIOCSTI's ioctl. Which of these matter beyond what the runner's own sysctls refuse depends on the host.
- **Chromium loads pages in the sandbox only with `--no-sandbox`**, on both runners, in every mode: a page loads over the DevTools protocol, as browser tools drive it. With its own sandbox on, it aborts at start. **So the browser rests entirely on enclos's sandbox:** a compromised renderer has no browser-side isolation around it, and only the bubblewrap sandbox, Landlock and seccomp stand between it and what the session can reach, its home and workspaces included. `--dump-dom` hangs on the host too, so its failures were the check's, not the sandbox's.
- **Sockets in the home are reached**, as §5 says, so each needs a deny-list entry.
- **A deny entry inside a workspace is masked, not absent.** Unlike the rest of the deny list, its name exists in the sandbox, as design §5 says: what it holds is hidden, and neither it nor the mask can be written. An entry missing from the host leaves a real, empty folder in the workspace, there after the session. The run's workspace is `~/proto-workspace`; one that holds entries of the shared list, such as `~/.cargo`, gets one such folder for each of them missing there, which was not run. The home itself cannot be a workspace: `validate` refuses a write grant that holds a protected path (design §5).
- **Surprises.**
  - The `--no-sandbox` Chromium left running by `--dump-dom` reached Google's update, Safe Browsing, GCM and component services through the proxy (`update.googleapis.com`, `safebrowsing.googleapis.com` about 8 MB, `android.clients.google.com`, `edgedl.me.gvt1.com`, `redirector.gvt1.com`, `www.google.com`). An allowlist sandbox would refuse them, and a public-mode one lets them through.
  - Hermes's installer took its Chromium from a different host on each architecture (above).
  - The hosts Chromium reaches vary by run: in [41120146313](https://github.com/victorbonnet/enclos/actions/runs/41120146313) the proxy logged no `safebrowsing.googleapis.com`, but `clients2.google.com` and another `*.gvt1.com` mirror.
  - Inside the sandbox, Chromium tried the system bus at `/run/dbus/system_bus_socket` and found no socket there (ENOENT), which shows the masking against a real program.
- **Still open:**
  - Hermes's browser tool itself driving Chromium in the sandbox (agent-browser's flags, real pages, clicks and forms), and Chromium under memory pressure without its OOM-score adjustments, in a VM;
  - TIOCSTI with `--new-session` alone;
  - around a mask: renaming the file mask, removing a mask, a mask in a read-only grant;
  - whether Chromium opens `oom_score_adj` with `O_TRUNC`, and whether `TRUNCATE` ends its refusals: `oom-check.sh` and `test_oom.py` cover a shell's write to its own file only, and Chromium itself is still unchecked;
  - open, not decided (design §15): renaming a folder that holds a deny entry, for which Linux has no mechanism (design §5 says it cannot be renamed; nothing here stops it), and a deny entry that is a link or sits under one: `wrap.py` hides its resolved path under the home, masks it in a grant, and refuses the session when it resolves anywhere else, a draft of one option until §15 decides. `sandbox-check.sh` plants both kinds of link; no run has shown them yet;
  - whether a program runs through the dynamic loader or from a `memfd` where Landlock refuses its exec, and whether vsock reaches the hypervisor from the sandbox;
  - a real desktop session's sockets;
  - a kernel without Landlock;
  - the login and a model call;
  - what a refusal leaves for the user to read.

### Manual steps for a VM: the login and a model call

These need an account, so they cannot run in CI. In a disposable VM (Ubuntu 24.04 or Debian 13, x86_64 or arm64), with this repository checked out:

1. `export ENCLOS_PROTO_DISPOSABLE_VM=1`, then `bash prototype/m3/setup-runner.sh`, which installs the packages and finds the AppArmor setting, and `bash prototype/m3/hermes-check.sh`, which installs Hermes in the sandbox's home (`~/.enclos/sandboxes/proto/home`).
2. Start the proxy in `--learn` mode on the sandbox's socket: `python3 -I prototype/m3/unix-proxy.py --socket ~/.enclos/sandboxes/proto/run/visible/proxy.sock --learn --log login.jsonl &`
3. Open a shell in the sandbox, full mode, with the relay: `SBX_RELAY=1 prototype/m3/sbx.sh -- /bin/bash`. Its first lines say what `inside.py` applied.
4. In it, `export PATH="$HOME/.local/bin:$PATH"`, then the device-code login, as the milestone 1 prototype ran it: `hermes auth add openai-codex --no-browser`. Open the URL it prints on another device and enter the code.
5. A model call: `hermes -z "Reply with exactly one word: ok" --provider openai-codex -m <a model the account offers>`.
6. Record, in the results table above: whether each step worked, the endpoints from `login.jsonl` (host, port, verdict), and whatever refused, never the code or a token.
7. Then the same in the mode without Landlock (`SBX_LANDLOCK=off`), and, for a desktop install, `bash prototype/m3/sockets-check.sh` from a graphical login.

### What enclos's relay may take from this one

`relay.py` forwards each direction in a thread of its own and carries an EOF across with `shutdown(SHUT_WR)`. A relay that closes both directions on the first EOF, or sends with a blocking `sendall` from one thread, can deadlock on a large two-way transfer; `test_relay.py` hangs and fails on one.

enclos's relay may take the behaviour, which `test_relay.py` states: an EOF ends one direction only, a direction blocked on a slow reader holds up neither the other direction nor other connections, and a failed direction ends both, one stuck in `sendall` included. (enclos's relay took all of it but the last: its failed upload ends the upload alone, as the proxy may still be answering.) It may take the tests' scenarios too. No test states memory: that it stays bounded per connection is read from the code, which holds nothing beyond one read and the kernel's socket buffers. It should not take the code: this is Python with two threads per connection, no limit on connections, no idle timeout (one that fires on a quiet direction would cut a long download or upload, so it needs a decision of its own), and no measurements of throughput or of many connections. In run [41120146313](https://github.com/victorbonnet/enclos/actions/runs/41120146313) it ran in the sandbox on both runners and carried every client in `relay-check.sh` and Hermes's installer, 941 MB down on x86_64 and 906 MB on arm64 by the proxy's log, the largest connection 146 MB; no client failed. Those transfers are almost all one way, so the two-way load and the half-close are still shown by `test_relay.py` alone, over loopback.

- `ioctl` refused with `EPERM` when its request's low 32 bits are `TIOCSTI` (`0x5412`) or `TIOCLINUX` (`0x541C`).
- `unshare` and `clone` refused with `EPERM` when their flags hold any of `CLONE_NEWNS`, `CLONE_NEWUSER`, `CLONE_NEWPID`, `CLONE_NEWNET`, `CLONE_NEWIPC`, `CLONE_NEWUTS`, `CLONE_NEWCGROUP`, `CLONE_NEWTIME`.

- `clone3` refused with `ENOSYS`, since its flags are in memory seccomp cannot read; the C library then falls back to `clone`.
- `ptrace` is not refused, so debuggers inside keep working, and the PID namespace leaves nothing outside to trace (the probe tries a host process). What is inside is another matter: these runs have no `--as-pid-1`, so bubblewrap's reaper is PID 1, with neither filter nor Landlock, and it is dumpable. Landlock refuses an attach to it, and so does Yama at `ptrace_scope` 1, since PID 1 is an ancestor; a host with neither, such as Raspberry Pi OS by the survey, has nothing in the way. Refusing `ptrace` alone would not do, because `/proc/1/mem` stays open. So the compiled arguments hold `--as-pid-1`, and what runs first confines itself and stays as PID 1 (`inside.py --stay-pid-1`, not dumpable). `sandbox-check.sh` compares the two with no Landlock and `ptrace_scope` 0; no run has shown it yet.

The errno is a choice for the backend: `EPERM` reads like the kernel's own refusals, so the probes tell the filter from bubblewrap by comparing the modes, not by the error.

## Namespaces per session or per sandbox

Design §5's A session's namespaces and its §14 items: a session with a network namespace of its own reaches neither its runtime's service port ([ADR 0028](../../docs/adr/0028-a-runtime-listens-and-its-sessions-reach-its-service.md)) nor anything another session of its sandbox listens on. The question is whether every session of a sandbox can share one network namespace enclos made first, with bubblewrap started inside it. bubblewrap joins an existing user namespace (`--userns`) and PID namespace (`--pidns`) but has no option to join a network namespace, and entering one needs a capability in the user namespace that owns it. So the experiment tries each way of joining, and records what sharing changes. It runs only in CI, as the bubblewrap checks above do (`lib.sh`'s guard).

**The holder.** `ns-holder.py`, started by bubblewrap in a new user, PID and network namespace, stands for what enclos would run per sandbox (in its proxy service, for instance). It opens its own namespaces and hands them as file descriptors to whoever connects to its Unix socket, in a folder of the sandbox's that no session mounts, so the host needs no access to `/proc/<pid>/ns`. It also serves the sandbox's one relay on `127.0.0.1` in that network namespace. It is started without `--dev /dev`: with that option bubblewrap makes a second, nested user namespace for the program it runs, so the holder hands out the inner user namespace while its network and PID namespaces belong to the outer one, and every join is refused (A namespace per session, below).

**The ways a session joins** (`nsjoin.py`; the descriptors arrive as 10, 11 and 12 through `ns-fds.py`):

| Way | What runs | Network | PIDs |
| --- | --- | --- | --- |
| `own` | `sbx.sh`'s arguments as they are (control) | its own | its own |
| `nsenter` | `nsenter` enters the holder's user and network namespaces; bubblewrap makes a user namespace nested in it | the sandbox's | its own |
| `nsenter-pid` | the same, `nsenter` also entering the holder's PID namespace, which bubblewrap keeps | the sandbox's | the sandbox's |
| `nsenter-userns` | `nsenter` enters the user and network namespaces, then bubblewrap is given that same user namespace with `--userns` (expected refused: a process cannot join the user namespace it is in) | the sandbox's | its own |
| `userns` | bubblewrap joins the holder's user and PID namespaces (`--userns`, `--pidns`) and keeps `CAP_SYS_ADMIN` there; `inside.py --setns-net-fd` enters the network namespace, then drops every capability, then applies Landlock and seccomp | the sandbox's | the sandbox's |
| `userns-subpid` | the same, with a PID namespace of the session's own under the holder's (`--unshare-pid` with `--pidns`) | the sandbox's | its own, under the sandbox's |
| `userns-net` (rejected) | bubblewrap joins the holder's user namespace alone (`--userns`, no `--pidns`), makes a PID namespace of the session's own, and keeps `CAP_SYS_ADMIN`; `inside.py --setns-net-fd` enters the network namespace, drops every capability, then applies Landlock and seccomp (no `--disable-userns`, which needs `--unshare-user`: the filter refuses a new user namespace) | the sandbox's | its own |

The sandbox cannot write `run/`, so it can neither move the socket nor change the port | its own | its own |

**How Hermes's dashboard starts, read in its source** (the public repository at `bf0203a794a07aac3ff764972ab9087baa4e4f4e`, the commit CI installed; the installed copy is checked in `dashboard/source.txt`). Read, then measured where this section's table says so:

- A second `hermes dashboard` or `hermes serve` attaches to a live one and exits 0 (`_attach_to_host_backend`) unless `--isolated`; that record lives in the home, which every session of a sandbox shares. So `dashboard-cmd.py` starts `hermes dashboard --no-open --isolated --port 0`, its server its own whatever another session left open. The terminal's address follows the bound port (`app.state.bound_port`), read in this source and not yet in a run; `dashboard-cmd-check.sh`'s last rows, with a dashboard open in another session, are what a run must show.
- Auth is off on a loopback bind (`should_require_auth` is true only for a host outside `localhost`, `127.0.0.1`, `::1`).
- The Host check (`_is_accepted_host`) drops the port and compares the name, so `127.0.0.1:<any port>` should pass; WebSockets repeat it (`ws_host_origin_reason`) and also check `Origin`, on the name alone. `/api/ws` also wants a loopback peer, which the holder's relay is in the namespace. The page builds its URLs from its own origin.

**The host's path** (ADR 0040, proposed; `host-listen.py`, `ns-holder.py --host-relay`, `dashboard-check.sh`): while the service runs, a listener on the host's `127.0.0.1` at the sandbox's reserved port passes each connection to a Unix socket in the host-only folder, and the holder's relay takes it to `127.0.0.1:<service port>` in the sandbox's network namespace. The address is hard-coded, with no setting. The port comes from the host's reading of the service's sockets, never from a file the sandbox writes. In the check, `run/<sandbox>/` is the holder's own folder, on the deny list, and the holder's side is called a relay as the glossary asks. Loopback is shared by every user of the host and Hermes has no auth there, and on this path, with nothing looking at who connects, a page that publishes its session token gave it to any local user. So `host-listen.py` refuses every other user's connection before a byte reaches the service (`peerowner.py`), measured with a second user in `enclos dashboard`, above.

### What this shows, and what it does not

- **Shown:** with a network namespace per session, a session reaches nothing another session of its sandbox listens on, and Hermes's chat fails to reach its gateway in another session (`Gateway connection failed; no local fallback`). A listener in a sandbox's network namespace is not reachable from the host either, on 127.0.0.1 or on every address. A holder in bubblewrap can make a sandbox's namespaces and hand them out over a socket.
- **Joining works once the holder has no `--dev /dev`:** with it, every join was refused with EPERM, by `nsenter` entering the network namespace and by bubblewrap's `--pidns`, because `--dev /dev` gave the holder a nested user namespace. The holder without it is joined in every way but `nsenter-userns`.
- **Also tried:** bubblewrap given the holder's user namespace (`--userns`) without `--pidns`, then `inside.py` entering the network namespace (`userns-net`), and a namespace per session with the service's port relayed through a Unix socket (`relay`), both in The relayed port, above.
- **Not tried, and no longer needed:** `nsenter` under an AppArmor `userns` profile of its own, which Joining the holder shows is not what refused it; the holder itself starting each session's bubblewrap from inside its namespaces.
- **Answered for Hermes:** its clients find a gateway in another PID namespace, and a chat that reaches the gateway starts none of its own (The relayed port, and Joining the holder). A chat started with no gateway running does start one (Restarts and each layer).
