# The bridge signs runtime-approval decisions

A runtime approval ([0053](0053-runtime-approvals-use-exact-native-requests-and-explicit-scopes.md)) reaches the agent's channel plugin as a `question.answer` from the bridge. The plugin knows the bridge only by the agent's token, which the agent can read ([0036](0036-an-agent-has-its-own-bot.md)), on a socket in the sandbox home. So a program of the sandbox can connect to its own plugin while the bridge is away, or listen on the socket's path and take the bridge's messages, and send an approval of its own command. A typed `/approve` in a `message.in` that says `host: true` does the same.

Decision (proposed):

- **The key.** The bridge signs every runtime-approval decision with a P-256 key of its own, made by the first command that needs it and kept in `app-approvals.key` in enclos's data folder, `0600`. It signs nothing else, and each statement starts with the label `enclos/runtime-approval/1`. It is not the bridge's X25519 Noise key, which cannot sign. No sandbox reads it: bubblewrap hides the whole data folder, and Seatbelt hides it with the bridge's database and Noise key, which a sandbox could read before.
- **What is signed.** The agent (`sandbox/agent`), the conversation, the approval's id, the id of the `question.answer` that carries the decision, the action, the approval's command, reason and patterns exactly as defined, and the signing time, each field after its length. The answer carries the time and the signature (`signed: {at, sig}`).
- **Where the plugin gets the public key.** `enclos runtime configure <sandbox>/<agent> --channel app` writes it into the agent's settings (Hermes: `MOBILE_APP_BRIDGE_KEY`), beside the plugin, and the plugin reads it once, when it starts. The bridge's `hello` carries no key: anyone with the token can send one. The plugin takes the agent's name from its socket and the sandbox's from `ENCLOS_SANDBOX`, which enclos sets for every process of the sandbox.
- **What the plugin checks.** Before it resolves a native approval, that the signature verifies with that key over the decision rebuilt from its own card (its id, conversation, command, reason and patterns), the `question.answer`'s id and the action asked, and that it was made within the last 60 seconds. An approval resolves once; a decision for one that is closed changes nothing. Any other decision, unsigned, forged, altered, stale or meant for another approval, is refused with `not_allowed`, logged, and its approval, while it waits, is denied: the command does not run on the word of whoever spoke on the socket.
- **Typed approval commands.** A `message.in` carries no proof of its person, so `host` grants nothing. The plugin answers every approval command itself, read with the runtime's own parser, whoever sends it, and the bridge refuses them from everyone, the host's person included. A runtime approval is decided with a paired device's buttons alone; `enclos app chat` sends `host: false`. This replaces 0053's rule that the host's person's typed commands pass on. Where no card can show an approval, nothing in the app decides it: the plugin denies it at once where the runtime resolves its exact request, and the runtime's timeout denies it otherwise.

**The trust assumption.** The plugin, its settings and the runtime are in the sandbox home, which the agent writes. The signature stops an agent that speaks on the plugin's socket, replays a decision or alters one on the way; it does not stop one that rewrites the plugin, its settings or the runtime, which can then skip any check made inside the sandbox, the runtime's own approval guard included. That is within [0014](0014-threat-model-accidental-damage.md)'s threat model, accidental damage by an agent the user mostly trusts. Putting the plugin and its key out of the agent's reach is a separate decision.

Reason: approving a command is the one message from the bridge that grants the agent something it does not have, so it is the one that needs a proof the agent cannot make. A signature the plugin checks needs no secret in the sandbox, unlike a shared key, and a configure-time key, unlike one in the `hello`, cannot be swapped by the program it guards against. Binding the signature to the plugin's own card, the request's id and a recent time makes a decision good for one approval, once.

Considered options: signing typed approval commands too, so that the host's person could still type `/approve`. It would keep a typed path that resolves the oldest pending request rather than an exact one, and needs a second signed message; the owner chose the buttons alone.
