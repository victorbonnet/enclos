# A runtime may listen in its sandbox, and the sandbox's sessions reach its service's port

Hermes 0.22.3's gateway binds a TCP listener on `127.0.0.1:0` when it starts, for its session WebSocket (`/api/ws`) and its dashboard, and exits if the bind is refused. Its chat (CLI, TUI, stream-json) never runs on its own: it finds the gateway, gets a ticket for its own agent (a Hermes profile) over the gateway's Unix socket in the home, and dials the port the gateway gives; it starts a gateway if none runs, and fails with no fallback when it cannot reach one. The compiled policy's `(deny network*)` refuses both the bind and the dial, so neither the gateway nor any chat works in a sandbox (issue #64). enclos adapts to Hermes as it ships.

Opening outbound loopback (`localhost:*`) would let the chat dial its gateway, and also every other loopback service: other sandboxes' proxies, and with them their policies, other sandboxes' gateways, and the user's own tools. That is the loopback exception §6 rules out.

So, for a runtime whose adapter declares a listening service:

- **It may listen.** The policy's `[network] listen`, which the adapter's layer sets, lets the sandbox bind TCP (`network-bind` and `network-inbound`) on any port but enclos's proxy range, which becomes 41000 to 41999 (from 41000 to 48999). Each port of that range is denied by exact port, whether or not it is reserved yet or its proxy runs, so no sandbox can take another sandbox's proxy port.
- **Its sessions reach its service's port.** When a session starts while the service listens, enclos gives it that port: the compiled policy, one per snapshot as before, holds `(if (param "ENCLOS_SERVICE") (allow network-outbound (remote tcp4 (param "ENCLOS_SERVICE"))))`, and `wrap` passes `-D ENCLOS_SERVICE=localhost:<port>`. `tcp4` opens 127.0.0.1 alone, where Hermes listens, not `[::1]` at the same port. The port is the one TCP port at 127.0.0.1, not every address, that the program enclos started for the service holds in the system's ephemeral range, with no other process holding 127.0.0.1 at that port, which is where a bind on port 0 lands, so a port the runtime binds by number (Hermes's API server and webhook adapters) is not taken for it. enclos reads it from its records of the service's session and `lsof`, never from a file the sandbox writes, checks that the program is the same process before and after reading its ports, so a reused PID is not taken for it, and gives no port when there is none or several, which the session says when it ends. Hermes then works as it does outside enclos: each client finds the gateway and gets a ticket for its own agent.
- **`connect` starts the sandbox's services** when the runtime is installed and its service is neither installed nor running, as when the sandbox was started before its runtime was installed, waits for it to listen, and says so, since a session started before the service listens gets no port. A service already installed is the service manager's to start again, so `connect` only waits for it.

`listen` means listening on any port but the proxy range, on every address, and Seatbelt enforces exactly that, so [0009](0009-refuse-what-cannot-be-enforced.md) has nothing partly enforced to refuse: no rule claims to hold a listener to loopback, and none could, since `(local tcp "localhost:*")` also allows a bind on `0.0.0.0`, which the host's network reaches, and no inbound filter on the peer's address changed that (macOS 26.5.2). Anything in such a sandbox can therefore serve the network on a port outside the proxy range, and answer over a connection it accepted, without the proxy or the network log. Under the threat model ([0014](0014-threat-model-accidental-damage.md)), a misled agent is unlikely to do that and a compromised one could; `enclos policy show` and `enclos policy test` say that listening is open, and `enclos status` names each such listener.

This revises [0007](0007-network-through-a-proxy-per-sandbox.md), where the proxy is a sandbox's only way out, for a runtime that declares a listening service: its sessions also reach that service's port, and what it serves can be reached from outside. It revises [0024](0024-agents-reached-through-the-runtime.md), where each sandbox has one proxy port: the sandbox keeps one proxy port, and its sessions also reach the port of its own service.

## Considered options

- **Outbound loopback for the sandbox:** works with nothing else, and opens every service on the host's loopback, other sandboxes' proxies among them (above).
- **A forward through the proxy, with the address and a token in the environment** (`HERMES_TUI_GATEWAY_URL`, `HERMES_DASHBOARD_SESSION_TOKEN`): survives a gateway restart, but Hermes binds a session reached that way to the agent the gateway was started for, and no client can name another, so every named agent ran as `default`; Hermes's kanban refuses that address outright (shown with Hermes 0.22.3, issue #64). Making it pick the agent would mean minting tickets over Hermes's private control protocol, for an agent enclos would have to guess.
- **One more reserved port per sandbox for the runtime's listener:** Seatbelt can allow exactly one port, but Hermes binds port 0 and has no setting for its port.
- **Pinning an older Hermes, or asking Hermes for a Unix-socket listener:** each makes enclos depend on the runtime not moving.
- **Denying only the proxy ports reserved when the policy is compiled:** a few rules, but a sandbox started before another was created could bind the newer one's port once that proxy exits, and the newer sandbox's running sessions would send their connections to it. Seatbelt has no port ranges, so the range is denied port by port: 1,000 rules add about 0.03 s to a launch and 8,000 about 0.9 s (macOS 26.5.2), hence a range of 1,000 ports.

## Consequences

- A session reaches the port the service held when the session started. When the service restarts, it binds another port, and the sessions opened before cannot reach it until they are opened again; the old port stays allowed for their lifetime, so another program that later listens on it at 127.0.0.1, on the host or in another sandbox, would be reachable from them.
- In such a session, a chat started while the service is down starts a gateway of its own, which it cannot reach, and which holds Hermes's gateway lock until it exits for idleness; the service cannot start meanwhile.
- The service itself, and what it starts, were started before it listened, so they get no port: the kanban processes Hermes's gateway starts cannot reach it.
- A Hermes adapter that listens on a port of its own (the API server, webhooks) is not the gateway's port, so chat keeps working; one bound to every address serves the host's network, and `enclos status` names it.
- A sandbox whose runtime declares a listener can be reached on that listener from the host, as the runtime is outside enclos: Hermes's dashboard works in the host's browser, and Hermes leaves its auth gate off on loopback.
- enclos's proxy ports are 41000 to 41999, every install's: at most 1,000 sandboxes on a Mac, fewer when other programs hold some of those ports. Programs outside enclos can still take one, as before (§4).
- A `connect` of such a sandbox whose service is not installed installs its services as `sandbox start` does: they start again at each login until `enclos sandbox stop`, and a running proxy (one an earlier `connect` started, or the proxy service) is replaced by the new proxy service, which cuts its open sessions' connections. `connect` says both, and so does its dry run; a start that fails removes the proxy service too, and says so.
- Another runtime with a local service declares its service; one without declares nothing and keeps today's policy.
