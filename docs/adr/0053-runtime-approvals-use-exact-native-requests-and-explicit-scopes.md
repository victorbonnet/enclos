# Runtime approvals use exact native requests and explicit scopes

Hermes's command guard already waits for Allow once, Allow for session, Always allow or Deny. Typing `/approve` addresses native pending work, while a stale app button must never resolve a later request. Treating a runtime approval as an ordinary information question would also invent Other/Skip or lose the meaning of persistent consent.

Decision (proposed): extend [0052](0052-questions-keep-their-runtime-waiter-and-structured-app-controls.md)'s durable control transport with explicitly typed runtime-approval metadata and actions, a separate capability and a distinct history kind. The runtime supplies the full redacted display command, reason and permitted consents; a card is made only when that display command is the very command of its pending native request, and otherwise the request is denied and shown as text, so no one approves a command redaction changed. The bridge requires both the current conversation owner and the host's own person on a paired device. Its adapter resolves only the exact native request; it neither sends a chat command nor executes a host shell command. The native guard continues under the unchanged sandbox policy, and retains responsibility for pattern grants and execution. Existing revision, receipt, reconnect and no-automatic-retry rules apply, including Deny.

The bridge signs each decision of these controls with a key no sandbox reads, and the channel acts on no other ([0060](0060-the-bridge-signs-runtime-approval-decisions.md), proposed): the agent's token, which the agent can read, proves nothing about the person. Typed approval commands (`/approve`, `/deny`, and `/yolo` and `/approvals`, which turn the gate off) decide nothing: a runtime reads them from whoever it is told speaks, and a message carries no proof of its person, so the bridge refuses them from everyone, the host's person included, and the channel answers them itself, read with the runtime's own parser. 0060 replaced this ADR's first rule, which passed the host's person's on. An approval in a conversation the host's person does not own is refused, and the runtime denies it at once.

Android and iOS show the complete command and reason with only the offered consent buttons, using each platform's native controls in the app's design tokens. The command wraps rather than hiding its end, writes out every hidden character (controls, bidirectional and zero-width marks) as `⟨U+XXXX⟩`, and is flagged when it holds a character outside ASCII. There is no default choice. Deny-only remains deny-only. Session and Always name the runtime's patterns they cover, every command matching them rather than this one alone; a runtime that cannot name them offers neither. Always asks for confirmation and says where its grant is revoked. An exact receipt confirms the consent action, never execution success. A native decision made elsewhere closes the card without inventing its undisclosed consent or outcome. Android is implemented first; the app's spec and ADR record iOS parity.

Reason: reusing durable delivery avoids a second control queue, while distinct typed actions preserve the authority difference between information, runtime consent and sandbox policy requests ([0046](0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md)). Feature-detect native exact-request and additive lifecycle APIs; older Hermes, bridges and apps get the command as readable text, which nothing in the app decides: the runtime denies it. Matching by command text, queue position or session alone cannot make a stale button safe. This is a generic runtime contract; Hermes is its first adapter.

Persisted typed approval answers and the actionless `resolved` state require an approval-aware bridge reader. Rolling back to the preceding binary over those retained records requires a compatible reader or a pre-feature database restore; client text fallback does not make that database downgrade safe.
