# The host's person manages sandbox policy from the phone

Extends the exact-scope approval surface in [0046](0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md) and amends the remote-control non-goal for the host owner's paired phone. The sandbox page needs to show accepted access and let its owner remove it or override inherited defaults later.

Only the host's person ([0044](0044-each-agent-has-a-home-conversation.md)) on a still-paired device may inspect or edit policy. The phone proposes one typed field change, never a command or a policy file. The host previews its exact resolved differences and restart requirement; apply revalidates that preview under the state lock against the snapshot, file and running-session state. Edits affect one sandbox, preserve normal host validation (a writable path the person adds is checked as on the host, not narrowed as an agent's request is under 0046: the person writes it, not the agent; so a paired device's keys can grant what `enclos policy edit` can), keep built-in sensitive read denials locked, and leave secret-grant management on the host. Inherited values can be overridden without changing a shared template. A list edit changes only the sandbox's own entries: an addition goes to `<list>_add`, and removing an inherited entry names it in a new `<list>_remove`, applied after a replacement and before additions, rather than writing the resolved list as a replacement, which would freeze the template's, the runtime adapter's and the built-in defaults' entries in the sandbox's file (a frozen `read_deny` would even be refused once a later enclos adds a default denial). `_remove` is part of the policy file format from then on: an older enclos refuses a file that uses it. Saving is audited, updates owner devices and supplies every agent the active policy context; interruption never queues a replay.

The phone asks for its owner each time (the owner's decision): answering a policy request ([0046](0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md), approve or deny) and saving a policy edit always ask for the phone's biometric or screen lock (on Android, a strong biometric or the device credential), whatever the app-lock setting, and cancelling the prompt sends nothing. A phone handed over unlocked, or left open on the sandbox page, then cannot widen a sandbox with one tap. This is the app's check (enclos-app #29 and #32): the bridge cannot see it, and a program holding a paired device's keys could send the same message without it, so the bridge's own checks (the host's person, on a device still paired) stay what guards the host.

This grants existing owner devices policy-editing authority, so revocation is unpairing the device. A separate admin enrollment would narrow authority further, but would split this owner's approval and later-removal flows; shared users and agent plugins receive no such authority. Full policy-file editing is rejected here because a typed single-field edit can be checked and explained before it is applied.
