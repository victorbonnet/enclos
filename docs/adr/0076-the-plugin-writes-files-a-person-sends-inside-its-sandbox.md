# The plugin writes files a person sends inside its sandbox

Context: a person should be able to send an agent photos and documents with a message from the app (issue #298). The bytes reach the bridge, which runs on the host outside every sandbox, and must end up where the agent's runtime reads them, in the sandbox home. Something has to write them there.

Decision: the agent's channel plugin writes them. The bridge stores the message with its files in its own media folder, as it keeps an agent's files, then sends the plugin `message.in` with the files declared and their bytes in `message.part`s over the plugin's existing socket. The plugin writes them in its own folder of the sandbox home and gives the runtime the message once every byte came. The bridge never writes into a sandbox home, and adds no listener, mount or grant for this. A plugin that does not name `incoming_files` is sent no file: a message with files for it is refused whole, never sent as its text alone. A message's bytes live only as long as the device's connection until it is stored: there is no upload session, resume, upload store or ledger, and a message whose bytes did not all come is dropped and sent again whole ([protocol.md](../protocol.md#sending-files)).

Reason: a host process writing into a folder the sandbox controls must defend every path step against links, renames and races a program of the sandbox can make, with the host's authority; a mistake lands bytes outside the sandbox. The plugin writing inside its sandbox stays under its existing policy and is trusted no more than the agent. The cost is that the bytes cross a second socket, in bounded parts, and are sent again whole after a disconnect, which the limits (4 files of 10 MB) keep small.

Current limitation: completion streams up to 40,000,000 bytes on the device's session thread while holding the plugin output lock. A slow plugin delays that device session and other forwards to the same agent. This proposal does not add a queue or change the threading model.

Retention is partially implemented: recognized completed or abandoned copies expire after 24 hours, checked each minute while listening; successful native conversation deletion removes copies with matching conversation metadata, and cleanup failures require retry. Legacy or incomplete metadata permits expiry but not conversation attribution; unexpected entries and symlinks are preserved. New file deliveries use public `admit_producer`, which commits independent immutable runtime-owned bytes. Receipt identity and session reference are atomically recorded. Plugin staging for this path expires after 24 hours, including restart uncertainty; runtime queued bytes are independent. Legacy pending markers remain protected. Focused synthetic public producer-ingress, native capture, receipt and reopened-ledger tests pass; actual native runtime/device integration remains unverified. Disconnect waits up to five seconds for its owned cleanup worker and shielded native admissions; timeout retains ownership and fails before teardown. Filesystem enumeration has no successful-completion time bound.

The device ACK confirms durable whole-message storage, including a successive file upload queued behind unsettled admission in the same conversation; it does not confirm runtime admission. Forwarding remains ordered, and other conversations can proceed.

Explicit plugin errors naming a stored incoming file operation now settle pending and append one deduplicated status notice in the original conversation in one transaction. The notice names the original device operation and filenames with a safe reason; after commit a connected original device receives an error naming its begin id. Following same-conversation messages wait for the file operation to settle, including files already sent on the current plugin connection; other conversations continue. A file ACK or committed terminal refusal resumes forwarding. Missing bridge copies settle in the same way before later text proceeds. Ordinary history retains the notice, and same-operation retry cannot reopen pending. Image eligibility and receipt-only staging expiry now have implementation; actual native runtime/device execution remains unverified.

Native capture is shielded through completion before active staging is released. A definitive refusal before the native write emits a correlated error; cancellation or a write with an uncertain outcome does not announce terminal failure. Failure to save the diagnostic receipt marker after admission does not undo admission or request a resend. New immutable-capture staging manifests permit expiry after 24 hours even across the commit-to-marker crash gap. Older pending staging without that manifest remains conservatively retained; it has no equivalent bounded-lifetime guarantee.

Image arrival checks enter the producer's owning profile scope before loading configuration or resolving the conversation model. The conversation resolver is a compatibility-guarded private Hermes seam; image routing and auxiliary requirement checks use public Hermes functions. Synthetic tests hold execution scheduling and substitute runtime scope/client-construction seams; they do not demonstrate a native app turn or model perception.
