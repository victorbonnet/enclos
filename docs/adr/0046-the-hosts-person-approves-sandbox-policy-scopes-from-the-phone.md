# The host's person approves sandbox policy scopes from the phone

Amends [0042](0042-a-bridge-on-each-host-serves-the-mobile-app.md)'s read-only consequence and §2's remote-control non-goal; narrows the future `approve` ability in [0043](0043-sharing-an-agent-is-not-hosting-it.md): it does not authorize widening a sandbox policy for another person.

A refused action should be reviewable from the mobile inbox, and accepting its grant should persist in the sandbox policy and the agents' knowledge. The sandbox remains the permission boundary ([0003](0003-sandbox-is-the-permission-boundary.md)); an approval for one agent therefore affects every agent in it.

Decision (proposed): only the host's person (ADR 0044: the person of the first device paired at the host's terminal, or the one `enclos app host` names), using a still-paired device, may approve or deny a request. While no host's person is recorded, decisions are refused. This applies to the host person's existing paired devices; pairing now carries the authority to approve these grants, so protect those devices and unpair a lost one. Sharing chat or a runtime's approval ability confers no policy authority. The bridge previews a single destination and its port, an explicit private-address opt-in, or a writable path and everything beneath it. The engine validates that exact change under its state lock, with an unchanged policy revision and no pending changes or unapplied edits. Decisions are audited with the person, device and request. Network changes go live through the proxy; filesystem changes restart the sandbox, explicitly stated on the approval button. Sensitive read denials and enclos's protected paths remain unavailable for approval.

The host's person may approve one absolute writable path under at least the policy validation of the app's manual editor and `enclos policy edit`. An agent proposes the path, but only the person's explicit approval grants it. Hidden folders such as `~/.gradle`, shell and tool settings, executable folders on the host's `PATH`, and paths outside the user's home are not refused merely for that location. A path that is, holds or is inside one of them (a hidden file or folder in the home, `~/Library`, `~/Applications`, `~/bin`, `~/go/bin`, or a folder on the bridge's `PATH`; on macOS without case) opens its preview with a warning naming it and saying that what an agent writes there can run as the person, outside the sandbox: a warning shown for every grant alike would carry no signal. The user's home folder itself and the folders holding it are refused: one approval would let an agent change everything in the home, and only enclos's own folders, when they are there, would otherwise stop it. The preview names the resolved path and warns that every agent in the sandbox may create, change or delete its contents, including hidden entries (`.git/hooks`, `.envrc`, editor settings), which tools on the host may read and run outside the sandbox. Approval persists and may require a sandbox restart. Built-in sensitive denials, protected paths and backend validation still apply; a request cannot grant a filesystem root or remove read denials. The host's person decides whether the warned access is appropriate, with the device authentication required by [0047](0047-the-hosts-person-manages-sandbox-policy-from-the-phone.md).

A private-address opt-in is for an IP address or a local name (`.local`, `.home.arpa`, `.internal`, `.lan`), which nobody outside can point at the host's network later. Other private-address opt-ins are granted through the policy editor or on the host. The phone shows the entry approval writes (the protocol's `scope`), the resolved path or normalized destination, apart from what the agent asked for.

A proxy refusal becomes a request once: refusals from before the bridge's first collection never do, and one seen before a request for the same access was made is that request's, so a denial is not asked again after an unrelated policy change; only a refusal after it is. One sandbox has at most 50 pending requests; an agent past that is told to wait. An agent that asks again for an access already decided under the active policy is told so, not left waiting.

Requests and decisions survive reconnect and bridge restart. One device claims a decision atomically; an interrupted application is marked for host review, never replayed. Denying changes no policy. The plugin persists a description of the active policy and supplies it to future model turns; that description is advisory, and the backend and proxy still enforce the policy. Approval does not automatically replay an attempted action.

[0054](0054-closing-a-policy-request-is-not-a-denial.md), proposed, adds a separate **Close request** action for pending and failed requests, including scopes unavailable for approval. Closing makes no new policy decision, uses the same host-person authority, and leaves any failed policy work for host review.

The proxy identifies a sandbox, not an agent: its refusals never acquire an invented agent or conversation. Hermes reports concrete file tool refusals and offers `enclos_request_access` for other actions, including a shell's refused filesystem operation. Arbitrary shell syntax is not parsed for grants. This does not observe every OS refusal, and cannot approve a new kind of capability the engine does not support.

Reason: an exact grant in a persistent policy is understandable and reusable, while accepting a command string on the host would turn agent text into authority. Keeping existing policy validation and restart rules avoids a second enforcement path. An additional per-device admin enrollment could narrow authority further, but this request uses the host person's already paired devices; the future general admin surface is separate (#166).
