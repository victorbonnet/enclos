# enclos 0.3.0

enclos now runs on Linux, with bubblewrap. This release also changes how `agent add` and `agent rm` treat a started sandbox, and upgrading needs one `enclos init`.

```bash
curl -fsSL https://enclos.dev/install.sh | bash
```

## Linux

enclos runs on Ubuntu 24.04 and 26.04, Debian 13 and 64-bit Raspberry Pi OS. The release has static (musl) archives for x86_64 and arm64, so they run whatever glibc the host has, and the installer picks the one for your host.

A Linux host needs systemd 254 or later, bubblewrap 0.9.0 or later, and user namespaces; on Ubuntu 24.04, AppArmor also needs a rule for bubblewrap. [Linux requirements](https://github.com/victorbonnet/enclos/blob/main/docs/getting-started.md#linux-requirements) says how to set each up. Create a sandbox with `--backend bubblewrap`.

Each sandbox has a network namespace of its own, and its services run as systemd user units. Your host cannot reach what a sandbox serves, so `enclos dashboard <sandbox>` opens its runtime's dashboard to you alone until Ctrl-C. A secret goes to the Secret Service, or to a `0600` file where none answers.

Where the host lacks a control, the sandbox still runs without it, and `enclos doctor` says what is not enforced, the risk and the fix:

- **No Landlock** on Raspberry Pi OS's kernel: writes are held by bubblewrap's mounts alone, and any program the sandbox can read can run.
- **No memory controller**, as Raspberry Pi OS's firmware leaves it: a `memory` limit runs not applied, and only once you accept it with `--accept-unenforced memory`. `doctor`, `sandbox start` and `policy test` name each field a sandbox runs with not enforced, and whether it is accepted ([ADR 0038](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0038-a-memory-limit-the-host-cannot-hold-runs-unapplied-once-accepted.md), #197).
- **`listen = false`** is declared, not held, on bubblewrap, on every host: a listener in one session is reached by the sandbox's other sessions, never by your host's network. Each session's start says so ([ADR 0041](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0041-listen-false-on-bubblewrap-runs-declared-and-said-at-each-start.md), [ADR 0057](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0057-landlocks-tcp-bind-right-is-not-built.md)).

For the same reason, `status` looks for no listener in a bubblewrap sandbox: `--json` gives its listeners as `not_provided` (#203).

## Changes on every system

- **`agent add` restarts the runtime's services.** Hermes's gateway serves only the agents that existed when it started. On a started sandbox, `agent add`, with or without `--from`, now restarts its services once the agent exists, which ends a chat in progress. So it asks first: without `--yes` it exits 3 (#243).
- **`agent rm` does the same** around the runtime's delete, and finishes a delete that Hermes 0.23 leaves half done (#204).
- **An agent with no provider chosen** is said so by `agent add` and `status`, with the command that chooses one: `enclos connect <sandbox> -- hermes -p <agent> model`. The login is shared; each agent's provider and model are its own (#204).
- **`agent rm --keep-data`** says what it left: the agent, only its folder, or nothing (#204).
- **`--json`:** `status` gains `provider` and `choose_provider` for each agent, and `agent add` gains `choose_provider` (#204); `agent rm` gains `files_left` (#204); `doctor`, `sandbox start` and `policy test` list each field the host does not enforce, a list always empty on macOS (#197).
- **The state database on a slow disk.** On a busy SD card, commands, sessions and the proxy failed with `database is locked`, and the proxy refused connections as `policy-unreadable`. `state.db` now runs in WAL mode, and writes take turns and wait longer where no person waits on them (#175, #199, #205, #240, #241, #242).
- **On macOS, `curl` in a sandbox** can check a site's certificate against the system's roots when its own bundle has no root for it, where it failed with `unable to get local issuer certificate` (#153).
- **A process enclos starts** holds none of its caller's descriptors, so a sandbox's proxy no longer keeps a `flock` lock of the command that started it (#187).
- **`policy edit`** no longer suggests a rollback when it refuses a `read_deny` that drops a built-in entry; it says to add yours with `read_deny_add` (#237).

## Upgrading

Your sandboxes, agents, policies and audit log carry over: since 0.2.0 the state database has only gained tables and columns. After running the install command:

1. Run `enclos init` once, which upgrades the database. Until then, every command that reads the state stops and says to run it.
2. Run `enclos sandbox restart <name>` for each started sandbox. Its proxy and gateway still run 0.2.0, which cannot read the upgraded database, so its proxy refuses every connection until then.
3. If you script `agent add` on a started sandbox, pass `--yes`.

The built-in defaults now hide more of your files from every sandbox, such as Signal's, Slack's, Discord's and Telegram's data on macOS, and Hermes's adapter adds one installer host. A sandbox keeps its policy as stored: `enclos policy refresh <sandbox>` lists the changes and asks before taking them, and the next `policy allow` lists them too.

`state.db-wal` and `state.db-shm` now stay beside `state.db`. They are part of it: a backup copies all three.

Going back to 0.2.0 is not supported once 0.3.0 has run: 0.2.0 refuses every command, `enclos init` included, with `state.db uses schema 12, written by a newer enclos (this one knows 9). Upgrade enclos`.

## Tested on

- **Raspberry Pi 5, 64-bit Raspberry Pi OS (Debian 13, kernel 6.18):** milestone 3's acceptance run, with Hermes 0.23. This release fixes what it found. The last fixes, #242 and #243, are shown by tests with stand-ins, not yet on the Pi.
- **Ubuntu 24.04 (x86_64 and arm64) and 26.04:** the test suite and the bubblewrap, confinement, cgroup, systemd and libsecret tests, in CI on GitHub's runners on every change. The release workflow also runs each Linux archive on Ubuntu 26.04 and in a Debian 13 container. x86_64 has run on these runners only, not on a host of its own.
- **macOS 15 and 26:** the test suite, in CI on this commit.
- **The upgrade:** an empty 0.2.0 state database upgraded by `enclos init`, then refused by 0.2.0, on macOS 27.2.

The [manual test](https://github.com/victorbonnet/enclos/blob/main/docs/manual-e2e.md) was not repeated on a Mac for this release, by the maintainer's decision. It last ran there for 0.1.0, and CI has no macOS 27 runner yet.

## Known gaps

- **`status` can take a long time** on a slow, busy disk, such as a Raspberry Pi's SD card under load: it measures each sandbox's folder, and a Hermes home holds about 2.5 GB.
- **Right after a gateway restart,** as `agent add`, `agent rm` or `sandbox restart` make, a first chat may fail until Hermes is ready. Try again after a moment.
- The [known gaps of 0.1.0](https://github.com/victorbonnet/enclos/blob/main/docs/release-notes/0.1.0.md#known-gaps) still apply on macOS, but for "Apple silicon Macs only".

## Checking this release

```bash
gh attestation verify enclos-aarch64-apple-darwin.tar.gz --repo victorbonnet/enclos
gh attestation verify enclos-x86_64-unknown-linux-musl.tar.gz --repo victorbonnet/enclos
gh attestation verify enclos-aarch64-unknown-linux-musl.tar.gz --repo victorbonnet/enclos
```

The installer checks the archive's SHA-256 and the binary's version. The attestation says which workflow run, commit and repository built the archive.
