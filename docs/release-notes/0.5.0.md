# enclos 0.5.0

This release is the first with the bridge for the enclos mobile app: from an Android phone on your tailnet, you talk to the agents in your sandboxes, answer their questions and runtime approvals, and review their policy requests. It also adds the enclos plugin, so Claude Code or Codex can set enclos up and run it for you, and the export and import of an agent's complete data. It fixes the findings of a security review of the bridge before its first release (Security, below). Upgrading needs no `enclos init`, but scripts that read `--json` must accept schema 2, and running sandboxes should be restarted.

```bash
curl -fsSL https://enclos.dev/install.sh | bash
```

## The mobile app and its bridge

This is milestone 4's work, and it is still in development. Every ADR behind it, from [ADR 0042](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0042-a-bridge-on-each-host-serves-the-mobile-app.md) on, is proposed, not accepted. Milestone 4's acceptance scenario has not run, and design §14 lists what is not shown yet (Known gaps, below).

**The bridge** is the part of enclos the app reaches. It listens on the host's loopback, port 47100 by default, and Tailscale is its one transport: `tailscale serve` puts it on your tailnet and tells it the caller's tailnet login. It runs in the foreground, in your terminal, until Ctrl-C. It is not a service yet: nothing starts it at login or keeps it running. It reaches each agent through a Unix socket in the sandbox home, which the runtime's channel plugin listens on, so no sandbox gets a new way out ([design §4](https://github.com/victorbonnet/enclos/blob/main/docs/design.md#4-architecture)).

**`enclos app`** has these commands (#155, #157, #162, #164):

- `app serve [--port 47100]`: run the bridge. It prints the `tailscale serve --bg 47100` that puts it on your tailnet, and the agents it serves.
- `app pair [--url ...]`: print a QR code, an `enclos://` link and an https link to open on the phone. A code works once, for 5 minutes, while `app serve` runs. The terminal then names the device, its tailnet login and node, and asks you to accept it. Pairing is an audit entry.
- `app devices` (or `app status`): who can reach the agents, from which device, and when each was last seen.
- `app unpair <device>`, audited. The app can also forget a host, which unpairs that device.
- `app host [<person>]`: show the host's person, the person of the first device paired, or hand the role to another person with a paired device.
- `app log [-n 50]`: the bridge's own log of connections, disconnections, refusals and phone requests.
- `app chat <sandbox>/<agent>`: talk to an agent through its app channel from the terminal, to check the channel without a phone.

**The app channel.** Only Hermes has one. To give an agent one, store a random token for it, grant it to that agent alone, then configure the channel:

```bash
openssl rand -hex 32 | enclos secret set lab/main-app
enclos policy edit lab      # [secrets.agents.main]  env = { MOBILE_APP_TOKEN = "secret:lab/main-app" }
enclos runtime configure lab/main --channel app
```

`runtime configure` writes the Hermes channel plugin, which the enclos binary carries, into the agent's own Hermes home, turns it on, and sets its socket, its Home conversation, the bridge's public key for runtime approvals, and an hour for Hermes's `clarify` to wait for an answer (#151, #154). Its services restart with it. The bridge reads which agents have a channel when it starts, so restart `enclos app serve` after setting one up.

**What a person does from the phone.** Every paired device's person may read and talk to every agent the bridge serves. The host's person alone also decides runtime approvals and policy requests, manages policy, routines, photos and display names, creates sandboxes and reads the audit log.

- **Conversations, Home and groups.** Start conversations with an agent, named by the runtime or by you, with how far each was read kept across your devices (#159, #163). Each agent has a Home conversation for its scheduled output and the runtime's own notices, owned by the host's person ([ADR 0044](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0044-each-agent-has-a-home-conversation.md), #173). Any agent may send on its own (#190). A group is one conversation with two to six agents of one sandbox, addressed by `@handle` or `@all`, whose turns the bridge runs, bounded at 3 rounds or 10 agent messages ([ADR 0045](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0045-group-conversations-are-the-bridges-among-one-sandboxs-agents.md), #206).
- **Files, artefacts, tool steps and agent commands.** An agent sends images and documents, up to 10 files of 25 MiB each in a message (#161). A self-contained HTML file opens as an artefact, in an offline viewer meant to run no scripts and load nothing from the network ([ADR 0048](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0048-artefacts-are-static-html-attachments.md), #210). The agent's tool steps show live while it works (#160), and typing `/` offers the runtime's agent commands, passed on as messages (#184). Messages are markdown, drawn by the app (#158).
- **Questions and runtime approvals.** A question from Hermes's `clarify` shows its choices, a free answer and Skip, and the answer goes to that exact question ([ADR 0052](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0052-questions-keep-their-runtime-waiter-and-structured-app-controls.md), #216). A runtime approval shows the whole command, its reason and only the consents the runtime offers; the bridge signs each decision with a key no sandbox is given, and the channel acts on no other. Typed `/approve`, `/deny`, `/yolo` and `/approvals` are refused from everyone ([ADR 0053](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0053-runtime-approvals-use-exact-native-requests-and-explicit-scopes.md), [ADR 0060](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0060-the-bridge-signs-runtime-approval-decisions.md), #217). The buttons need a Hermes with its exact approval API; with an older one, an approval comes as text that nothing in the app decides. A runtime approval changes no sandbox policy.
- **Policy requests and policy management.** A proxy refusal, or a request from the agent's plugin, becomes a policy request for one destination, private address or writable path. The host's person sees the exact entry approval would write, and whether it restarts the sandbox, then approves or denies it ([ADR 0046](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md), #208). A request the agent writes is narrower than `policy edit`: a writable path must be in your home or on an external volume, and not a hidden folder, `~/Library` or a folder on the host's `PATH`. The sandbox page shows the active policy and edits one field at a time, with the host's preview, rechecked under the state lock ([ADR 0047](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0047-the-hosts-person-manages-sandbox-policy-from-the-phone.md), #209). Both are audited. Refusals made by `policy test` are kept out of the requests ([ADR 0059](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0059-diagnostic-provenance-lives-in-a-side-database.md)).
- **Routines, agent photos and display names.** Edit, pause, resume, run and delete a Hermes agent's routines, which stay the runtime's to keep and run ([ADR 0050](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0050-routines-stay-with-the-runtime.md), #213). Give an agent a photo, re-encoded on the host (#211), and a display name, the same on every phone (#214, [ADR 0051](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0051-agent-display-names-belong-to-the-bridge.md)).
- **Archive and delete.** Archive a conversation and restore it later, its history kept; Home cannot be archived ([ADR 0049](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0049-conversation-archives-belong-to-the-bridge.md), #212, #215). Delete a direct or group conversation for good: the runtime removes its own copy first, then the bridge removes its history and files ([ADR 0062](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0062-conversation-deletion-retires-native-chats-before-bridge-history.md), #254).
- **Audit pages.** Read the host's audit log, newest first, 25 entries a page. This does not verify the hash chain: `enclos audit verify` does (#256).
- **Creating sandboxes and installing runtimes.** Create a sandbox from `minimal` or `assistant`, with the backend `sandbox create` takes by default, and install Hermes in it ([ADR 0064](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0064-the-hosts-person-can-provision-sandboxes-from-a-paired-phone.md), #255, #267). An install stops after an hour and is undone (#271). The runtime's login, the app channel and starting the sandbox stay on the host.

**The protocol** between the app, the bridge and the plugin is enclos's own, [`docs/protocol.md`](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md), version 1 (`v: 1`), in the `enclos-protocol` crate the bridge and the app share. Version 1 is released with 0.5.0: from now on, a change an older app or plugin would misread raises it, and a bridge speaks the version before it for at least one release. The decisions behind it are still proposed. A newer feature is an optional message or capability, so an older app or bridge goes on working without it.

**The app** is a separate repository, [victorbonnet/enclos-app](https://github.com/victorbonnet/enclos-app), Android only. It has no release: only debug builds exist, built from source with `just android`, or taken from the `enclos-debug-apk` build each pull request's CI uploads. Debug builds are debuggable, so with USB debugging on, `adb shell run-as` reads the app's private storage. Its README says nothing in it is a security guarantee yet.

## The enclos plugin for Claude Code and Codex

The enclos plugin teaches a host assistant what enclos is and every command it has, so it can set enclos up and run it for you through the CLI, as you would. It adds no MCP server and no permission of its own (#167, #168).

- **The `enclos` skill** loads when you ask about enclos or for something it does. It drives the CLI one command at a time, treats what comes from inside a sandbox as data, never sees a secret's value and leaves logins to you (#170, #172).
- **`/enclos:setup`** (`$setup` in Codex) takes the host from nothing to a running agent, step by step, and picks up where the host already is. It runs only when you ask (#171).
- **Generated references.** The command reference is generated from the CLI and the policy reference from [policy compilation](https://github.com/victorbonnet/enclos/blob/main/docs/policy-compilation.md); a test fails when either is stale. The command reference names its enclos version, and the assistant reads `enclos <command> --help` when yours differs (#169).
- **The marketplace** is this repository, named `enclos`. The plugin's version is enclos's.

```text
/plugin install enclos --marketplace victorbonnet/enclos                           # Claude Code 2.1.275 or later
codex plugin marketplace add victorbonnet/enclos && codex plugin add enclos@enclos   # Codex
```

Neither assistant lets a plugin bring an allow rule, so it asks before each `enclos` command until you add one. A rule for `enclos *` allows every command, `policy allow` and `sandbox rm` included: [the plugin's README](https://github.com/victorbonnet/enclos/blob/main/plugins/enclos/README.md) says how to allow only reads.

## Export and import an agent

`enclos agent export <sandbox>/<agent> --to <file>` writes an agent's complete data to one file, and `enclos agent import <sandbox>/<agent> --from <file>` restores it, on another host or in another sandbox of the same one ([guide](https://github.com/victorbonnet/enclos/blob/main/docs/agent-export.md), #253).

- **Included:** the runtime's data for the agent (for Hermes, its files, memories, skills, plugins, the runtime's own sessions and databases, and the runtime-held logins), the secrets granted to that agent, its display name and photo, and its direct app conversations with their files. Questions and runtime approvals come back as history only, never as decisions still to take.
- **Not included:** device pairings, the bridge's keys, group conversations, other agents, files outside the sandbox home, and the runtime's installation.
- **The file holds secrets in plain text.** It is written `0600`, and only once complete; keep it private.
- **Import** needs the same runtime installed and an agent name not in use. It stores the secrets under new names granted to the imported agent alone, keeps the destination's policy, gives the agent a new app channel token, and gives its conversations to the destination's host's person, so that host must be paired first. `--dry-run` checks the file and the destination; `--metadata-only` restores only the name and photo.

An export pauses the source sandbox's runtime services while it copies, then starts them again. Neither command removes the source: stop it before the copy runs its bots or routines. This is proposed in [ADR 0061](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0061-agent-exports-include-enclos-presentation.md), which also proposes this exception to secrets staying in the secret store. `agent add --from` still imports a runtime's own export.

## Other changes and fixes

- **Hermes's dashboard on macOS.** The address `enclos status` gave loaded a page whose calls Hermes refused, and the page kept reloading. `enclos dashboard <sandbox>` now opens it on macOS as on Linux, to you alone until Ctrl-C. It needs the sandbox running and its gateway listening, and the dashboard can bind no TCP port. The URL it prints holds a random path: treat it as a password. `status` names the command and no longer prints an address. Proposed in [ADR 0063](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0063-a-dashboard-on-macos-uses-a-private-inherited-socket.md), which supersedes the macOS parts of ADRs 0028 and 0040; checked with Hermes 0.23.1 (#257).
- **`sandbox stop` while a start runs.** A `sandbox start`, `sandbox restart` or a policy change that restarts the sandbox, run while `sandbox stop` removed the services, left the sandbox recorded stopped with its services running. The stop now fails, leaves the sandbox running, and says to run it again (#270).
- **A new sandbox's port.** A port is taken for free only when two connections 5 ms apart are refused, so a new sandbox is no longer given the port of a listener that reopens between clients, where its proxy could not listen (#251).
- **The bridge**, fixed before its first release (#261 to #273): a message it cannot use is answered and the connection goes on; a policy or sandbox list too large for one message is answered with the host command to use; a database error no longer drops or misplaces an agent's message, which the plugin sends again within seconds; a message is stored together with its files; a device gets its messages in order, after its sync; a group member's further messages for its turn are kept; conversations of a removed sandbox can be deleted; and the phone creates a sandbox with the same default backend as the CLI.
- **Releases.** The release workflow now builds only a commit on which the `ci` workflow passed on `main` (#262).

## Upgrading

Run the install command above. Your sandboxes, agents, policies and audit log carry over: the state database has not changed since 0.3.0, so no `enclos init` is needed. `enclos init`'s folders and files are the same as in 0.4.0.

**Scripts that read `--json`.** Every JSON document now says `"schema_version": 2`. `status --json` no longer has a sandbox's `dashboard` address; read `dashboard_command`, which macOS now gives too. It is `null` until the runtime is installed, and on macOS until the sandbox runs and its gateway listens. A script that requires schema 1 must accept 2 first (#257).

**Policy snapshots are unchanged**, as are their hashes: the templates, Hermes's policy layer and the policy model did not change. The policy file gains `write_remove`, `read_deny_remove`, `allow_remove` and `private_remove`, which take inherited entries out of a list; the phone's policy page writes them. On macOS, the compiled file gains the protected dashboard's rules and hides the bridge's files, so `enclos doctor` may say a sandbox's policy compiles differently from the file its sessions ran under, until they start again.

**Restart started sandboxes:** `enclos sandbox restart <name>`. They keep running, but their proxies run 0.4.0's code until then, so the refusals `policy test` causes are not marked as diagnostic, and a paired phone may be offered them as policy requests. On macOS, a restart is also what hides the bridge's files from them (Security, below).

**New files in enclos's data folder** (`~/.enclos` on macOS, `~/.local/share/enclos` on Linux, or `ENCLOS_HOME`), each made when first needed:

- `app.db`, the bridge's own database: devices, conversations, messages, groups, questions and policy requests; and `app-media/`, the files agents sent.
- `app-bridge.key`, the bridge's key, which paired devices pin, and `app-approvals.key`, which signs runtime-approval decisions.
- `probe-sources.db`, beside `state.db`, which marks the refusals `policy test` caused (ADR 0059).

A backup of the data folder should include them. Unpairing every device does not remove `app.db`.

**The audit log** names whoever the bridge acted for: an entry the bridge causes, such as a pairing, a policy decision or an install from the phone, has `<person> (device <id>)` as its user, on the host's name, and a policy request's decision adds `, request <id>` (#267). The audit file's format is unchanged.

**Going back to 0.4.0** keeps your state database, which 0.4.0 still reads, but 0.4.0 refuses a `policy.toml` that uses a `_remove` list.

## Security

This release fixes the bridge and macOS findings of [GHSA-q84r-9cqv-hh52](https://github.com/victorbonnet/enclos/security/advisories/GHSA-q84r-9cqv-hh52) (severity: moderate). No released version was affected: the bridge is new in 0.5.0, and the files involved exist only on hosts that ran a development build of it.

- **Files agents send to the phone are hidden from other sandboxes on macOS.** `~/.enclos/app-media/` and `~/.enclos/probe-sources.db` were readable from any Seatbelt sandbox. Both are now on the list the Seatbelt profile denies, and `policy test` probes each of them. Linux already hid the whole data folder. A process keeps the profile it started with, so restart running macOS sandboxes after upgrading: `enclos sandbox restart <name>`.
- **An agent can no longer break a phone's sync.** An agent's file could carry a media type or name too large for one device message, and every later sync stopped at it. The bridge now keeps a media type to 255 bytes, a name to 120 characters, and a title within bounds, on the live path, at export and at import. A message whose details leave no room for its text is refused, and the plugin is told. A stored message still too large for a device is passed over and logged (`enclos app log`, `skipped`), so the sync goes on. The first time the 0.5.0 bridge opens `app.db`, it rewrites the attachment rows an earlier build stored to these rules, once (recorded as `attachment_details_kept` in its `settings` table).
- **A connection must send its first message within 30 seconds**, however slowly its bytes arrive. Before, a frame sent a byte at a time could hold one of the bridge's sixteen connection slots for days. A device that stops reading is let go after 30 seconds without progress, and the person's other devices are not held up by it.
- **Replies stay with their owner.** `conversation.new` with an id in use by another person sends nothing of that conversation, and a plugin's `ack` clears only its own agent's messages.
- **Pairing links name the host plainly.** A link's host is 1 to 63 letters, digits, `-` or `_`. Before, a name with `/` or `:` could make the app file a second host's conversations under the first's agents. `enclos app pair` derives the name from the host's address.
- **Non-TLS tunnels are documented.** [Design §6](https://github.com/victorbonnet/enclos/blob/main/docs/design.md) states what a CONNECT tunnel to an allowlisted plain-HTTP port carries, and what the proxy then does not see.

Not fixed in this release, and listed in the advisory:
- A second tailnet login accepted at `enclos app pair` can reach every agent. Sharing (ADR 0043) is not built, so pair only your own devices.
- Pairing shows no comparison code on the phone and in the terminal.
- The app-side items (host names in the app, the lock timer, Markdown nesting) are fixed in the enclos-app repository, not in enclos.

## Tested on

- **macOS 15 and 26:** the test suite, in CI on this commit.
- **Ubuntu 24.04 (x86_64 and arm64) and 26.04:** the test suite and the bubblewrap, confinement, cgroup, systemd, libsecret and musl tests, in CI on this commit. The release workflow also runs each Linux archive in a Debian 13 container, and the x86_64 one on Ubuntu 26.04.
- **The Hermes channel plugin:** its tests in CI on every change, and again against Hermes's default branch, where a skipped test now fails the job (#259). They use Hermes's source and stand-ins, not a running gateway and a phone.
- **The bridge:** unit and connection tests with stand-in plugins and devices. A real Hermes gateway made its socket in the sandbox home under Seatbelt and the bridge reached it, on a Mac; on Linux this is not tried yet.

The [manual test](https://github.com/victorbonnet/enclos/blob/main/docs/manual-e2e.md) was not repeated for this release, on a Mac or on Linux.

## Known gaps

- **The bridge runs only while `enclos app serve` runs.** It is not a service, and nothing starts it at login. A new agent's app channel needs a restart of it.
- **No push notifications.** A phone gets messages only while the app is connected; what came meanwhile arrives at its next sync.
- **Android only, debug builds only.** No iOS app, and no release build of the Android app.
- **No sharing.** Sharing an agent with another person ([ADR 0043](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0043-sharing-an-agent-is-not-hosting-it.md)) is not built: every paired device's person reads and talks to every agent the bridge serves. Pair only your own devices.
- **One transport.** Tailscale is the only one. That the bridge reads the caller from `tailscale serve`'s headers is shown with a stand-in for `tailscale whois`, not yet through `tailscale serve` itself.
- **Linux.** That a Hermes gateway can make its app channel socket under Landlock, and the bridge reach it across the sandbox's network namespace, is not shown.
- **Not shown with a real gateway and phone:** questions, runtime approvals and their signed decisions, routines, display names, archives, deletion, and the Hermes plugin's policy requests. Tests show each with stand-ins; design §14 lists what remains. The artefact viewer's restrictions are shown only by a first probe on an Android emulator.
- **From the phone**, you cannot send an agent a file, install a runtime other than Hermes, use the `autonomous` template, log a runtime in, set up an app channel, or start, stop or remove a sandbox.
- **`enclos dashboard` on macOS:** talking to the agent in the dashboard from start to end, and the dashboard's terminal, are not shown.
- **`/enclos:setup`** has not run end to end in a test: the [manual test](https://github.com/victorbonnet/enclos/blob/main/docs/manual-e2e.md) covers it, and has no section for the bridge and the app yet.
- The [known gaps of 0.4.0](https://github.com/victorbonnet/enclos/blob/main/docs/release-notes/0.4.0.md#known-gaps) all still apply.

## Checking this release

```bash
gh attestation verify enclos-aarch64-apple-darwin.tar.gz --repo victorbonnet/enclos
gh attestation verify enclos-x86_64-unknown-linux-musl.tar.gz --repo victorbonnet/enclos
gh attestation verify enclos-aarch64-unknown-linux-musl.tar.gz --repo victorbonnet/enclos
```

The installer checks the archive's SHA-256 and the binary's version. The attestation says which workflow run, commit and repository built the archive, and the release workflow built only a commit CI passed on.
