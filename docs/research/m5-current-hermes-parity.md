# M5 parity against current main

Research date: 2026-11-16. This compares enclos main `6683752078753b3cefcb1416cbe178b8a6bcd7dc`, the published M5 tip `6e9b5622c33a98eab345feb384df131c314df074`, and enclos-app main `f9478492bd23761a432e1cde17b32c85518f8fce`. Sources were read from these immutable Git objects while integration was in progress. The SDK findings below select OpenClaw 2026.11.2, commit `b556fdf457b026574bf0f1e7b4914b15f3f179ce`; searches of upstream main were used only to locate files, then the release files were read. No installation, model call, phone interaction, native deletion or Linux acceptance was performed for this research.

## Recommendation

First integrate current main into M5 and preserve its newer bridge/protocol/Hermes behavior. Then add OpenClaw **answering activity** through the existing channel dispatch lifecycle as one small PR. This fills a visible gap without inventing a native task board or conflating model attempts with API calls. Usage is a worthwhile subsequent PR, but its exact accounting contract needs the additional work below. The original [M5 scope and acceptance record](https://github.com/victorbonnet/enclos/blob/6e9b5622c33a98eab345feb384df131c314df074/docs/m5-openclaw.md) remains the baseline, including accepted question/routine limits.

## Next small implementation: answering activity

The existing [M5 channel](https://github.com/victorbonnet/enclos/blob/6e9b5622c33a98eab345feb384df131c314df074/channels/openclaw/channel.js) already authenticates ingress, resolves exact account/person/conversation routing, awaits `channel.inbound.dispatch`, and finalizes its native ingress in `finally`. The release's [public SDK](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/src/plugin-sdk/channel-inbound.ts) maps this to `dispatchRoutedChannelTurn`. Its [lifecycle owner](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/src/channels/turn/lifecycle.ts) awaits dispatch and delivery settlement; [execution](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/src/channels/turn/execution.ts) retains admission and authority checks. No new Gateway credential is needed to observe this already-owned operation.

Proposed implementation: retain a per-account map of active ingress ids to conversations, begin after successful native admission immediately before dispatch, end in `finally`, deduplicate conversations when publishing at most 16 `answering` entries, and send the current snapshot after each hello. Publish only to a bridge that negotiated `activity`; current empty state has `doing=[]`, `since=0`. Keep it transient rather than replaying stale busy frames from the durable outbox. Clear/revoke on account stop. Overlapping ingresses in the same conversation must not let the first completion clear the second. Activity reports only dispatches owned by this enclos channel; it does not establish a native task board, cron activity, CLI activity, or successful model execution. Native dispatch may defer work into an existing run, so this bounded view must not be described as a complete Gateway run inventory.

Meaningful verification: negotiated and older bridge; two concurrent conversations; overlap in one conversation; failed ingress/dispatch; exact cancellation; disconnect/reconnect while busy and after completion; stopped/replaced account; bounded snapshots. Reuse the existing generic [activity wire/authority rules](https://github.com/victorbonnet/enclos/blob/6683752078753b3cefcb1416cbe178b8a6bcd7dc/crates/enclos-protocol/src/task.rs). Hermes currently combines answering and board-task activity; its reporter does not establish a routine-activity feed either.

The release's native [session deletion reference](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/docs/cli/sessions.md) also says ordinary deleted transcripts become verified `.jsonl.deleted.<timestamp>` archives (incognito transcripts are removed). A follow-up must reconcile that retention with enclos's permanent-delete promise; merely calling a function named delete is insufficient evidence that all native transcript data was erased.

## Usage requires exact accounting first

The release's [`PluginHookLlmOutputEvent`](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/src/plugins/hook-types.ts) exposes model/provider, run/session ids and optional input/output/cache usage. Its public usage type does not include reasoning. [`PluginHookAgentContext`](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/src/plugins/hook-agent-context.types.ts) supplies optional agent/session/channel/account identity. However, the embedded runner emits `llm_output` using **`state.attemptUsage`**, an attempt aggregate, in [`attempt-result.ts`](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/src/agents/embedded-agent-runner/run/attempt-result.ts). A single hook observation cannot honestly become one API call merely because enclos's omitted `calls` defaults to 1. `model_call_ended` provides a call id/outcome/duration but no token usage. A later reporter must prove correlation and coverage across attempts, tools, retries, failed runs and alternative harnesses, or explicitly evolve the contract to represent its narrower measurements.

Native [normalized usage](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/src/agents/usage.ts) separates uncached input from cache reads/writes, matching enclos's meaning. Preserve unknown fields; do not fill reasoning or cost with zero, treat total/context-window snapshots as cumulative consumption, or derive counts from tool/typing events. Outside-app attribution requires an exact current agent and a proven non-app origin; unmatched app hooks must not be relabelled outside-app usage. CLI historical reporting and live bridge counters are different data sources/windows and should be separate reviewable outcomes. The [native usage reference](https://github.com/openclaw/openclaw/blob/b556fdf457b026574bf0f1e7b4914b15f3f179ce/docs/concepts/usage-tracking.md) distinguishes provider quota, recorded session cost and per-response usage; none can silently substitute for another.

## Integration findings and limits

The integration keeps per-connection native-scope opt-in in the encrypted connection, and updates broadcast routing and negotiated support under one route lock. A same-device reconnect cannot lend its opt-in to the old connection or have old cleanup erase the new one.

OpenClaw's implicit `main` is no evidence of stored data when `.openclaw` does not exist. Its pinned native delete cleans separate agent, session, workspace and database paths, and can leave their parent folder present. A single `AgentFacts.folder` cannot prove complete deletion. Until native deletion receipts and custom paths have a complete absence contract, the bridge conservatively retains OpenClaw history while `.openclaw` exists, even when the roster omits the agent. Removing the whole sandbox without `--keep-data` remains generic proof of absence. This is an explicit gap in removed-agent Forget and conversation deletion, not complete parity. Native agent removal retains the existing M5 behavior; it is not converted into parent-directory deletion.
