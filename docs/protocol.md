# The mobile app protocol

Status: **proposed, version 1 draft**, with [ADR 0042](adr/0042-a-bridge-on-each-host-serves-the-mobile-app.md) and [ADR 0043](adr/0043-sharing-an-agent-is-not-hosting-it.md). This is the evolving contract of the mobile PR stack; each feature records its verification separately. Its words are the glossary's: host, sandbox, agent, runtime, bridge, paired device, person, share, conversation.

The protocol has two legs, one message format:

```
paired device ──WebSocket over the tailnet, Noise inside──► bridge ──Unix socket in the sandbox home──► channel plugin ──► runtime
```

- **The device leg**: the enclos app and the host's bridge. The bridge listens on the host's loopback, reached through `tailscale serve`. Every frame after the handshake is a Noise transport message.
- **The plugin leg**: the bridge and one agent's channel plugin, inside the sandbox. A Unix socket the plugin listens on in the sandbox home, one per agent; JSON lines, no encryption (it never leaves the host).

It describes conversations, people and capabilities, never one runtime's words: a runtime's own features (Hermes's kanban, OpenClaw's nodes) stay out, or come as an optional capability.

## Messages

Every message is one JSON object: UTF-8, at most 1 MiB, with these fields first. On the plugin leg a receiver reads a line of up to 1 MiB; a longer one it answers with an `error` (`bad_message`, `of` its `id` when its first bytes hold one), so the sender knows at once that it did not arrive, and then ends the connection (below).

| Field | Type | Meaning |
| --- | --- | --- |
| `v` | integer | The protocol version, `1` |
| `type` | string | What the message is (below) |
| `id` | string | Unique per sender, a UUID; used to acknowledge and to drop duplicates |

Unknown fields are ignored. An unknown `type` is answered with an `error` of code `unknown_type` and otherwise ignored, so a newer peer can send optional messages to an older one. A message the receiver cannot use (not JSON, too big, a field missing or wrong) is answered with an `error` of code `bad_message`, its `of` naming the message's `id` when one could be read, and the receiver goes on reading: one bad message never ends the connection. Two things do: a `v` the receiver does not speak, answered with `version` ([Errors](#errors)), and, on the plugin leg, a line over 1 MiB, answered with `bad_message` (its `of` when the line's first bytes hold its id, as above), so a sender checks the size of each message before it sends it. On the device leg a frame that does not decrypt ends the connection too (below).

On the plugin leg, one message per line (`\n`, never inside a message). On the device leg, one message per WebSocket binary frame, inside a Noise transport message.

A Noise transport message holds at most 65,535 bytes, its 16-byte tag included, and this protocol defines no fragmentation. So **on the device leg a message is at most 65,519 bytes**, as it is sealed: its JSON and the line break after it. The 1 MiB limit holds on the plugin leg only.

- **An agent's text that does not fit** (`message.out`, or a cron job's output) is split by the bridge, at character boundaries, into several `message`s of the same conversation, each with the next `seq` and stored as it is sent. A device sees them in order, as consecutive messages from the agent; the plugin and the runtime see one message.
- **A person's text is one message:** the app refuses, before sealing, a `message.send` whose text would not fit as a `message` (its echo, with the conversation's other fields), and keeps the person's text; `enclos-protocol`'s `split_text` giving one piece is the test. The bridge answers one that gets through with `bad_message` and stores nothing, and closes a connection whose frame does not decrypt, so a larger one ends it.

### Names

Every id and name a message carries (`id`, `of`, `conversation`, `person`, and a plugin `hello`'s `runtime` and `agent`) is not empty, at most 128 bytes, and holds no control character; an `error`'s `message` holds no control character either. A message that breaks this is a bad message. The host prints some of them, so text from the sandbox can neither move a terminal's cursor nor break a log's line.

- **An agent** is `<sandbox>/<agent>` on one host, as enclos names it. The app adds the host it reached.
- **A conversation** is a UUID the app makes. The plugin gives it to the runtime as the chat's id, so a new conversation is a new chat for the runtime, and a cron job created in it remembers it as its origin.
- **A person** is a tailnet login, as Tailscale's WhoIs gives it (`alice@example.com`). In version 1 the only person is the host's user; the field is there from the start so sharing (ADR 0043) changes no stored history.

## The plugin leg

The plugin listens; the bridge connects. Several bridges never connect at once: the plugin refuses a second connection while one is open. The plugin has 10 s to answer the bridge's `hello`, and 10 s to read what the bridge writes; past either, the bridge ends that connection and opens a new one on its next try, and other agents' plugins do not wait for it.

1. **`hello`, bridge to plugin, first:** `{"v":1,"type":"hello","id":…,"token":"…","home":"home.lab.main"}`. The token is the agent's, a secret granted to that agent ([ADR 0036](adr/0036-an-agent-has-its-own-bot.md)). The plugin compares it in constant time and closes the socket, saying nothing, on any other first message or token. `home`, optional, is the agent's [Home](#home) conversation.

   **What the token proves, and what it does not.** It keeps the host's other programs, and other sandboxes, off the agent's socket, and nothing more. The token is in the sandbox, where the agent and anything it runs can read it, as they can every secret of the agent's (ADR 0036), and the socket is in the sandbox home. So a program in the sandbox can connect to its own plugin while the bridge is not connected and send it any message the bridge sends, and a program that listens on the socket's path gets the token from the bridge. Hence the rule: **no message from the bridge to the plugin carries authority the agent must not have.** A message the plugin passes on is what a person said, never a decision the runtime then trusts more than the agent's own words; a decision that must come from the person needs its own proof, which version 1 does not define.
2. **`hello`, plugin to bridge:** `{"v":1,"type":"hello","id":…,"runtime":"hermes","agent":"main","capabilities":[…]}`. The plugin has 10 seconds in all for it, and at most 64 KiB: the bridge gives up on the connection after that, and tries again when it next needs the agent. One agent's plugin slow to answer holds up only what needs that agent.
3. Then, in either direction:

| `type` | From | Fields | Meaning |
| --- | --- | --- | --- |
| `approval.request` | plugin | `conversation`, `access`: `{kind: network|write|read, target, private: boolean}`, `action` (short description) | Request a sandbox policy scope; no authority and no host command |
| `policy.context` | bridge | `text` | The active policy described for the agent's future turns; only for plugins announcing `approval` |
| `message.in` | bridge | `conversation`, `person`, `text`, `attachments`? (reserved; version 1 defines none, and a receiver ignores it) | A person's message to the agent |
| `message.out` | plugin | `conversation`, `text`, `kind` (`reply`, `notify` or `status`), `reply_to`?, `attachments`? (`[{file, mime, name, size}]`, see [Files](#files)) | What the agent says: a reply, or `notify` for one nobody asked for now (a cron job, background work), which every runtime may send; `status` is the runtime about itself (Hermes's gateway online or shutting down), not the agent |
| `typing` | plugin | `conversation`, `on` (boolean) | The agent is working on an answer |
| `conversation.title` | plugin | `conversation`, `title` (one line, at most 100 characters) | The runtime's short name for the conversation, from what was said in it |
| `conversation.rename` | bridge | `conversation`, `title` (empty: no name) | The person named the conversation, or cleared its name |
| `tool` | plugin | `conversation`, `call` (the runtime's id of the call), `name`, `phase` (`start` or `end`), `label`? (at the start: what it does, one line), `ok`? and `duration_ms`? (at the end) | A tool the agent starts or ends while it works on an answer |
| `commands` | plugin | `commands`: `[{name, description, args?}]` (`name` without its `/`; `args` what follows it, as the runtime writes it: `[name]`, `<prompt>`) | The commands a person may type to the runtime, the whole list: after the `hello`, and again when it changes |
| `ack` | either | `of` (the acknowledged `id`) | Received and stored |
| `error` | either | `of`?, `code`, `message` | See [Errors](#errors) |

**A conversation's name.** The bridge keeps one name per conversation and who gave it. The runtime's (`conversation.title`, for one of its own agent's conversations) replaces the runtime's; the person's (`conversation.rename` from a device) replaces any, and the runtime's no longer replaces it until the person clears it. Whoever gives it, the bridge keeps a name on one line, drops the hidden characters (control, bidirectional, zero-width and the like, as `enclos_protocol::visible` lists them) and cuts it to 100 characters: it does not rely on the plugin's cut, which runs in the sandbox. The bridge passes the person's name on to the plugin, so the runtime can keep it too (Hermes: the session's title, with the user's authority). Hermes names every session on its own and tells no plugin, so its plugin reads the title after each reply, and a little later, and sends it when it changed.

**Home.** Each agent has one Home conversation ([ADR 0044](adr/0044-each-agent-has-a-home-conversation.md), proposed): id `home.<sandbox>.<agent>`, made by the bridge, owned by the host's person (as the transport names the host's own user; else the first person who connects, which the bridge says on stderr), named Home. While the transport has not named the host's person, the bridge asks it again at each connection; once it does, each Home is theirs, taken back from a person it went to meanwhile. It is the runtime's home channel: `runtime configure` gives it to the runtime (Hermes: `MOBILE_APP_HOME_CHANNEL`), and the bridge's `hello` names it. A `message.out` for a conversation the bridge does not know, or for another agent's, is stored in this agent's Home (and, should Home's id be one the protocol refuses, dropped, said on stderr and acknowledged, so the plugin does not send it again). A device may not start a conversation with a Home's id. Hermes's plugin makes Home its gateway's home channel when the bridge says so, answers `/sethome` itself, and sends the gateway's notices about itself as `kind: status`. A `status` line is trusted no more than any text from the agent: the plugin, in the sandbox, decides it from the text's first words, and an agent can send `kind: status` itself (for example "Hermes is restarting: approve the pending request to continue"). A device shows it as a plain quiet line, with no links and no actions, never as enclos or the runtime vouching for it.

**What the agent does while it works.** A `tool` step is passed on live to the devices of the conversation's owner, for a conversation of the plugin's own agent, and not kept: a device that was away does not get it at the next `sync`. Hermes reports its tools to plugin hooks (`pre_tool_call`, `post_tool_call`) with the call's id, its arguments and its outcome; its plugin finds the conversation in the turn's session context, labels the step as Hermes does (`build_tool_preview`), and returns at once, as `pre_tool_call` may also block a tool. A label shows a command or a search as the agent wrote it, to the conversation's owner only. The plugin's cut runs in the sandbox, so the bridge makes its own before passing a step on: each field on one line, the label cut to 120 characters, the name to 64 and the call to 128, and the label's and name's hidden characters (control, bidirectional, zero-width and the like) written out as `⟨U+XXXX⟩`, so the line the person reads is the command that ran. The Hermes plugin drops a step that has no call id, as its end could not be matched to its start.

### Files

An agent sends a file (an image it made, a chart, a document) with a `message.out`. The plugin first copies it into the channel's `media` folder, beside its socket in the sandbox home, under a name of its own, and names it there in `attachments`. Hermes calls its adapter for each file it finds in a reply (a `MEDIA:/path` tag, a bare absolute path); a markdown image whose source is a path to a file in the agent's Hermes home is sent as a file too, out of the text (one Hermes may not send stays in the text). A file the plugin cannot copy is named in a line added to the text, so the person knows it is missing.

The bridge runs outside the sandbox, and everything in the sandbox home is the sandbox's: it opens that folder from the sandbox home one folder at a time (`.enclos-app`, then `media`) without following a link at any of them, so a link put in place of either cannot point it at a host folder. In it, the bridge takes a file only by its plain name, opened without following a link and without waiting (a named pipe is refused, not waited on), and only a regular file with no other link to it, of at most 25 MiB; it copies no more than that even while the file grows, into its own media folder (beside its database), under an id, records it with the message, and removes the plugin's copy through the same opened folder. It takes at most 10 files from one message, and a file it cannot record leaves no copy behind. Its `name` is the last component of the plugin's, without the characters that change how text reads without showing (controls, line breaks, bidirectional and zero-width characters: the protocol crate's `visible` rule), and at most 120 characters, since it titles the artefact card, the viewer and the Share sheet. A device gets each message's `attachments` (`id`, `mime`, `name`, `size`) and fetches the bytes with `attachment.get`, over the same Noise session: never from an address, and only for its person's own conversations.

**Static HTML artefacts.** A self-contained UTF-8 HTML file is sent as an ordinary attachment, with `mime: "text/html"` ([ADR 0048](adr/0048-artefacts-are-static-html-attachments.md), proposed). In Hermes the agent writes the file, then emits `MEDIA:/absolute/path/page.html` on its own line. The media type alone makes it an artefact; the file name is not checked (Hermes derives `text/html` from a `.html` or `.htm` name). The app offers an artefact card that opens the page in a separate viewer, with Back, its name and Share. The viewer is meant to render inline CSS and data images or fonts, and to refuse scripts, network assets, relative files, forms and automatic outgoing navigation. Same-page anchors stay in the viewer. A main-frame HTTP(S) link the person taps first shows a native sheet with the destination host and full address; only after the person confirms does the website open in the preferred browser's Custom Tab on Android where supported, with the browser's normal state. Redirects, subframes, navigation without a user gesture and other schemes are meant not to reach that sheet. These are intended controls: which of them the platform probes have shown is in [design §14](design.md#14-awaiting-prototype-verification) and the app's spec. A link the person opens carries whatever the agent put in its address to that website, from the phone, outside the sandbox's network policy; the sheet is there so the person sees where it goes. The channel hint tells the agent this contract. No new message, capability or delivery path is introduced; an older app can still share the attachment. HTML in `text` keeps the markdown behavior below.

**What the agent says is markdown.** The `text` of a `message.out` is CommonMark with GitHub's tables, strikethrough and bare links; a device draws it, and fetches and runs nothing in it: an image in it shows as its alt text, a link to it, and is never loaded (a file the agent sends comes as an attachment, [Files](#files)); HTML shows as its text; and only `http`, `https` and `mailto` links open on a tap (HTTP(S) in the preferred browser's Custom Tabs on Android where supported, `mailto` in its system handler; the app's [ADR 0002](https://github.com/victorbonnet/enclos-app/blob/main/docs/adr/0002-messages-are-markdown-drawn-by-the-app.md), proposed). A plugin tells its runtime so (Hermes: the platform's `platform_hint`), so that the agent formats when it helps. What a person sends (`message.in`) is plain text, shown as typed.

**Delivery is at least once.** The plugin keeps each `message.out` on disk, in the sandbox home, until the bridge's `ack` for it, and sends what it kept again after each `hello`. The bridge drops an `id` it has already stored. The bridge acknowledges a `message.in` it sent only once it has stored it; the plugin acknowledges it once the runtime has it.

**An agent's messages are paced.** Every runtime may send on its own, so the bridge stores at most 30 of an agent's `message.out` at once and then 30 a minute (`src/bridge/pace.rs`). Past that, it reads the plugin's next message only when there is room again: the plugin waits, and loses nothing, since it keeps each message until the `ack`.

## The device leg

### Pairing

`enclos app pair` prints a QR code holding:

```
enclos://pair?v=1&host=<host name>&url=https://<host>.<tailnet>.ts.net&key=<bridge static key>&code=<one-time secret>&exp=<unix time>
```

- `key`: the bridge's static X25519 public key, base64url, which the app pins.
- `code`: 128 random bits, base64url, single use, valid until `exp` (5 minutes).

It also prints that link, and an https link to open on the phone: `https://<host>.<tailnet>.ts.net/pair#v=1&host=…` (the same parameters, after `#`). A chat or a note opens an https link, not an app's own scheme. The bridge answers `GET /pair` with one static page, the same for everyone, which reads the parameters in the browser, shows the host and the time left, and opens the `enclos://pair` link in the app on a tap. The page vouches only for its own bridge: it shows the address it was loaded from, not the link's `host`, and offers nothing when the link's `url` is another origin, so a link that names this host but another bridge does not read as this host's. A browser never sends what follows `#`: the code does not reach the bridge, its transport or a log through the page. The link itself, code included, stays wherever the person pasted it (a chat, a note) until it expires, 5 minutes after `enclos app pair` made it, and the host's terminal still has to accept the phone. Every other request is a device's WebSocket.

The app makes its **device key**, a P-256 key in the phone's hardware (Android Keystore, StrongBox where the phone has it; Secure Enclave on iOS, which holds only P-256), and its own static X25519 key, kept encrypted under a hardware key. It runs the Noise handshake below as a device the bridge does not know yet, then sends, instead of `auth`:

| `type` | From | Fields |
| --- | --- | --- |
| `auth` | device | `device`, `sig` (base64url DER signature of the handshake hash) |
| `authenticated` | bridge | `person` |
| `pair.request` | device | `name` (the device's model), `device_key` (P-256 public key, SEC1, base64url), `proof` (HMAC-SHA256 of the handshake hash, keyed with `code`), `push` (`{"kind":"fcm","token":…}`)? |
| `pair.accepted` | bridge | `device` (its id on this host), `push_key` (32 bytes, base64url) |
| `pair.refused` | bridge | `reason`: `expired`, `used`, `bad_proof`, `declined` |

The bridge checks `proof`, then shows at the terminal the device's name, its tailnet person and node (WhoIs), and asks to confirm. Only then does it store the device: both public keys, the person, the node, `push_key`, and writes an audit entry. A code works once, whatever the answer. The device chose its `name`, so the bridge keeps it plain before the terminal shows it: without the characters `enclos-protocol`'s `visible` rule calls hidden (controls, bidirectional and invisible marks), white space made single spaces, at most 64 characters. While the person decides, the device's pings count as hearing from it.

### Handshake

`Noise_IK_25519_ChaChaPoly_SHA256`, the device as initiator, the bridge's static key known from pairing; the handshake messages carry no payload. The device's first message once it is done is `auth` (or `pair.request` while pairing): its id on this host and an ECDSA P-256 signature, by the device key, DER as the phone's keystore gives it, of the **handshake hash**, which binds it to this session's ephemeral keys. The bridge then:

1. knows the device by its static key, or refuses it (unless pairing);
2. checks `sig` with the device key it stored, and answers `authenticated` with the person the device speaks for;
3. asks Tailscale who is calling, and refuses a person or a node other than the device's own;
4. writes each refusal, with its reason, in the bridge's log (`enclos app log`).

Any login of the tailnet gets as far as the first message, so the bridge keeps callers that are not authenticated yet few and short: at most 16 at once (one more is closed at once), 30 s from connecting to its first message, and no WebSocket message or frame larger than one Noise message (65,535 bytes). It logs at most 10 refusals per caller address and minute; past them, that address's connections are closed that minute without a log line or a question to Tailscale. The log keeps its newest 10,000 lines. Once authenticated, a session with nothing from the device, not even a ping, for 75 s ends: the enclos app pings every 30 s. When a device connects again while its old connection is still open, the new connection is the one messages go to.

The hardware key never signs anything but handshake hashes, the pairing handshake's included. `pair.request` itself carries no signature: it proves the one-time code (`proof`), and the device key it names is the one whose signature the same handshake already carried.

**An agent's commands** are the runtime's, which the bridge passes on without running or checking them: a command is a message like any other, sent with `message.send`. The bridge keeps the last list of each agent while it runs and gives a device each name once (lower case letters, digits, `_` and `-`, at most 32), each description on one line of at most 120 characters and `args` of at most 60, in the plugin's order until they fill 60,000 bytes, so the message fits a Noise message. Each description and `args` loses its hidden characters (controls, bidirectional marks, zero-width characters), so what is shown beside a command is what was sent. A plugin that connects again without the `commands` capability has its list dropped, and devices are sent an empty one. When a device asks for the agents, the bridge also opens the plugin connections not yet open, one pass at a time, so it learns the commands without waiting for a first message.

### Groups

A group is one conversation between a person and two to six agents of **one sandbox** ([ADR 0045](adr/0045-group-conversations-are-the-bridges-among-one-sandboxs-agents.md), proposed): a sandbox is enclos's boundary, and a group across two would carry one's conversation into the other. The bridge keeps its log, in order with every other message, and runs its turns; the device shows them and sends the person's messages (`message.send`), as in any conversation. Each member keeps its own session for the group in its runtime: the bridge gives the plugin the group's id as the conversation, apart from the member's one-to-one conversations, and never copies those into the group.

**Addressing.** A member's handle is its name in the sandbox (`main`, `coder`), matched whatever the case. `@handle` addresses that member, several mentions those members, `@all` and `@everyone` every member, and a message with none every member. In an agent's message, a mention of another member asks it for a follow-up turn.

**Turns.** One at a time per group; groups run side by side. A person's message starts a discussion: its first round is the members it addresses, in the group's order; each next round is the members an agent's message mentioned since and who have not spoken since. For each turn the bridge sends the member a `message.in` whose text gives the group's name, the member's handle and the others', the group's messages the member has not seen, oldest first (the newest 24 at most, each with its speaker: `User (<person>):` or `@handle:`, each cut at 3,000 bytes and 24,000 bytes in all, so the `message.in` fits a plugin's line), and the rules: reply once if there is something new to add, else reply exactly `(pass)`; mention a member to bring it in; never reveal what was said in a private conversation. A message's own lines are indented under its speaker: every line break in it (`\r`, U+2028, U+2029, U+0085, a form feed or a vertical tab as much as `\n`) is one, and its hidden characters are dropped, so no member writes a line that reads as the person's or as the rules. A member the person addressed by name, its handle or `@all` ("a response from all"), is told to answer or say what blocks it, not to pass, and a pass from it fails its turn; a message naming no one invites every member, who may pass. The turn ends with the member's `reply` to that message: `(pass)` is stored as no message, anything else as the member's message (and what it sent before the reply, `notify` in the meantime, as its messages too). A turn with no reply after 15 minutes fails; one fails at once when the member's plugin answers its `message.in` with an `error`, or its connection closes, and the next member's turn starts. The discussion ends **settled** when a round brings no new message, or **bounded** after 3 rounds or 10 agent messages (checked before each turn: the members still queued are then cancelled); a new message of the person's waits behind the running turn, then starts a new discussion, and the turns queued for the old one are cancelled.

**What lasts.** Messages, turns and each member's position (the last message of the group it has been given) are in the bridge's database; turns have ids made from the group, the person's message, the round and the member, so a retry does not run one twice. A turn running when the bridge stops is failed when it starts again, and the discussion ends there: `group.state` says `failed`, reason `bridge_restarted`, the members still queued do not run, and the person's next message starts a new discussion. The member's reply, if it comes yet (a plugin sends again what was not acknowledged), is kept as its message. `group.stop` cancels what is queued, and a running turn is sent `/stop` (Hermes interrupts it); its reply, if it comes, is dropped, and so is the runtime's answer to `/stop` itself. `group.state` says where the discussion is, to every device of the owner, at `sync` and whenever it changes.

**How far a conversation was read** is the bridge's too, not the runtime's: the agent does not see what the person reads in the app. A device sends `conversation.read` when the person opens the conversation or reads a message arriving in it; the bridge keeps the highest `seq`, from the conversation's owner only and never past its newest message, and sends the `conversation` again to all of the person's devices. A device that syncs, a new one or one that was away, so counts as unread only the agent's messages after `read`.

### Archived conversations

Archiving is the bridge's conversation metadata ([ADR 0049](adr/0049-conversation-archives-belong-to-the-bridge.md), proposed), independent of the runtime's own session state. A device sends `conversation.archive` with `archived: true` to set a conversation aside or `archived: false` to restore it. The boolean is required; replaying either value is idempotent. The bridge accepts only the conversation's owner and stores the value. On success it sends canonical `conversation` metadata directly to the requesting device before the `ack`, including an idempotent retry; changed state is also broadcast to all of that person's connected devices. Another person's conversation and an unknown id both receive `not_allowed`.

The `conversation` metadata has optional `archived` (`true` when archived, false when absent) and `revision` (a nonnegative integer, 0 when absent). The bridge advances the revision when the name, read position or archived state changes, and when it publishes group members or claims Home ownership. Devices persist the highest revision with the metadata and ignore a lower revision, whether it arrives in a broadcast or sync response, so delayed delivery cannot restore an older state. Earlier bridge databases gain archived=false and revision=0 for existing conversations. Every sync sends all conversation metadata, regardless of `since` and archived state, then the requested history. Older apps may ignore the field and keep listing the conversation; archive controls need an updated bridge and app. Revisions, like `seq`, assume the bridge's database is never reset or restored from an older copy: a device that kept a higher revision for an id the new database reuses (a Home's, `home.<sandbox>.<agent>`) ignores its metadata until the person clears the app's cache. The protocol has no database identity to detect that yet. A storage failure answers `unknown` with a generic message; the database's own error stays in the host's log.

This operation keeps the same id, title, read position, messages, attachments and group members. It applies to direct, group and Home conversations alike. New messages continue to be stored and delivered without clearing the flag, and archiving does not cancel a group's work. A request that waits for the person, an agent's `question` or a runtime approval of a command, is the exception: when the bridge stores one for an archived conversation, it clears the flag, advances the revision and sends the `conversation` to the owner's devices before the request, so it shows in the active Inbox. Home remains the runtime's home channel under the same id. No archive message or command reaches the plugin leg: Hermes and a future OpenClaw plugin need no archive-specific method. The runtime's saved memory, context and own archive flags are unchanged. The app filters active and archived views and restores visibility only on an explicit Unarchive.

### Notifications

When a `message` arrives for a conversation whose owner has no device connected, the bridge sends a push to each of the owner's devices through FCM: a high-priority data message whose payload is

```json
{"v":1,"host":"<host name>","seq":1234,"preview":"<base64url: nonce ‖ ciphertext>"}
```

`preview` is XChaCha20-Poly1305 under the device's `push_key`, over `{"agent":"lab/main","conversation":…,"text":"<at most 120 characters>"}`. Google sees the host's name, a number and ciphertext. The app decrypts it, shows the notification, and fetches the message with `sync` over the tailnet when it can.

## Capabilities

A plugin's `hello` and each agent of `agents.list` name what the runtime does, and the app shows only that. Sending on its own (`kind: notify`) is not a capability: every runtime may, and a device shows such a message whichever runtime sent it. Version 1 first listed it as `notify`; a plugin that still announces it is read as announcing nothing more.

| Capability | Meaning |
| --- | --- |
| `typing` | It reports working on an answer |
| `stream` | It sends a reply in parts, batched (never one message per word); version 1 defines no parts message yet |
| `attachments` | It takes and sends files; version 1 defines none yet |
| `approval` | It requests sandbox policy scopes and receives active policy context (`approval.request`, `policy.context`) |
| `abort` | It can stop an answer; reserved, no messages in version 1 |
| `titles` | It names conversations (`conversation.title`) and keeps the person's names |
| `tools` | It reports the tools it runs while it works (`tool`) |
| `commands` | It lists the commands a person may type to it (`commands`) |
| `routines` | It manages runtime-owned scheduled work through `routine.request` / `routine.response` |

Hermes and OpenClaw are meant to have `typing`; the Hermes plugin also has `titles` and `tools`, and `commands` when it can read the gateway's: Hermes's own that are not for its terminal only and those its plugins register, as its Telegram and Slack menus list them, without `/sethome` (which the plugin answers), `/start` and `/topic` (Telegram's). A runtime reached through `enclos exec` (Claude Code, Codex) has none, and the bridge sends a `message` of `kind: notify` when its turn ends.

## Errors

`{"v":1,"type":"error","id":…,"of":"<id or absent>","code":"…","message":"<for people, may be shown>"}`

| Code | Meaning |
| --- | --- |
| `unknown_type` | The receiver does not know this `type` |
| `bad_message` | Not JSON, too big, or a required field is missing |
| `version` | `v` is one the receiver does not speak; it answers this, then closes the connection |
| `not_allowed` | The person may not do this (no share, or not that ability) |
| `unknown_agent`, `unknown_conversation` | No such agent or conversation for this person |
| `agent_unavailable` | The plugin is not reachable, disconnected or timed out; conversation messages are kept and sent when it is, but live routine controls are not queued |
| `conflict` | What the request changes changed since the revision it names, or a request id was reused; nothing was changed. Refresh before deciding whether to retry |
| `internal` | The receiver failed on its side; nothing was changed, and trying again later may work |
| `unsupported` | The runtime or routine does not support this control |
| `not_found` | The runtime no longer has the requested routine |
| `unknown` | The receiver failed on its own side (its storage, say), or a runtime could not confirm a routine control it received, and the outcome is not known; a later sync shows it, and an idempotent request may be retried. Also what a receiver reads for a code it does not know |

## Versions

`v` is the protocol's version, not enclos's or the app's. A change that an older peer would misread raises it; adding an optional field, `type` or capability does not. A bridge speaks its version and the one before it for at least one release, and a device that receives `error` of code `version` tells the person to update the app.

## Sandbox policy requests

[ADR 0046](adr/0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md), proposed. `access.kind` is `network` (one exact host:port, optional private-address opt-in), `write` (one absolute path and everything beneath it), or `read` (shown for review, never removes a read denial). `action` is an agent-supplied label, at most 240 characters; it is data, never executed, and the bridge drops its hidden characters (control, bidirectional and zero-width). A target is at most 4,096 bytes and contains no hidden characters. The plugin's connection supplies its sandbox and agent; the bridge accepts only that agent's own conversation or a group it belongs to. It answers every request with `ack`, after an `error` (`not_allowed`) when it refused it, so the plugin's outbox does not send it again. A sandbox has at most 50 pending requests; past that an agent's request is refused and a proxy refusal waits. A proxy refusal is per sandbox, with no requesting agent or conversation claimed.

The host generates `change`, `scope`, `restart`, `available`, `reason` and the opaque `revision`. `scope` is the entry approval writes: the normalized destination, or the writable path with its symlinks resolved, which the app shows apart from `access.target` when they differ. It refuses wildcards, blocked destinations, protected filesystem paths, pending policy changes, unrelated policy edits and stale previews. Since the agent writes the target, a writable path must be inside the user's home or on an external volume (`/Volumes/<volume>/…`, `/mnt/<volume>/…`, `/media/<user>/<volume>/…`), never a hidden file or folder, `~/Library`, `~/Applications`, `~/bin`, `~/go/bin`, or a folder on the host's `PATH` (or one holding it); such scopes are granted on the host. A private opt-in is per host, including its other ports that the policy already allows, which the preview discloses; from the phone it is for an IP address or a local name (`.local`, `.home.arpa`, `.internal`, `.lan`) only. Write grants store and show the resolved destination, so a changed symlink invalidates the preview and cannot redirect a saved grant. A write change restarts all running sessions; services restart, interactive work ends. An unsupported request stays visible, with Deny and its reason but no approval. The device submits only the stored request id, the preview revision and its decision. The host person must match the transport's own identity and the device must still be paired. An unknown identity or other person gets `not_allowed`.

States: `pending`, `applying`, `approved`, `denied`, `failed`. A database claim serializes two devices' decisions. Requests deduplicate by sandbox, access scope and active policy; a pending scope is not duplicated when the policy changes. A resolved scope may be requested again after a later policy change. A proxy refusal counts once: one older than the bridge's first collection is never collected, and one last seen before a request for the same scope was made is that request's, so after a denial only a refusal later than the request asks again. They are independent of message `seq` and are included at every sync. A stale preview is refreshed and must be reviewed again. `approved` follows the engine's successful application; failure may leave a pending or active change, so `failed` says to review the host's policy. A bridge restart makes an interrupted `applying` request `failed`, never replays it. Denial changes no policy. Both decisions have audit entries naming the device and request.

The bridge sends the active policy as `policy.context` (its grants, and only the number of read denials) after a supporting plugin's hello and after a decision, for every connected agent of the sandbox. Hermes persists it beside the channel socket and supplies it through `pre_llm_call`; a newly connected plugin gets a fresh description. It does not modify user-authored memory or imply that an inactive grant is available. The agent can use approved scopes in later work. Neither side automatically repeats an attempted action.

The Hermes plugin reports concrete `read_file`, `write_file` and `patch` permission errors when their absolute path is known, and registers `enclos_request_access` for explicit requests, including file operations attempted through a shell; both only in an enclos conversation, through the agents that conversation reached. Against a running gateway this is to verify (design §14). A proxy's recorded allowlist/private-address refusals are collected while the bridge runs. There is no attempt to infer a policy from arbitrary shell strings or to observe every backend refusal. Rerun `runtime configure <sandbox>/<agent> --channel app` for existing agents to install the updated plugin.

## Sandbox policy management

Proposed in [ADR 0047](adr/0047-the-hosts-person-manages-sandbox-policy-from-the-phone.md). Only the transport-identified host owner on a still-paired device may read or edit a sandbox policy through this surface. The bridge must list an agent of the sandbox. A page shows the active resolved filesystem, network, resource and secret-reference policy. Accepted access comes from all approved records, independent of the inbox history limit, and labels only entries still present in the active policy. Secret contents are never sent; secret grant management remains on the host.

An edit adds, replaces or removes one entry or replaces one scalar. The host validates it, supplies its exact policy differences and whether it stops running work, and binds the preview to both the active snapshot and policy file. Apply repeats the preview under the state lock; changed sessions can also invalidate a restart-free preview. A pending policy or unapplied file edits disables editing. Removing the last destination for a private host also removes its unused private opt-in, shown in the preview. Public network mode still permits public web ports after an explicit destination is removed, which the preview discloses. Inherited settings are overridden only for that sandbox, and a list edit never copies what the sandbox inherits into its file: an added entry goes to the list's `_add` (or into the list the file already replaces), an entry of the file's own comes out of its list, and an inherited one is named in the list's `_remove`, so the template's, the runtime adapter's and the built-in defaults' other entries stay inherited and later versions of them still reach the sandbox. Its audit entry names the field and the entry before and after. Protected built-in read-deny entries cannot be edited or dropped. Normal compiler, path and backend validations remain authoritative.

Edits are audited with the owner and device. Network-only changes go live; launch-time changes explicitly require Save & restart and use the existing restart path. After an application attempt, the owner gets the current policy and every capable agent plugin gets active policy context. Nothing is automatically replayed after interruption. Cached policy data on the phone is read-only until a fresh host response; clear cache and forgetting a host remove it.

### Diagnostic probe notifications

The reserved `probe.enclos.invalid` network destination is used by the built-in policy probes, not an actionable resource. The bridge never creates access requests for that exact host, on any port, and refuses explicit agent requests for it. Existing pending notifications are atomically reclassified as terminal `diagnostic`, with approval unavailable and no policy change, then delivered so connected devices hide them. Startup and sync perform this cleanup too; a stale phone decision cannot approve the old notification. Network logs remain intact. Other destinations, including private addresses and other `.invalid` names, are never excluded by address alone.

Each policy-test run registers a random, sandbox-scoped, expiring marker in host-only diagnostic metadata (`probe-sources.db`, mode 0600, a side database beside the state database: [ADR 0059](adr/0059-diagnostic-provenance-lives-in-a-side-database.md), proposed). Its curl requests and host controls carry that marker to the proxy; the marker is stripped from forwarded HTTP requests. The proxy still makes exactly the same policy decision. At log insertion, it verifies the marker against an active host registration and atomically records diagnostic provenance beside the unchanged network log. Unregistered, expired or wrong-sandbox markers do not suppress requests. The regular network log and `enclos net denied` retain all refused test connections; the approval collector reads only non-diagnostic refusals. Existing proxy processes must be refreshed once after this host upgrade to record markers.

Pending proxy notifications whose matching refusal history is entirely verified diagnostic traffic are retired without changing policy. A genuine refusal to the same host keeps the notification eligible. An explicit authenticated agent request retains its identity and is not retired by this test-source filter; if it supplies identity after a proxy-only request, the existing pending row is enriched. A later genuine request after a diagnostic notification was closed gets a different id, preserving both stale-decision protection and denial deduplication. Historical untagged log rows are not guessed to be diagnostics; only individually verified legacy probe events can be backfilled.


## Routines

An agent's optional `routines` capability exposes its runtime's scheduler ([ADR 0050](adr/0050-routines-stay-with-the-runtime.md), proposed). These are live controls: the bridge keeps neither definitions nor a second scheduler. They require the transport-identified host's person on a still-paired device, even for a list; a conversation share alone confers no routine-management authority. `agents.list` says so for each person with `can_manage_routines` (true for the host's person only; absent from an older host, meaning false), so an app offers routines only to the person who may manage them. A runtime without the capability keeps the ordinary conversation channel.

Both legs use `routine.request` and `routine.response`. The device request names `agent` (`<sandbox>/<agent>`); the bridge's authenticated plugin connection already identifies it. A response carries `of`, the original request id, and the same device-side `agent`. An `error` uses the same correlation. The bridge uses a separate plugin request id, binds pending work to the requesting device and plugin connection, and accepts only a matching response of the expected result kind. A routine response is not a conversation message and is never placed in its message outbox. The plugin request also carries `person` and `device`, the requester as the bridge authenticated them, never as a device claims.

A routine runs unattended, long after the request that made it, and outlives the device: unpairing a device removes none of the routines it made. So the bridge's log records every change it forwards (`routine.create`, `routine.update`, `routine.delete`, `routine.run`, `routine.pause`, `routine.resume`) with the device, the person, the agent and the routine, once when it is sent and once with its outcome: `confirmed` (with the new routine's id for a creation), the runtime's error code, or `unknown` after a timeout, a disconnection, an unreadable answer or a bridge database it could not read. A list or a read is not recorded. A routine id is the runtime's choice, so the bridge takes only one of at most 128 bytes with no control or hidden character (the shared rule of `enclos_protocol::visible`), from a device as from the runtime: a creation answered with another id is `unknown: invalid response`, and a list leaves such a routine out. `enclos app log` escapes every field it prints. The Hermes adapter also keeps the person and device on the routine it creates (`_enclos_person`, `_enclos_device` in its native origin), and refuses a creation once 50 live routines of the agent were made from the app (`not_allowed`); routines the agent made itself do not count.

| `action` | Request fields | Successful `result` |
| --- | --- | --- |
| `list` | optional `cursor` | `list`: bounded `routines` summaries, optional `next_cursor`, runtime `options`, bridge-authorized `deliveries`, `deliveries_limited` |
| `get` | `routine` id | `routine`: one complete definition and summary |
| `create` | `definition` | `routine`: the saved routine |
| `update` | `routine`, `revision`, `definition` | `routine`: the saved routine |
| `set_enabled` | `routine`, `revision`, explicit `enabled` boolean | `routine`: its confirmed state |
| `run` | `routine`, `revision` | `run`: accepted routine id; acceptance is not completion |
| `delete` | `routine`, `revision` | `deleted`: removed routine id; this does not promise cancellation of running work |

Fields are flat beside the envelope, for example `{"v":1,"id":"r1","type":"routine.request","agent":"lab/main","action":"list"}` and `{"v":1,"id":"r2","type":"routine.response","agent":"lab/main","of":"r1","result":"list","routines":[],"options":{"timezone":"Europe/Paris","features":[],"skills":[],"models":[],"toolsets":[]},"deliveries":[],"deliveries_limited":false}`.

`schedule` is typed: `{kind:"cron",expression:"0 9 * * *"}`, `{kind:"interval",minutes:60}` or `{kind:"once",at:"2026-12-01T09:00:00+01:00"}`. Daily, Weekly and Monthly are editor presets for five-field cron. The Hermes adapter takes a cron expression only as five fields of numbers, `*`, ranges, steps and lists, with three-letter names only for the month and the day of the week. The adapter validates native syntax and computes actual run times. `options.timezone` describes the runtime's effective timezone; it is not an editable per-routine timezone. `features` names supported controls: `skills`, `model`, `provider`, `toolsets`, `script`, `script_only`, `working_directory` and `run`; unknown names are ignored. Skill/toolset choices have `id` and `label`. Model choices additionally have optional `provider`: selecting one changes the model/provider pair together, even if two providers use the same model id. Saved values absent from a catalog remain unchanged.

A `definition` has optional `name`, `prompt`, `schedule`, optional `delivery` conversation id, `skills`, optional `model`/`provider`, optional `toolsets`, optional `script`, `script_only`, and optional `working_directory`. Missing/null toolsets means runtime defaults; `[]` deliberately selects none. Missing delivery means save output without sending it. Scripts name relative files under the agent's scripts directory, including resolved symlink containment; a script a native routine already had is kept as saved when an update leaves it unchanged; script-only requires a script. A working directory is an existing absolute directory and conveys no additional sandbox access. Definitions are bounded (including an 8 KiB prompt); oversized existing native definitions produce an explicit error rather than a truncated editable prompt. Native fields outside this interface survive updates.

Summaries contain opaque `id` and editable-definition `revision`, name, schedule, enabled state, bounded prompt preview, `delivery_label`, `editable`, and optional observed `state`, `paused_reason`, `last_error`, `next_run_at`, `last_run_at` and `last_status`. A disabled routine may be completed rather than paused. A revision covers the definition, not scheduler progress; the adapter compares it under the runtime's lock before changing an existing routine. Native jobs whose targets or settings cannot safely be edited may be shown read-only. This includes external channel destinations rather than making the app rewrite them into an app conversation. A native job the app's format cannot carry at all (no schedule, another kind of schedule, a null field, an id the bridge refuses) is left out of a list, and the Hermes adapter logs that it was, so one such job does not stop the others from being listed. A full definition is loaded only on request; lists paginate at most 25 summaries rather than sending every prompt in one Noise frame. The adapter reads its skill, toolset and model catalogues at most every 30 seconds, not for each page. Plugin results are bounded to 44 KiB before bridge enrichment; device results stay within 60 KiB.

The bridge supplies delivery choices, never trusting a plugin-supplied catalog: only the host person's direct/Home conversations with this exact agent, including archived ones. Groups, another agent's conversations, and another person's conversations are refused. To bound a response it offers Home plus at most 50 recently created conversations and sets `deliveries_limited` when more exist; a full definition preserves its authorized saved target even when that target falls outside the picker. Its internal plugin request carries the allowed conversation ids so the adapter can also check an existing target before a mutation. That list is not accepted from a device. The bridge does not execute scripts, change policy or run a host shell command.

Requests are not queued when the agent is unavailable, and mutations are not automatically replayed after timeout or disconnect. A lost reply after dispatch can leave the outcome unknown; refresh before retrying. When the bridge cannot read its own database, it answers `unknown` and says why in its own output: before dispatch nothing was sent; after the runtime answered, the outcome is unknown, and that answer is not kept, so a retry once the database reads again gets the runtime's replayed answer. The Hermes adapter deduplicates creation using trusted request identity stored with the native job, without writing the jobs file itself. A scheduler-registration failure after a job was saved reports that outcome and does not invite another create. Bounded live replay handling protects repeated requests; it does not promise exactly-once execution across every crash.

Hermes keeps a versioned receipt of at most 4 KiB beside its channel socket for each app-created routine (request fingerprint and native id only), retaining that receipt after deletion so retrying an old create cannot recreate it: the receipts grow by one small file per creation from the app, and none is removed. The native job's origin marker recovers a create interrupted before its receipt was written. `run` claims a native manual attempt before returning acceptance, then dispatches the exact claimed snapshot asynchronously; a paused routine must be resumed first. Native manual execution may advance the next interval occurrence; the app shows the scheduler's resulting next-run time.

Hermes revision comparison and mutation share its native reentrant jobs lock. Its normal cross-process file lock can fall back to in-process locking after a native timeout or locking failure; protection against concurrent native CLI changes inherits that documented limitation ([source evidence](research/hermes-routines.md)). The plugin does not replace its scheduler's locking implementation.

## Shared agent photos

The bridge owns one optional photo for each listed `<sandbox>/<agent>` in its private database. `agents.list` adds optional `avatar: {revision, version}` and `can_edit_avatar` fields. New hosts always include `can_edit_avatar` (false for non-owners); its presence signals photo support so devices never send these messages to older hosts. Revision zero with no version means no photo has been set; a removal retains its increasing revision. `version` is the SHA-256 hex digest of the canonical JPEG, or null. The host's transport-identified owner on a still-paired device may change photos. Currently paired people shown the agent (the same rule as `agents.list`) may fetch its photo; an agent they are not shown is refused with `unknown_agent`. A photo belongs to the agent's name: an agent made again under that name shows it until it is changed.

- `agent.avatar.get`: `agent`. Replies with `agent.avatar`.
- `agent.avatar.set`: `agent`, `revision` (the last observed revision), `image` (base64url raster bytes, or null to remove). The host compares the revision atomically, commits the photo and device audit entry, then returns `agent.avatar` with the request id in `of`. A refusal changes nothing; when the person may still read the photo, the host sends the current one first, then the error: `conflict` for a stale revision, `not_allowed` for a person other than the host's or a device no longer paired, `unknown_agent`, `bad_message` for an image it does not take, `internal` when its database fails.
- `agent.avatar`: `agent`, `revision`, `version`, `image`, `of`. An update or removal is broadcast, with empty `of`, to every other connected device that is still paired and shown the agent; the device that made it gets the reply instead. Devices ignore older revisions. Reconnecting devices learn the latest metadata through `agents.list` and fetch a missing/different photo; images are transferred only through the authenticated Noise connection, without public URLs.

Uploads are JPEG or PNG, at most 32 KiB and 512 × 512 pixels with bounded decoding allocation. The host crops and re-encodes a 256 × 256 JPEG, stripping source metadata and bounding the result to 32 KiB. Base64 plus the envelope fits one Noise transport frame. Clients resize/compress a selected photo before upload, show only confirmed host data and retain the coloured initial when no photo exists. Cached photos are private to the app, scoped to the full host/sandbox/agent address, hash-checked and removed by Clear cache / Forget this host. Removing a cached copy does not remove the shared host asset.
