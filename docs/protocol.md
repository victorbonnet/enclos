# The mobile app protocol

Status: **version 1, released with enclos 0.5.0.** The decisions behind it are still proposed, with [ADR 0042](adr/0042-a-bridge-on-each-host-serves-the-mobile-app.md) and [ADR 0043](adr/0043-sharing-an-agent-is-not-hosting-it.md); each feature records its verification separately. Its words are the glossary's: host, sandbox, agent, runtime, bridge, paired device, person, share, conversation.

The protocol has two legs, one message format:

```
paired device ──WebSocket over the tailnet, Noise inside──► bridge ──Unix socket in the sandbox home──► channel plugin ──► runtime
```

- **The device leg**: the enclos app and the host's bridge. The bridge listens on the host's loopback, reached through `tailscale serve`. Every frame after the handshake is a Noise transport message.
- **The plugin leg**: the bridge and one agent's channel plugin, inside the sandbox. A Unix socket the plugin listens on in the sandbox home, one per agent; JSON lines, no encryption (it never leaves the host).

It describes conversations, people and capabilities, never one runtime's words: a runtime's own features (Hermes's kanban, OpenClaw's nodes) stay out, or come as an optional capability.

## Messages

Every message is one JSON object: UTF-8, at most 1 MiB, with these fields first. On the plugin leg a receiver reads a line of up to 1 MiB; a longer one it answers with an `error` (`bad_message`, `of` its `id` when its first bytes hold one), so the sender knows at once that it did not arrive, and then ends the connection (below).

| Field | Type | Meaning |
| --- | --- | --- |
| `v` | integer | The protocol version, `1` |
| `type` | string | What the message is (below) |
| `id` | string | Unique per sender, a UUID; used to acknowledge and to drop duplicates |

Unknown fields are ignored. An unknown `type` is answered with an `error` of code `unknown_type` and otherwise ignored, so a newer peer can send optional messages to an older one. A message the receiver cannot use (not JSON, too big, a field missing or wrong) is answered with an `error` of code `bad_message`, its `of` naming the message's `id` when one could be read, and the receiver goes on reading: one bad message never ends the connection. Two things do: a `v` the receiver does not speak, answered with `version` ([Errors](#errors)), and, on the plugin leg, a line over 1 MiB, answered with `bad_message` (its `of` when the line's first bytes hold its id, as above), so a sender checks the size of each message before it sends it. On the device leg a frame that does not decrypt ends the connection too (below), and so does a first message, once the handshake is done, that is not an `auth` or a `pair.request` the bridge can use: a bad one (including a `sig`, `proof` or `device_key` that is not base64url) is answered with `bad_message` or `unknown_type` first, and the refusal is logged.

On the plugin leg, one message per line (`\n`, never inside a message). On the device leg, one message per WebSocket binary frame, inside a Noise transport message; a text frame is answered with `bad_message`, with no `of`.

A Noise transport message holds at most 65,535 bytes, its 16-byte tag included, and this protocol defines no fragmentation. So **on the device leg a message is at most 65,519 bytes**, as it is sealed: its JSON and the line break after it. The 1 MiB limit holds on the plugin leg only.

- **An agent's text that does not fit** (`message.out`, or a cron job's output) is split by the bridge, at character boundaries, into several `message`s of the same conversation, each with the next `seq` and stored as it is sent. A device sees them in order, as consecutive messages from the agent; the plugin and the runtime see one message. A `message.out` whose other fields leave no room for any text in a device message is refused (`bad_message`) and stored nowhere; with its files' details kept as [Files](#files) says, none does.
- **A person's text is one message:** the app refuses, before sealing, a `message.send` whose text would not fit as a `message` (its echo, with the conversation's other fields), and keeps the person's text; `enclos-protocol`'s `split_text` giving one piece is the test. The bridge answers one that gets through with `bad_message` and stores nothing, and closes a connection whose frame does not decrypt, so a larger one ends it.

### Names

Every id and name a message carries (`id`, `of`, `conversation`, `person`, and a plugin `hello`'s `runtime` and `agent`) is not empty, at most 128 bytes, and holds no control character; an `error`'s `message` holds no control character either. A message that breaks this is a bad message. The host prints some of them, so text from the sandbox can neither move a terminal's cursor nor break a log's line.

- **An agent** is `<sandbox>/<agent>` on one host, as enclos names it. The app adds the host it reached.
- **A conversation** is a UUID the app makes. The plugin gives it to the runtime as the chat's id, so a new conversation is a new chat for the runtime, and a cron job created in it remembers it as its origin.
- **A person** is a tailnet login, as Tailscale's WhoIs gives it (`alice@example.com`). In version 1 the only person is the host's user; the field is there from the start so sharing (ADR 0043) changes no stored history.

## The plugin leg

The plugin listens; the bridge connects. Several bridges never connect at once: the plugin refuses a second connection while one is open. The plugin has 10 s to answer the bridge's `hello`, and 10 s to read what the bridge writes; past either, the bridge ends that connection and opens a new one on its next try, and other agents' plugins do not wait for it.

1. **`hello`, bridge to plugin, first:** `{"v":1,"type":"hello","id":…,"token":"…","home":"home.lab.main"}`. The token is the agent's, a secret granted to that agent ([ADR 0036](adr/0036-an-agent-has-its-own-bot.md)). The plugin compares it in constant time and closes the socket, saying nothing, on any other first message or token. `home`, optional, is the agent's [Home](#home) conversation. Optional `capabilities`, absent meaning an empty list, advertises bridge support for `questions`, `runtime_approvals`, `activity`, `tasks`, `held_tasks` and `task_events` independently.

   **What the token proves, and what it does not.** It keeps the host's other programs, and other sandboxes, off the agent's socket, and nothing more. The token is in the sandbox, where the agent and anything it runs can read it, as they can every secret of the agent's (ADR 0036), and the socket is in the sandbox home. So a program in the sandbox can connect to its own plugin while the bridge is not connected and send it any message the bridge sends, and a program that listens on the socket's path gets the token from the bridge. Hence the rule: **no message from the bridge to the plugin carries authority the agent must not have.** A message the plugin passes on is what a person said, never a decision the runtime then trusts more than the agent's own words; a decision that must come from the person needs its own proof. Version 1 defines two, both signatures by the bridge, which the plugin checks with a key it gets when the channel is set up, not over this socket: of each runtime-approval decision ([Runtime approvals](#runtime-approvals), [0060](adr/0060-the-bridge-signs-runtime-approval-decisions.md), proposed), and of each message the host's person sends in a direct conversation, which OpenClaw's channel gives its runtime's owner authority ([0077](adr/0077-the-hosts-person-speaks-to-openclaw-with-its-owner-authority.md), proposed).
2. **`hello`, plugin to bridge:** `{"v":1,"type":"hello","id":…,"runtime":"hermes","agent":"main","capabilities":[…]}`. The plugin has 10 seconds in all for it, and at most 64 KiB: the bridge gives up on the connection after that, and tries again when it next needs the agent. One agent's plugin slow to answer holds up only what needs that agent.
3. Then, in either direction:

**A conversation's name.** The bridge keeps one name per conversation and who gave it. The runtime's (`conversation.title`, for one of its own agent's conversations) replaces the runtime's; the person's (`conversation.rename` from a device) replaces any, and the runtime's no longer replaces it until the person clears it. Whoever gives it, the bridge keeps a name on one line, drops the hidden characters (control, bidirectional, zero-width and the like, as `enclos_protocol::visible` lists them) and cuts it to 100 characters: it does not rely on the plugin's cut, which runs in the sandbox. The bridge passes the person's name on to the plugin, so the runtime can keep it too (Hermes: the session's title, with the user's authority). Hermes names every session on its own and tells no plugin, so its plugin reads the title after each reply, and a little later, and sends it when it changed.

**Cancelling a turn.** `turn.abort` names one original ingress, never the latest run of a conversation. A missing, completed or mismatched target has no effect on another turn. An acknowledgement accepts the cancellation request; it does not claim native cleanup has drained. OpenClaw retains the exact public run abort signal. Hermes uses its public processing lifecycle and interruption helper with native task/guard identity checks. [Source and native tests](../channels/openclaw/NATIVE_CANCELLATION.md) describe those compatibility boundaries.

**Home.** Each agent has one Home conversation ([ADR 0044](adr/0044-each-agent-has-a-home-conversation.md), proposed): id `home.<sandbox>.<agent>`, made by the bridge, owned by the host's person, named Home. An agent made again after it was [forgotten](#forgetting-a-removed-agent) gets a new id, `home.<sandbox>.<agent>.<n>`, with the first `n` from 2 that no conversation, deletion or other Home has used: the bridge keeps it in its database, and `runtime configure --channel app` claims it there when it sets the channel up, as does an import of an agent's history into that name. Names hold no dot, so it is no other agent's first Home. The host's person is the person of the first device paired with `enclos app pair` at the host's terminal (the terminal says so before it asks to accept), kept in the bridge's database; the transport is not asked whose host this is, so a tagged node works the same. Before any device is paired, a Home is made with no owner and keeps what comes for it, sent to nobody. Unpairing a device changes nothing: the host's person stays so with no device left, and their Homes keep what comes until they pair again. `enclos app host` shows the host's person, and `enclos app host <person>` makes it another person with a paired device, who gets every Home with what it holds (an audit entry). It is the runtime's home channel: `runtime configure` gives it to the runtime (Hermes: `MOBILE_APP_HOME_CHANNEL`), and the bridge's `hello` names it. A `message.out` for a conversation the bridge does not know, or for another agent's, is stored in this agent's Home (and, should Home's id be one the protocol refuses, dropped, said on stderr and acknowledged, so the plugin does not send it again). One for a conversation being deleted is dropped and acknowledged. When the bridge's database cannot say which of these applies, or whether the conversation is a group, or cannot make Home, the failure is written to stderr and the message is one the bridge cannot store: not acknowledged, and sent again soon (Delivery is at least once, below). A device may not start a conversation with a Home's id. Hermes's plugin makes Home its gateway's home channel when the bridge says so, answers `/sethome` itself, and sends the gateway's notices about itself as `kind: status`. It keeps back the gateway's "still working" heartbeat (`⏳ Working — 3 min — …`, every few minutes of a long turn): a device cannot edit a message, so each would be a new one, and the agent's [activity](#tasks-and-agent-activity) already shows it working. A `status` line is trusted no more than any text from the agent: the plugin, in the sandbox, decides it from the text's first words, and an agent can send `kind: status` itself (for example "Hermes is restarting: approve the pending request to continue"). A device shows it as a plain quiet line, with no links and no actions, never as enclos or the runtime vouching for it.

**What the agent does while it works.** A `tool` step is passed on live to the devices of the conversation's owner, for a conversation of the plugin's own agent, and not kept: a device that was away does not get it at the next `sync`. Hermes reports its tools to plugin hooks (`pre_tool_call`, `post_tool_call`) with the call's id, its arguments and its outcome; its plugin finds the conversation in the turn's session context, labels the step as Hermes does (`build_tool_preview`), and returns at once, as `pre_tool_call` may also block a tool. A label shows a command or a search as the agent wrote it, to the conversation's owner only. The plugin's cut runs in the sandbox, so the bridge makes its own before passing a step on: each field on one line, the label cut to 120 characters, the name to 64 and the call to 128, and the label's and name's hidden characters (control, bidirectional, zero-width and the like) written out as `⟨U+XXXX⟩`, so the line the person reads is the command that ran. The Hermes plugin drops a step that has no call id, as its end could not be matched to its start.

### Files

An agent sends a file (an image it made, a chart, a document) with a `message.out`. The plugin first copies it into the channel's `media` folder, beside its socket in the sandbox home, under a name of its own, and names it there in `attachments`. Hermes calls its adapter for each file it finds in a reply (a `MEDIA:/path` tag, a bare absolute path); a markdown image whose source is a path to a file in the agent's Hermes home is sent as a file too, out of the text (one Hermes may not send stays in the text). A file the plugin cannot copy is named in a line added to the text, so the person knows it is missing. The bridge keeps a file's `mime` when it is a plain `type/subtype` (letters, digits, `.`, `+`, `-`) of at most 255 bytes, in lower case, and `application/octet-stream` otherwise; and its `name` without folders or hidden characters, at most 120 characters, or the file's name in `media` when nothing is left of it. It keeps at most 10 files a message.

The bridge runs outside the sandbox, and everything in the sandbox home is the sandbox's: it opens that folder from the sandbox home one folder at a time (`.enclos-app`, then `media`) without following a link at any of them, so a link put in place of either cannot point it at a host folder. In it, the bridge takes a file only by its plain name, opened without following a link and without waiting (a named pipe is refused, not waited on), and only a regular file with no other link to it, of at most 25 MiB; it copies no more than that even while the file grows, into its own media folder (beside its database), under an id, first in its `.incoming` folder. It stores the message and its files' records together, then moves its copies into place, and only then removes the plugin's copies through the same opened folder. A file refused for what the sandbox did (its name, its kind, a link, another link to it, its size, a read that fails) is left out, and the message is stored without it. A message the bridge cannot store this way, its database or its own copy failing (a full disk, a media folder it cannot make), is not acknowledged, and the plugin sends it again with its files still in place. The bridge removes its copies for that message; should it stop before, it does so when it starts again, and moves into place those of a message it had stored. A message sent again once stored is not stored twice; the plugin's copies of its files, left there if the bridge stopped before removing them, are removed then. It takes at most 10 files from one message. Its `name` is the last component of the plugin's, without the characters that change how text reads without showing (controls, line breaks, bidirectional and zero-width characters: the protocol crate's `visible` rule), and at most 120 characters, since it titles the artefact card, the viewer and the Share sheet. A device gets each message's `attachments` (`id`, `mime`, `name`, `size`) and fetches the bytes with `attachment.get`, over the same Noise session: never from an address, and only for its person's own conversations.

**Static HTML artefacts.** A self-contained UTF-8 HTML file is sent as an ordinary attachment, with `mime: "text/html"` ([ADR 0048](adr/0048-artefacts-are-static-html-attachments.md), proposed). In Hermes the agent writes the file, then emits `MEDIA:/absolute/path/page.html` on its own line. The media type alone makes it an artefact; the file name is not checked (Hermes derives `text/html` from a `.html` or `.htm` name). The app offers an artefact card that opens the page in a separate viewer, with Back, its name and Share. The viewer is meant to render inline CSS and data images or fonts, and to refuse scripts, network assets, relative files, forms and automatic outgoing navigation. Same-page anchors stay in the viewer. A main-frame HTTP(S) link the person taps first shows a native sheet with the destination host and full address; only after the person confirms does the website open in the preferred browser's Custom Tab on Android where supported, with the browser's normal state. Redirects, subframes, navigation without a user gesture and other schemes are meant not to reach that sheet. These are intended controls: which of them the platform probes have shown is in [design §14](design.md#14-awaiting-prototype-verification) and the app's spec. A link the person opens carries whatever the agent put in its address to that website, from the phone, outside the sandbox's network policy; the sheet is there so the person sees where it goes. The channel hint tells the agent this contract. No new message, capability or delivery path is introduced; an older app can still share the attachment. HTML in `text` keeps the markdown behavior below.

**What the agent says is markdown.** The `text` of a `message.out` is CommonMark with GitHub's tables, strikethrough and bare links; a device draws it, and fetches and runs nothing in it: an image in it shows as its alt text, a link to it, and is never loaded (a file the agent sends comes as an attachment, [Files](#files)); HTML shows as its text; and only `http`, `https` and `mailto` links open on a tap (HTTP(S) in the preferred browser's Custom Tabs on Android where supported, `mailto` in its system handler; the app's [ADR 0002](https://github.com/victorbonnet/enclos-app/blob/main/docs/adr/0002-messages-are-markdown-drawn-by-the-app.md), proposed). A plugin tells its runtime so (Hermes: the platform's `platform_hint`), so that the agent formats when it helps. What a person sends (`message.in`) is plain text, shown as typed.

### Sending files

A person sends an agent 1 to 4 photos or documents with a message, in a direct conversation or Home, never a group ([ADR 0076](adr/0076-the-plugin-writes-files-a-person-sends-inside-its-sandbox.md), proposed). A bridge that takes them names `message.begin` in `authenticated`'s `capabilities`, for every person.

**What a file may be.** Each is declared `{name, mime, size}`: `size` 1 to 10,000,000 bytes; `name` one component (no `/` or `\`), not `.` or `..`, no control, line break, bidirectional or zero-width character (the `visible` rule), no space at either end, at most 120 characters and 255 bytes; and its extension, after the last dot with something before it, in any case, must be one of these with exactly that `mime`: `.jpg` `.jpeg` `image/jpeg`, `.png` `image/png`, `.webp` `image/webp`, `.gif` `image/gif` (photos); `.pdf` `application/pdf`, `.md` `text/markdown`, `.txt` `.log` `.py` `.sh` `text/plain`, `.csv` `text/csv`, `.json` `application/json`, `.xml` `application/xml`, `.yaml` `.yml` `application/yaml`, `.toml` `application/toml`, `.zip` `application/zip`, `.doc` `application/msword`, `.xls` `application/vnd.ms-excel`, `.ppt` `application/vnd.ms-powerpoint`, `.docx` `.xlsx` `.pptx` their `application/vnd.openxmlformats-officedocument.…` types (documents; the protocol crate's `FILE_TYPES`). A name or type is refused, never changed. The type is declared, not checked against the bytes.

**On the device leg.** The device sends `message.begin` (`conversation`, `text`, `files`), whose `id` is the message's, as a `message.send`'s is; then every byte of its files in `message.part`s on the same connection (`message`: the begin's id, `file`, `offset`, `data`, as on the plugin leg, each with an `id` of its own): file 0 from offset 0, each part at the offset where the last one ended, a file ending exactly at its `size`, the next starting at 0, every byte once. The bridge answers no part. Once the last byte came, it stores the message with its files, as an agent's are kept, sends its `message` (with `attachments`, which `attachment.get` fetches) and then `ack`s the begin's id as a durable storage receipt. Plugin admission settles separately: a message queued behind an unsettled file delivery in the same conversation receives its storage receipt and waits in order; other conversations can proceed. One message with files is sent at a time on a connection; other messages may come between its parts. Nothing of it outlives the connection until it is stored: there is no upload, resume or partial state. A connection that ends before the last byte, a part that is not the next one or goes past its file's `size`, or a line the bridge cannot read meanwhile (a part with bad `data` among them) drops the whole message, and the device sends it again whole, `message.begin` first, under the same id: one stored already is not stored again, and is acknowledged. The bridge answers an `error` naming the begin's id: `bad_message` for files out of these bounds (at `message.begin`, before any byte), a part not the next, or a text too long for one message with its files; `not_allowed` for a conversation not the person's, a group, a typed approval command or `/sethome` (answered by the plugin, so its files would go nowhere); `unsupported` when the agent's plugin does not name `incoming_files`, checked at `message.begin` and again at the last byte; `conflict` for a conversation being deleted, or a second `message.begin` while one is being sent (naming the second); `agent_unavailable` when the agent cannot be reached at `message.begin` (waiting up to 15 seconds first for a restarting agent's channel, as a conversation message does, with the same bound on when a retry starts; nothing is kept either way, and a stopped or created sandbox is answered as any unreachable agent is); after durable storage, forwarding failure retains the message for delivery and does not revoke its receipt; `internal` when the bridge cannot keep a file. A part that names no message being sent gets `bad_message` naming the part.

**On the plugin leg.** The bridge sends a stored message with files only to a plugin that named `incoming_files`: `message.in` with `files`, then at once all their bytes in `message.part`s, in the same order, under the `message.in`'s id. To another plugin it sends neither the files nor the text alone: the message waits. The plugin gives the runtime the message once every byte came, and acknowledges it as any `message.in`. An interrupted connection drops the partial plugin copies and permits a whole-message retry. A malformed part drops the copies and produces `error` `bad_message` naming the `message.in`; that explicit refusal settles the stored operation with a terminal status notice rather than sending it again. The Hermes plugin writes the files in its own folder beside its socket in the sandbox home, `.enclos-app/incoming/<agent>/<random>/<n>-<name>`, the name reduced to ASCII letters, digits, `.`, `_`, `-` and spaces; it opens each folder from the socket's without following a link, makes each file new (never through a link, mode 0600), and gives Hermes a `MessageEvent` with `media_urls` (those paths), `media_types`, and `message_type` `PHOTO` when any file is an image, `DOCUMENT` otherwise, as Hermes's own platforms do, so a photo reaches its vision and a document its document handling. **Retention:** the bridge keeps its copies with the message until the conversation is deleted; the plugin expires recognized completed or abandoned copies after 24 hours, checked each minute while listening. Successful native deletion removes copies with matching conversation metadata; cleanup failure returns an error for retry. Legacy or incomplete metadata permits expiry but not conversation attribution; unexpected entries and symlinks are preserved. New file deliveries use public `admit_producer`, which captures independent immutable runtime-owned bytes before committing admission. Plugin staging from this path expires after 24 hours, including after a crash between admission and receipt recording; active in-process captures stay protected. Receipt identity is written through an atomic pending-marker replacement. Legacy pending markers retain their conservative lifetime. Public media capture and queued/terminal resource behavior have focused tests; complete producer ingress/restart integration is not yet verified. See proposed [ADR 0076](adr/0076-the-plugin-writes-files-a-person-sends-inside-its-sandbox.md) for lifecycle and slow-plugin limits.

A plugin error naming a stored incoming file message settles its pending state and appends one deduplicated `kind: status` notice to the original conversation, naming the original device operation and filenames with a safe reason. Missing bridge copies use the same settlement before later text in that conversation proceeds. Other conversations can progress independently. After commit, the original device, if connected, receives `error.of` naming its original begin id. The notice remains in ordinary history after disconnect or restart; the original operation stays deduplicated. Native capture protects active staging through completion; cancellation or an uncertain write does not announce terminal failure. Owner-accepted limitation: in the rare case where the native chat is deleted during native handoff, a typed not-found error can report terminal failure and release plugin staging even though the runtime may already have committed. This limitation is not fixed; generic store errors remain uncertain, and no other authority, safety, lifetime or retry invariant is excepted. Receipt ACK is not proof of model delivery. Images additionally require `incoming_images` (dependent on `incoming_files`), checked at begin, final storage and forwarding. Hermes rechecks the selected conversation runtime at arrival using its session resolver, image routing and auxiliary probe. Unknown eligibility refuses images; documents are unaffected. The session resolver is currently a private Hermes integration seam. Full public-ingress/restart and refusal/reconnect proof remains outstanding.

**Delivery is at least once.** The plugin keeps each `message.out` on disk, in the sandbox home, until the bridge's `ack` for it, and sends what it kept again after each `hello`. The bridge drops an `id` it has already stored. A `message.out` the bridge cannot store or place, as its database fails, is not acknowledged, and the bridge ends the connection, so that the plugin sends it again when the bridge connects again: within seconds, then, while that keeps happening, after 3 seconds, twice as long each time, up to a minute. What the plugin sent behind it on that connection is read no further, and comes again the same way; a `message.in` whose `ack` it held is sent again, and the plugin drops one it has already. The bridge acknowledges a `message.in` it sent only once it has stored it; the plugin acknowledges it once the runtime has it.

**An agent's messages are paced.** Every runtime may send on its own, so the bridge stores at most 120 of an agent's `message.out` at once and then 60 a minute, one a second (`src/bridge/pace.rs`). Past that, it reads the plugin's next message only when there is room again: the plugin waits, and loses nothing, since it keeps each message until the `ack`.

## The device leg

### Pairing

`enclos app pair` prints a QR code holding:

```
enclos://pair?v=1&host=<host name>&url=https://<host>.<tailnet>.ts.net&key=<bridge static key>&code=<one-time secret>&exp=<unix time>
```

- `host`: the first label of the bridge's address: 1 to 63 letters, digits, `-` or `_`. A link with any other is refused, so a host's name never holds the `/` or `:` an app may join a host, a sandbox and an agent with. When the address starts with no such label, `enclos app pair` says so and writes `host`.
- `key`: the bridge's static X25519 public key, base64url, which the app pins.
- `code`: 128 random bits, base64url, single use, valid until `exp` (5 minutes).

It also prints that link, and an https link to open on the phone: `https://<host>.<tailnet>.ts.net/pair#v=1&host=…` (the same parameters, after `#`). A chat or a note opens an https link, not an app's own scheme. The bridge answers `GET /pair` with one static page, the same for everyone, which reads the parameters in the browser, shows the host and the time left, and opens the `enclos://pair` link in the app on a tap. The page vouches only for its own bridge: it shows the address it was loaded from, not the link's `host`, and offers nothing when the link's `url` is another origin, so a link that names this host but another bridge does not read as this host's. A browser never sends what follows `#`: the code does not reach the bridge, its transport or a log through the page. The link itself, code included, stays wherever the person pasted it (a chat, a note) until it expires, 5 minutes after `enclos app pair` made it, and the host's terminal still has to accept the phone. Every other request is a device's WebSocket.

The app makes its **device key**, a P-256 key in the phone's hardware (Android Keystore, StrongBox where the phone has it; Secure Enclave on iOS, which holds only P-256), and its own static X25519 key, kept encrypted under a hardware key. It runs the Noise handshake below as a device the bridge does not know yet, then sends, instead of `auth`:

| `type` | From | Fields |
| --- | --- | --- |
| `auth` | device | `device`, `sig` (base64url DER signature of `enclos auth v1` ‖ the handshake hash) |
| `authenticated` | bridge | `person`, optional `capabilities` (`usage` for usage windows, `usage.series` for their series over time and `usage.cost` for their costs and windows of one sandbox or agent, and `message.begin` for [sending files](#sending-files), offered to every person; `sandboxes` for provisioning, `audit` for audit pages, `approval.close` for closing policy requests and `agent.forget` for forgetting removed agents, offered to the host's person) |
| `pair.request` | device | `name` (the device's model), `device_key` (P-256 public key, SEC1, base64url), `proof` (HMAC-SHA256 of `enclos pair proof v1` ‖ the handshake hash, keyed with `code`), `sig` (base64url DER signature, by `device_key`, of `enclos pair v1` ‖ the handshake hash), `push` (`{"kind":"fcm","token":…}`)? |

The bridge checks `proof`, and `sig` with `device_key`, so the device holds the key it asks to pair; then it shows at the terminal the device's name, its tailnet person and node (WhoIs), and asks to confirm. Only then does it store the device: both public keys, the person, the node, `push_key`, and writes an audit entry. A code works once, whatever the answer. The device chose its `name`, so the bridge keeps it plain before the terminal shows it: without the characters `enclos-protocol`'s `visible` rule calls hidden (controls, bidirectional and invisible marks), white space made single spaces, at most 64 characters. While the person decides, the device's pings count as hearing from it.

### Handshake

`Noise_IK_25519_ChaChaPoly_SHA256`, the device as initiator, the bridge's static key known from pairing, with the prologue `enclos/device/1` on both sides, so a handshake of another version never yields this one's hash; the handshake messages carry no payload, and one that does is refused. The device's first message once it is done is `auth` (or `pair.request` while pairing): its id on this host and an ECDSA P-256 signature, by the device key, DER as the phone's keystore gives it, of a fixed label and the **handshake hash**, which binds it to this session's ephemeral keys. The bridge then:

1. knows the device by its static key, or refuses it (unless pairing);
2. checks `sig` with the device key it stored, and answers `authenticated` with the person the device speaks for;
3. asks Tailscale who is calling, and refuses a person or a node other than the device's own;
4. writes each refusal, with its reason, in the bridge's log (`enclos app log`).

Any login of the tailnet gets as far as the first message, so the bridge keeps callers that are not authenticated yet few and short: at most 16 at once (one more is closed at once), 30 s from connecting to its first message, however slowly that message's bytes come, and no WebSocket message or frame larger than one Noise message (65,535 bytes). It logs at most 10 refusals per caller address and minute; past them, that address's connections are closed that minute without a log line or a question to Tailscale. The log keeps its newest 10,000 lines. Once authenticated, a session with nothing from the device, not even a ping, for 75 s ends: the enclos app pings every 30 s. So does a session when a write to its device makes no progress for 30 s: a device that stopped reading. When a device connects again while its old connection is still open, the new connection is the one messages go to.

The hardware key signs two things only, each a fixed label then the handshake hash: `enclos auth v1` for `auth`, `enclos pair v1` for `pair.request`. A signature for one is never one for the other, nor for anything outside this protocol.

`authenticated.capabilities` is an optional list of strings advertising device-facing bridge controls, such as `["approval.close"]`. `approval.close` enables closing sandbox policy requests; an older bridge omits it, so clients keep that action disabled. This advertisement is feature support, not authority, and does not replace each control's person and pairing checks: the bridge offers it, like the other host controls, only to the host's person, and checks that person and the device's pairing again on each close.

`auth` may additionally declare `capabilities`, an array of optional device features supported on this connection. Missing means empty; unknown names are ignored and this declaration grants no authority. `runtime_approval_scopes` opts into the [independent native approval scope](#runtime-approvals) representation. `task_events` says the device draws a runtime's [task events](#task-events) as task lines; without it, it gets each as a `notify`. Neither is inferred from an agent's capabilities or saved with the paired device.

### Deleting conversations

[ADR 0062](adr/0062-conversation-deletion-retires-native-chats-before-bridge-history.md), proposed, records the deletion order and retained ids.

Deletion is separate from Archive. `conversation.delete` removes an active or archived direct or group conversation; Home is refused. An unknown id and another person's id receive the same `not_allowed` answer. The bridge treats an agent as already removed only when the runtime's no-follow identity and folder checks confirm no native identity or data remains; a missing channel, a removed record or an unreadable home is insufficient. A sandbox removed with its folder (`sandbox rm`) leaves no native data, so its agents count as removed. Its agents' Homes stay, with their messages and files, as Home cannot be deleted here; the host's person may [forget](#forgetting-a-removed-agent) such an agent instead. A sandbox removed with `sandbox rm --keep-data` no longer records its runtime, so every runtime's checks look in the home it left. When enclos cannot tell (its state or the folder cannot be read), the agent does not count as removed: the deletion needs its channel, and the reason is written to the bridge's standard error. Otherwise it checks every remaining member's `conversation_delete` plugin capability, stops group scheduling, then sends each plugin `conversation.delete` with the conversation id. A plugin acknowledges only after its native session owner removes that chat's history, and answers errors without acknowledging. Hermes uses the same revision- and generation-fenced native delete mutation as its Android and iOS REST clients, including route retirement and transcript/request-dump cleanup. Native interrupt and cancellation stop running and queued admissions; the plugin never deletes rows behind the gateway. A pre-owner Hermes release uses its mobile endpoint's native `SessionDB.delete_session` with active-write guards and native compression-lineage lookup, followed by `SessionStore.remove_by_session_id` and cache retirement in the running gateway. The selected database must belong to the adapter's captured agent home. A runtime or channel without either supported deletion API answers `unsupported`.

Before native requests, the bridge reserves the id durably, blocks new messages and group turns in it, and checkpoints each acknowledged member. After every member confirms, it removes its attachment files, messages, questions, turns, members and conversation metadata. Only the id and owner remain as a permanent deletion record, preventing reuse and informing phones that last synced past every deleted message. Deletion runs on a bounded worker; the requesting session continues reading pings, syncing and draining its outbox during native round-trips. One `conversation.deleted` broadcast reaches every connected device of the owner before the requesting device's `ack`. Final removal and one `conversation.delete` log entry (device, person and id) commit together; idempotent retries do not add another deletion entry. Every sync repeats permanent deletions regardless of `since`. Devices persist them and ignore later metadata, messages, typing, tools and group state for that host and id.

An unavailable or unsupported channel discovered before native deletion releases a fresh reservation. Once native deletion may have started, an interrupted, timed-out or failed attempt retains its reservation and remaining targets for an explicit retry of Delete, including after a bridge restart. Bridge history stays until completion, and acknowledged targets are skipped on retry. A lost final response is recovered by retry or sync. Late runtime output for a reserved or deleted id is acknowledged and dropped, rather than redirected to Home. Agents, saved memory and scheduled routines remain; routines targeting the deleted id need a new destination.

### Forgetting a removed agent

Proposed [ADR 0067](adr/0067-the-hosts-person-can-forget-a-removed-agent.md). The bridge offers `agent.forget` in `authenticated.capabilities` to the host's person only. `agents.removed` lists, in `agents.removed.list`, each agent the person has a Home or a direct conversation with that the deletion check above confirms removed: no native identity or data left, as after `sandbox rm`. An agent removed with `--keep-data`, or one enclos cannot tell about, is not listed, and `agent.forget` refuses it with `not_allowed`; a name that is not `<sandbox>/<agent>` gets `bad_message`. The bridge checks the host's person and the device's pairing again on each forget, as for the other host controls.

`agent.forget` deletes the agent's Home and every direct conversation of the person's with it, archived ones included, each as a completed deletion with no native round-trip, since nothing native is left: its id is kept as a deletion record, its messages, files, questions and turns are removed, and every connected device of the person's gets `conversation.deleted` for it, before the requesting device's `ack`; one offline gets it at `sync`, as for any deletion. Groups the agent was in stay, each deleted on its own. A deletion of one of these conversations that was started and not finished is finished by the forget. Other people's conversations with the agent stay theirs. When it deletes any conversation, the bridge's log (`enclos app log`) gets one `agent.forget` entry with the device, the person, and the agent and every conversation id; forgetting an agent with none left, or again, deletes and logs nothing, and still keeps its Home forgotten.

From then on, the agent has no Home: the bridge makes none for it, drops a `message.out` that would go there (said on stderr), and refuses to connect to its plugin until its app channel is set up again. When it is, it gets a Home with a new id ([Home](#the-plugin-leg)).

### Groups

A group is one conversation between a person and two to six agents of **one sandbox** ([ADR 0045](adr/0045-group-conversations-are-the-bridges-among-one-sandboxs-agents.md), proposed): a sandbox is enclos's boundary, and a group across two would carry one's conversation into the other. The bridge keeps its log, in order with every other message, and runs its turns; the device shows them and sends the person's messages (`message.send`), as in any conversation. Each member keeps its own session for the group in its runtime: the bridge gives the plugin the group's id as the conversation, apart from the member's one-to-one conversations, and never copies those into the group.

**Addressing.** A member's handle is its name in the sandbox (`main`, `coder`), matched whatever the case. `@handle` addresses that member, several mentions those members, `@all` and `@everyone` every member, and a message with none every member. In an agent's message, a mention of another member asks it for a follow-up turn.

**Turns.** One at a time per group; groups run side by side. A person's message starts a discussion: its first round is the members it addresses, in the group's order; each next round is the members an agent's message mentioned since and who have not spoken since. For each turn the bridge sends the member a `message.in` whose text gives the group's name, the member's handle and the others', the group's messages the member has not seen, oldest first (the newest 24 at most, each with its speaker: `User (<person>):` or `@handle:`, each cut at 3,000 bytes and 24,000 bytes in all, so the `message.in` fits a plugin's line), and the rules: reply once if there is something new to add, else reply exactly `(pass)`; mention a member to bring it in; never reveal what was said in a private conversation. A message's own lines are quoted under its speaker, each starting `    | `: every line break in it (`\r`, U+2028, U+2029, U+0085, a form feed or a vertical tab as much as `\n`) is one, and its hidden characters are dropped, so no line a member writes starts as a speaker's or the rules do. A model may still take quoted words for the person's: this keeps the lines apart, it does not make a runtime ignore them. A member the person addressed by name, its handle or `@all` ("a response from all"), is told to answer or say what blocks it, not to pass, and a pass from it fails its turn; a message naming no one invites every member, who may pass. The turn ends with the member's `reply` to that message: `(pass)` is stored as no message, anything else as the member's message (and what it sent before the reply, `notify` in the meantime, as its messages too). A further `reply` to the same message, such as the files Hermes sends after a reply's text, is kept as the member's message too, unless it is `(pass)`; it ends no other turn. While the discussion goes on, the mentions in what a member sends for its turn besides the reply, before or after it, ask for follow-up turns as the reply's do. A turn with no reply after 15 minutes fails; one fails at once when the member's plugin answers its `message.in` with an `error`, or its connection closes, and the next member's turn starts. The discussion ends **settled** when a round brings no new message, or **bounded** after 3 rounds or 10 agent messages (checked before each turn: the members still queued are then cancelled); a new message of the person's waits behind the running turn, then starts a new discussion, and the turns queued for the old one are cancelled.

**What lasts.** Messages, turns and each member's position (the last message of the group it has been given) are in the bridge's database; turns have ids made from the group, the person's message, the round and the member, so a retry does not run one twice. A turn running when the bridge stops is failed when it starts again, and the discussion ends there: `group.state` says `failed`, reason `bridge_restarted`, the members still queued do not run, and the person's next message starts a new discussion. The member's reply, if it comes yet (a plugin sends again what was not acknowledged), is kept as its message. A turn is recorded replied only once its reply is stored: a reply the bridge cannot store fails its turn, as if none came, and is kept when the plugin sends it again. `group.stop` cancels what is queued and requests `turn.abort` for the running member's exact original ingress when its plugin advertises `abort`; its reply, if it comes, is dropped. Unsupported plugins receive no native text command. `group.state` says where the discussion is, to every device of the owner, at `sync` and whenever it changes.

**How far a conversation was read** is the bridge's too, not the runtime's: the agent does not see what the person reads in the app. A device sends `conversation.read` when the person opens the conversation or reads a message arriving in it; the bridge keeps the highest `seq`, from the conversation's owner only and never past its newest message, and sends the `conversation` again to all of the person's devices. A device that syncs, a new one or one that was away, so counts as unread only the agent's messages after `read`.

### Archived conversations

Archiving is the bridge's conversation metadata ([ADR 0049](adr/0049-conversation-archives-belong-to-the-bridge.md), proposed), independent of the runtime's own session state. A device sends `conversation.archive` with `archived: true` to set a conversation aside or `archived: false` to restore it. The boolean is required; replaying either value is idempotent. The bridge accepts only the conversation's owner and stores the value. On success it sends canonical `conversation` metadata directly to the requesting device before the `ack`, including an idempotent retry; changed state is also broadcast to all of that person's connected devices. Another person's conversation and an unknown id both receive `not_allowed`.

The `conversation` metadata has optional `archived` (`true` when archived, false when absent) and `revision` (a nonnegative integer, 0 when absent). The bridge advances the revision when the name, read position or archived state changes, and when it publishes group members or claims Home ownership. Devices persist the highest revision with the metadata and ignore a lower revision, whether it arrives in a broadcast or sync response, so delayed delivery cannot restore an older state. Earlier bridge databases gain archived=false and revision=0 for existing conversations. Every sync sends all conversation metadata, regardless of `since` and archived state, then the requested history. Older apps may ignore the field and keep listing the conversation; archive controls need an updated bridge and app. Revisions, like `seq`, assume the bridge's database is never reset or restored from an older copy: a device that kept a higher revision for an id the new database reuses (a Home's, `home.<sandbox>.<agent>`) ignores its metadata, and one that kept a forgotten Home's deletion ignores that Home for good, until the person clears the app's cache. The protocol has no database identity to detect that yet. A storage failure answers `internal` with a generic message; the database's own error stays in the host's log.

This operation keeps the same id, title, read position, messages, attachments and group members. It applies to ordinary direct and group conversations. Home cannot be archived: `archived: true` for Home receives `not_allowed` without changing its metadata or broadcasting a change. This uses its stable Home identity, not its title, so renaming Home does not bypass it and an ordinary conversation named Home remains archivable. A Home a development build archived is restored when the bridge opens its database, with a new revision. Home remains the runtime's home channel under the same id. New messages continue to be stored and delivered without clearing an archived conversation's flag, and archiving does not cancel a group's work. A request that waits for the person, an agent's `question` or a runtime approval of a command, is the exception: when the bridge stores one for an archived conversation, it clears the flag, advances the revision and sends the `conversation` to the owner's devices before the request, so it shows in the active Inbox. No archive message or command reaches the plugin leg: Hermes and a future OpenClaw plugin need no archive-specific method. The runtime's saved memory, context and own archive flags are unchanged. The app filters active and archived views and restores visibility only on an explicit Unarchive.

### Questions

[ADR 0052](adr/0052-questions-keep-their-runtime-waiter-and-structured-app-controls.md), proposed. Questions are structured conversation controls backed by a runtime's existing waiting call (Hermes: `clarify`). Ordinary markdown lists remain ordinary messages. The channel advertises `questions` only when both its native adapter and the bridge's hello support it. A missing bridge capability list means text fallback; no version bump is required for these optional types and fields.

An ordinary question definition is `{id,text,choices,multiple}`: an immutable opaque id, nonblank question text, ordered string labels, and a multiple-selection flag. Choices default to empty and multiple defaults to false; an empty choice list asks for free text. There are at most 12 choices and at most 24 KiB of serialized definition JSON. Labels remain whole and in order, are distinct, and are one line each. Neither the text nor a label holds a hidden character: a control character other than a newline in the text (so no CR or tab), a bidirectional mark, embedding, override or isolate, a zero-width or other default-ignorable character (soft hyphen, tag characters, variation selectors), a line or paragraph separator, or a blank filler (enclos-protocol's `visible` rule, which the app and the channel apply too). The joiners U+200C and U+200D and the emoji variation selectors U+FE0E and U+FE0F are text between two non-ASCII characters (Persian spelling, joined emoji) and hidden anywhere else. Two labels are distinct once joiners are set aside, so a label cannot read as another. A native question outside these bounds uses readable, bounded text fallback instead of losing choices. Optional `approval` metadata is reserved for the separate [runtime approval](#runtime-approvals) contract below.

Answers are `{kind:"choices",indices:[0,2]}`, `{kind:"text",text:"..."}` or `{kind:"skip"}`. Indices are zero-based, distinct and within this definition, with exactly one for a single-selection question; a multiple selection is stored and forwarded in ascending definition order. Other/custom text is available alongside choices. An answer has at most 8 KiB of serialized JSON. Empty text and hidden characters other than a newline are refused, including NUL-prefixed runtime sentinel strings; the app sends a pasted CRLF as a newline. The plugin maps the typed Skip action to its runtime's own sentinel.

Canonical metadata has the definition's flattened fields plus `conversation`, requesting `agent` (`sandbox/agent`, including in groups), `state`, nonnegative `revision` and optional `answer`. Ordinary question states are `pending`, `answered`, `skipped`, `expired` and `cancelled`. Only `answered` has an answer, which is a choice selection or text; other states have none. An `answered` question may have none too: the runtime took an answer this contract cannot carry (text typed in the composer that holds a hidden character, say), and the agent has it. Optional `confirmed` (false when absent) is true when the settlement is the one a paired device submitted, matched by its request; a state the channel reports on its own is unconfirmed, and the app shows it as the agent's report. Revisions fit the signed 64-bit storage range, and terminal state cannot reopen. Full metadata is bounded to 48 KiB. Metadata and readable message text travel in separate frames, each within the device transport budget.

The plugin persists `question.ask` and `question.update` in its acknowledged outbox. The bridge atomically creates the question and a readable fallback history message with `kind:"question"` and its question id. Terminal settlement atomically advances the revision and appends a quiet `kind:"status"` message with that id, so incremental history sync observes completion. That message says "Answered: …" only when the answer is the one a paired device submitted, matched by its request; an answer the channel reports on its own (a reply in the composer, or a plugin that claims one) reads "Answered, as the agent reports: …". Repeated asks cannot alter a definition or duplicate history. The bridge refuses an ask (`bad_message`) when its conversation already has 4 pending questions or its agent 32, so pending refreshes stay bounded, or when it cannot save it; the channel then sends the question as text. A stored question that no longer passes these rules (one an earlier bridge wrote before a rule was tightened) is left out of every sync and closed as expired by its agent's next terminal update. Repeated or stale unsolicited terminal updates retain the first terminal result and are acknowledged. The bridge sends current `question` metadata before every live or synced history message that references it; old apps ignore the optional metadata and use the readable text. Every device sync refreshes current pending-question metadata regardless of `since`. Only a sync with `open_items:true` also refreshes the newest 256 unclosed expired ordinary questions asked within the last 30 days, even when their introduction is older than its cursor. Historical unreadable rows are omitted and logged; database read errors still report discovery unavailable.

Only the current conversation owner on a still-paired device may submit `question.answer`, at the current revision while pending. The bridge checks the input and a live matching origin plugin, then sends a distinct correlated `question.answer` to it. The plugin checks the saved native entry identity, session key and conversation before resolving that exact waiter. It never converts the response into `message.in`, a new turn or the next pending question. A group question must originate from one of its members. Unknown and foreign controls give no existence distinction. Question answers change no sandbox policy and execute no host command.

An exact native receipt and persisted canonical result produce `question.result` with the device request's `of`; an ordinary metadata broadcast is not a receipt. Two-device races keep the first native answer. A differing terminal result is a conflict; matching unsolicited metadata may update the card while its exact receipt remains pending. A refusal before the answer is written to the channel (the agent disconnected, or too many answers in flight: 16 per person, 256 in all) is `agent_unavailable`: nothing was sent and answering again is safe. Disconnects after sending and timeouts (25 s) are ambiguous, `unconfirmed`, and never automatically resend. The app keeps the newest host-scoped revision, disables closed/offline/pending cards and refreshes ambiguous pending state at reconnect sync.

On plugin reconnect, the bridge reconciles pending ids in `question.sync` batches of at most 128 for that authenticated agent. The plugin reaffirms live entries, replays settlements and expires missing entries. An orphan ask replayed from a previous process is followed by retirement too. A channel that reconnects without the `questions` capability cannot answer its cards: the bridge expires them at once. The bridge also expires, within a minute, the pending questions of an agent it no longer serves, and those of an agent whose channel has stayed away for two hours (twice the hour enclos gives Hermes's `clarify`): no runtime still waits for them. Hermes's waiters live in memory: runtime restart does not recreate them. The adapter calls `get_pending` / `resolve_gateway_clarify`, observes retirement and handles `retire_clarify_card`; closing the channel cancels a waiting question in Hermes too, and an entry it can no longer read cancels its card. A runtime without these functions keeps text fallback, and says so in its log. The plugin does not mark a card's entry as awaiting text: an option's number or text, or "skip", typed in the composer answers it, and other prose cancels it and reaches the agent as a message; in a group, a message waits behind the running turn, so the card is the way to answer. Hermes batches arrive sequentially, one question card per native waiter. Its registered `enclos:app-questions` skill and short channel hint teach the agent to use `clarify` with choices and wait for the actual result.

Hermes's command confirmations (`BasePlatformAdapter.send_slash_confirm`, for `/new`, and its alias `/reset`, and `/undo` while `approvals.destructive_slash_confirm` is on, `/reload-mcp` while `approvals.mcp_reload_confirm` is, and a `/model` switch Hermes's guard warns about) are shown as question cards too, with no new message or field: a command confirmation is the runtime's own prompt, not an agent's question, and the card carries it over the same transport. The text is Hermes's prompt, without its paragraph naming `` `/approve` `` (the typed replies its own text offers) and its hidden characters, followed by the plugin's note that Hermes asks before it runs the command, that this is not a runtime approval and changes no access, and, when Always is offered, that Always turns the confirmation off in the agent's settings, so Hermes does not ask it again. The choices are `Approve once`, `Always` and `Cancel`, in that order; for `/model`, Hermes treats Always as Once and writes nothing, so its card has no Always. The plugin binds the card to Hermes's exact pending confirmation (`tools.slash_confirm`: the session key Hermes uses and the confirm id) and wraps its handler through Hermes's own `register`, with the same id, command and authority, to learn which choice ran it. An answer resolves through `tools.slash_confirm.resolve`, as Hermes's button adapters do: a choice as its own word (`once`, `always`, `cancel`), Skip as `cancel` (`skipped`), and text as Hermes reads a typed reply (`_SLASH_CONFIRM_CMD_CHOICES`, then `approval.inputs.confirm_*` in English and the active language), or `bad_message` when it reads none or the card does not offer it. The command runs beside the connection; when Hermes's resolver returns its reply as text (a `/new` or `/undo` reply included), the reply follows as a message once the card has settled. When two answers race, the one Hermes ran keeps its receipt and the other gets the card's state. Always makes Hermes write its opt-out (`approvals.destructive_slash_confirm: false`, or `approvals.mcp_reload_confirm: false`) to the agent's `config.yaml`, which Hermes reads before each such command; enclos leaves those two keys out of the settings whose change restarts the gateway ([ADR 0069](adr/0069-an-agents-model-is-changed-through-its-runtimes-channel.md)). A reply typed in the composer settles the card unconfirmed, with the choice it ran: Hermes reads it when no turn runs, and the plugin when one does and the reply is one of Hermes's approval words (`yes`, `always`, `cancel`...), which it keeps from Hermes then (see [Runtime approvals](#runtime-approvals)). A confirmation Hermes drops (a session reset, a newer one for the session) cancels its card, one past Hermes's five minutes, by the plugin's clock, expires it, and closing the channel drops it with its card. Where no card can show a pending confirmation (a bridge without `questions`, one that refuses the card, a card outside the bounds, a confirmation that cannot be bound), the plugin sends it as its own text, ending "Reply yes, always or cancel." ("yes or cancel" for `/model`), and tells Hermes it was shown, so Hermes's own text, which names `/approve`, is not sent; only when that text cannot be sent either does Hermes send its own. A typed `/approve` or `/deny` sent while a confirmation waits and no runtime approval blocks is still refused, with that way to answer instead. A Hermes without `send_slash_confirm`, or without `register`, `get_pending`, `resolve` and `clear` in `tools.slash_confirm` (said once in the log), keeps Hermes's own text.

### Open items

Optional device capability `open_items` provides discovery across the person's conversations on this host. A device opts in with `sync {since,open_items:true}` on each connection; old syncs receive no new frames. `open_items {revision,reset,complete,unavailable?,items}` carries a full host snapshot in chunks of at most 24 entries, each encoded envelope within the Noise budget. Every snapshot has one person-scoped increasing revision, starts with reset and ends with complete; a bridge restart may reset its sequence, so authentication resets the device's sequence. A device atomically replaces only that host's rows after a complete snapshot. Empty successful snapshots remove its rows. `unavailable:true` retains cached rows and shows a refresh error; partial or malformed snapshot envelopes must not clear the cache. An unreadable or future-kind item is omitted and logged without discarding the other valid items; the 8192-item input limit includes omitted items. At most 8192 entries are supported; an over-limit projection reports unavailable.

Each item is `{id,kind,agent?,conversation?,summary,since,expired,waits_on?}`. Kinds are `question`, `runtime_approval`, `held_task`, `policy_request`; kind and agent scope the source id. A `held_task` item always carries `waits_on`; a device omits the row when it says `team`, every other kind has none, and an absent or unknown value reads as `person`. `summary` removes hidden characters, collapses whitespace and is limited to 300 characters. Ordinary questions belong to the conversation owner; runtime approvals, held tasks and policy requests additionally require the current host's person. The bridge reads the canonical sources under one database read transaction and publishes refreshed snapshots to opted-in, currently paired devices after source changes. These entries confer no action authority and have no independent native state.

Pending ordinary questions and at most the newest 256 expired unanswered ordinary questions asked within the last 30 days are included, excluding per-person closures. Expired runtime approvals are excluded. A terminal ordinary question remains natively terminal. Expired requests are read-only: apps offer no answer, skip or late-reply draft, and may offer View conversation and Dismiss reminder. Neither action answers the old waiter or injects a late reply into a newer native question.

Legacy optional `question.close {question,revision}` remains for compatibility; current apps use Dismiss reminder instead. It is a separate discovery action for an expired ordinary question. It requires the still-paired conversation owner and exact current revision. An immediate transaction records a per-person closure without changing question state, revision, answer or conversation history. It is idempotent and returns `question.closed {of,question}` for that exact device request, then disappears from subsequent open-item snapshots, including on other devices and after restart. Pending questions and runtime approvals cannot be closed by this message. Capabilities `open_items`, `question.close` and `suggested_replies` are announced in authenticated metadata.

Optional `open_item.dismiss {kind,item,agent?,version}` hides one exact reminder for its person. `version` is the opaque source generation carried by each open item. The bridge rechecks both pairing keys and the canonical source visibility in an immediate transaction, rejects unknown/foreign items and stale generations, then stores a per-person dismissal separately from native request state. An exact receipt is `open_item.dismissed {of,kind,item,agent?,version}`; subsequent complete snapshots omit that generation across devices and restarts. This never answers, approves, denies, resumes, cancels or edits work. Held revision changes and policy revision/state changes reappear; an ordinary question's expiry alone does not. The optional `open_item.dismiss` capability is advertised in authenticated metadata.

`held_task.get {agent,task}` is a read-only task detail request for the host's person, requiring current pairing keys and the exact owned held reference kept by the bridge. Authenticated capability `held_task.get` and creator plugin capability `held_task_details` gate it. The plugin leg uses `task.get {task,held:true}` with that exact opaque reference (including its board prefix), answered using the existing correlated `task.detail`/error. No bare-id or alternate-board fallback is allowed. Ordinary `task.get` stays unchanged. Hermes reads only that board's task created by this profile, never mutating the board. Details stay in memory for the request; current host ownership and both pairing keys are checked again before delivery.

A bridge advertising `held_task.board` can answer `held_task.board {agent,task,revision}` with `held_task.board.link {of,path}` for the host's person on a still-paired device. The request names the exact currently held card and revision. The bridge audits the request as `held_task.board` and returns a path of the form `/task-board/open#<ticket>`, where the ticket is 43 unpadded base64url characters. The app matches `of` to the tap and opens the path on the paired bridge's HTTPS origin. The ticket expires in a minute and is exchanged once by the browser on the same transport node as the paired device. The browser waits up to 24 seconds for the dashboard to start. The browser session expires after 15 minutes.

Each board request checks the browser session cookie, the transport identity, the current pairing keys and host person, and the agent. A GET may reuse a transport lookup for up to 10 seconds within the browser session, keyed by the normalized node address and login from the trusted proxy. Ticket exchange and writes require a fresh transport lookup and matching HTTPS `Origin`. The held reference selects the Hermes board and task. The bridge adds a script to the Kanban page that seeds that board and, once the board has drawn the task's card (its `data-task-id`) within 30 seconds, taps it once, which opens the task's details; an id that is not a path component (letters, digits, `-`, `_`, `.` and `@`, not `.` or `..`) is not written into the page, which then opens on the board. Reads are scoped to the board for the life of the browser session. Before forwarding an allowed task update, comment or specification, the bridge checks that the exact card is still held. The current revision may differ from the opening revision. It records `held_task.board.write` with the person and device before forwarding to Hermes, which applies its own rules. See [ADR 0070](adr/0070-paired-devices-open-a-held-tasks-board-through-the-bridge.md).

### Suggested replies

Optional `suggested_replies` on plugin `message.out` and device `message` is an array of at most four distinct nonblank, visible single-line strings, each at most 256 UTF-8 bytes. Distinctness uses the question visible-text rule. Invalid optional metadata is ignored without rejecting the message. The bridge stores it atomically on the last piece of a split ordinary message and repeats it on history sync; duplicate delivery cannot replace stored replies. Status messages do not carry it. An older peer ignores the field.

A device offers each literal label as an ordinary `message.send` in the same conversation, disabled offline or while a send awaits its receipt. Any later person message retires those buttons. This is no structured question or runtime/policy approval. Hermes's `suggest_replies` tool stages the labels for its next ordinary message in the active conversation turn, at most five minutes; a newer inbound message invalidates abandoned metadata. Status notices and native approval text do not consume it. The bundled app-questions skill asks for one or two simple explanatory sentences and short selectable choices, keeping internal reports out of the digest. Notification actions are not included.

### Runtime approvals

[ADR 0053](adr/0053-runtime-approvals-use-exact-native-requests-and-explicit-scopes.md), proposed. A runtime approval uses the same durable `question.ask` / `question.update`, device `question` / `question.result` metadata and `question.answer` control path, with a distinct `runtime_approvals` capability on both bridge and plugin hellos. `questions` alone does not enable it. The introduction has `kind:"runtime_approval"`, so an older app displays its readable fallback, which decides nothing, rather than ordinary question controls. An ordinary message asking for `/approve` never gains inferred buttons.

The immutable definition adds `approval: {command,reason,actions,smart_denied,patterns?,scopes?}`. `command` and `reason` are the native runtime's display fields, not raw execution data; `text` is a short heading, `choices` must be empty and `multiple` false. `smart_denied` defaults to false. Actions are distinct canonical values in the order `once`, `session`, `always`, `deny`; Deny is required, and a set beyond Deny alone also requires Once. Without the independently negotiated scopes below, Always requires Session. A smart denial permits only Once/Deny or Deny alone. For legacy approvals, `patterns` names, in the runtime's own words, what a session or always grant covers: every command matching one of them, not this command alone. It is required when Session or Always is offered and absent otherwise: at most 16 distinct nonblank strings without hidden characters. A runtime that cannot name them offers neither (Hermes keeps Once and Deny). Preserve the runtime's final offered set, including Deny-only when full-command delivery failed. Existing control-character and 24 KiB definition / 48 KiB metadata bounds apply. The complete command is shown in full and wrapped, with every hidden character (enclos-protocol's `visible` rule: a control other than newline, a bidirectional mark, embedding, override or isolate, a zero-width or other default-ignorable character such as a tag or variation selector, a line or paragraph separator, a blank filler, and a joiner except between two non-ASCII characters) written out as `⟨U+XXXX⟩` and a tab as `⟨tab⟩`, and flagged when it holds a character outside ASCII; written out that way it must still fit 24 KiB. The bridge's readable introduction follows the same rule. Oversize or unsupported native prompts use bounded full text fallback, without shortening the command or widening actions.

**Independent native scopes** ([ADR 0056](adr/0056-native-approval-scopes-are-explicitly-negotiated.md), proposed) additionally require `runtime_approval_scopes` on the bridge and plugin hellos. The immutable approval then supplies `scopes: {description,fallback}`: nonblank literal native persistence/scope explanation and complete native answer instructions, together at most 8 KiB encoded. This opt-in permits Always without Session while retaining canonical ordering, Once/Deny and smart-denial restrictions. It does not invent a Session action or drop a native Always action. The app shows the supplied description instead of assuming every runtime grants Hermes command patterns. Readable history includes the full command/reason, every offered action label and native instructions; it never fabricates Hermes `/approve` syntax for this extension.

A device opts in per connection with `capabilities:["runtime_approval_scopes"]` in its Noise-encrypted `auth`. The optional field defaults to empty; an older bridge ignores it. The bridge sends extended structured question/receipt metadata only to an authenticated device that advertises this capability, on live delivery and sync, and refuses structured answers from devices that did not opt in. All devices still receive complete readable history. A pairing connection without this declaration retains fallback until its next authenticated connection. Capabilities are not persisted with the pairing. An older bridge does not announce the plugin extension, so a supporting plugin keeps native text fallback and does not send an extended definition. Retained independent-scope records require a compatible bridge/cache reader for rollback; older validators may reject Always without Session. No automatic database restore or history deletion is performed.

The only valid answer is `{kind:"approval",action:"once"|"session"|"always"|"deny"}`, and the action must be offered. Ordinary choices, text and Skip cannot answer a runtime approval; an approval action cannot answer an ordinary question. An accepted action uses `state:"answered"` with that typed answer, including Deny. `pending`, `expired` and `cancelled` have no answer. New terminal `resolved` also has no answer and is valid only for runtime approvals: the native runtime reports a decision made elsewhere without disclosing which action won. It cannot confirm this device's submission. `skipped` is invalid for approvals. Terminal state cannot reopen.

Structured app decisions require a still-paired device, the current conversation owner **and the host's own person**, refusing an unknown host identity, and go to the plugin signed (below). Origin membership, revision, offered-action validation, live plugin capability and exact connection/request fencing apply. Accepting a decision is not proof of execution or completion. The runtime guard continues under the existing sandbox policy; only its native code owns session pattern grants and persistent profile allowlists. This control neither changes enclos policy nor runs a command on the host. It is distinct from the sandbox policy inbox's `approval` capability. All structured decisions, including Deny, require an explicit action and are never queued or automatically resent. An approval the runtime resolved meanwhile, or no longer has, answers `conflict`: this decision changed nothing. Typed approval commands decide nothing ([0060](adr/0060-the-bridge-signs-runtime-approval-decisions.md), proposed, which replaced the rule that passed the host's person's on): a runtime reads them from whoever the plugin says speaks, and a message carries no proof of its person. A `message.send` whose text a runtime reads as `/approve`, `/deny`, `/yolo` (no approval for the rest of the session) or `/approvals` (sets the approval mode, `off` included), in any case, with arguments or an `@name` suffix, after leading `@image:`/`@file:`/`@url:` lines and whitespace as Python reads it (U+001C to U+001F included), gets `error` `not_allowed` from the bridge, from anyone, the host's person included, and is neither stored nor relayed. The plugin reads every `message.in`, whatever its `host`, with its runtime's own command parser and aliases (Hermes: `MessageEvent.get_command` and `resolve_command`), and answers an approval command itself instead of passing it on, so a parser difference between the bridge and the runtime, or a message the agent sends its own plugin, opens nothing. A bare word decides too, in Hermes: while a runtime approval blocks the session key Hermes uses for the conversation (`tools.approval.has_blocking_approval`), its gateway reads a message that is only one of its approval words (`approval.inputs.approve`, `deny`, `always` and `session`, in English and the active language, and 👍 and 👎, compared after `.strip().lower()`) as `/approve [always|session]` or `/deny`, and runs it. Hermes reads a message some time after the plugin hands it over (in `busy_input_mode: queue` it holds a burst of text up to a second first), so the plugin cannot tell from whether an approval blocks when it looks whether one blocks when Hermes reads. It therefore takes as approval words those of every language Hermes supplies, since an agent's profile may set another language than the gateway's (the English list when they cannot be read, said once in the log), and, for such a word: while an approval blocks the session, it refuses the message itself, answering that the app's buttons decide, and acknowledges it; while a turn runs in the session (Hermes's adapter guard, `_active_sessions`, or its runner's `_is_session_running`), it answers a pending command confirmation with it, read as Hermes reads a reply, and otherwise hands the word over with `allow_gateway_control` false, which Hermes's route requires, so that it is an ordinary message, never a decision; when no turn runs, it passes on untouched. The session keys are the runner's own (`_session_key_for_source`, with which Hermes sends this conversation's runtime approvals), those the adapter derives (`_event_session_key`) and the plugin's. The cost: while a turn runs, such a word typed as a reply to a question (`clarify`) is an ordinary message, and the question's card is the way to answer it. The bridge does not refuse these words: it cannot tell whether an approval waits.

**Signed decisions.** The bridge signs each runtime-approval decision it sends with a P-256 key of its own, `app-approvals.key` in enclos's data folder (`0600`, made by the first command that needs it, hidden from every sandbox), which signs nothing else but the host's person's messages below, under another label. The statement is each of these fields' UTF-8 bytes after their length as 4 bytes big-endian: the label `enclos/runtime-approval/1`, the agent (`sandbox/agent`), the conversation, the approval's id, the `question.answer`'s `id`, the action, the approval's `command`, `reason` and the number of its `patterns` in decimal followed by each one, and the signing time in decimal seconds since the Unix epoch. The answer carries `signed: {at, sig}`: that time, and the ECDSA P-256 SHA-256 signature, `r` then `s`, 64 bytes in base64url without padding (`enclos_protocol::decision`, with the fixture `tests/fixtures/decision/approval.json`). `runtime configure <sandbox>/<agent> --channel app` gives the plugin the public key, SEC1 uncompressed in base64url (Hermes: the setting `MOBILE_APP_BRIDGE_KEY`); the bridge's `hello` carries none, as anyone with the token can send one. Before it resolves a native approval, the plugin checks the signature with that key over the statement rebuilt from its own card (its id, conversation, command, reason and patterns), its agent (`ENCLOS_SANDBOX` and its socket's name), the answer's `id` and action, and that `at` is at most 60 seconds old and 5 seconds ahead. Any other decision, unsigned, forged, altered, stale or meant for another approval, gets `error` `not_allowed`, is logged, and, while its approval waits, the plugin denies it and reports that as the agent's (`answered`, Deny, no `of`). A decision for a closed approval changes nothing. A plugin without the key, or without the `cryptography` package Hermes ships, offers no `runtime_approvals`. The plugin, its settings and the runtime are in the sandbox home, which the agent writes: the signature stops a program that speaks on the plugin's socket, replays a decision or alters one on the way, not one that rewrites the plugin or the runtime (0060's trust assumption).

**Signed messages of the host's person** ([0077](adr/0077-the-hosts-person-speaks-to-openclaw-with-its-owner-authority.md), proposed). When the bridge gives a plugin a message the host's person sent from a paired device in a direct conversation (Home included) with no attachments, it signs it as it sends it, with the same key: the statement is the label `enclos/host-message/1`, the agent (`sandbox/agent`), the conversation, the `message.in`'s `id`, the person, the text and the signing time, encoded as above, and the message carries `signed: {at, sig}` (`enclos_protocol::decision::HostMessage`, with the fixture `tests/fixtures/decision/host_message.json`). A group turn, another person's message, `enclos app chat`'s and one with files are never signed; the labels keep a signed message from reading as a decision, and the reverse. OpenClaw's channel checks the signature over the message as it received it, on receipt, with the 60 and 5 seconds above, and passes a message that verifies to OpenClaw from the sender `host`, which `runtime configure --channel app` names in `commands.ownerAllowFrom` as `enclos:host`, keeping the sandbox's other owners; by OpenClaw 2026.11.5's source, that sender then has its owner-only tools, such as `automations`, which a running gateway is still to show (design §14). Any other message keeps its person as its sender, and an unsigned one whose person is `host` (in any case, trimmed) gets `error` `not_allowed` before it binds a route; `enclos:host` is refused alike. A signature that does not verify is logged and the message passed on as its person's. The message's receipt makes its id count once. The Hermes plugin ignores `signed`.

An approval in a conversation the host's person does not own could be answered by no one: the bridge refuses its `question.ask` with `not_allowed` and stores nothing, and the channel denies the native request at once and says why in the conversation, rather than leave the runtime waiting out its timeout. Any other approval no card shows (an ask the bridge refuses, a definition outside these bounds, a bridge or runtime without the capability) goes as text that shows the whole command and says the app cannot decide it: the channel denies it at once where the runtime resolves its exact request, and the runtime's timeout denies it otherwise. At most 4 runtime approvals wait in one conversation and 32 of one agent; the bridge refuses more (`bad_message`), so pending approval refreshes stay bounded. A channel that connects without `runtime_approvals` cannot answer the approvals it left: the bridge expires them. The history says a consent was given ("Runtime approval: allowed once.") only for the action a paired device submitted, matched by its request; an action the channel reports on its own reads "…, as the agent reports."

Hermes uses `_send_exec_approval_prompt(ExecApprovalPrompt)` while retaining its base whole-command visibility flow. The adapter saves the prompt's exact `request_id`, session and conversation, registers an additive `observe_gateway_settle` callback and calls only `resolve_gateway_approval_card` with that id. It never infers identity from command text, the oldest queue entry or session alone. Missing/stale ids resolve nothing. Native actions stay restricted when full-command delivery failed. An own exact resolver success, on a signed decision, can produce the action receipt; a settlement made elsewhere (the runtime's own surfaces) closes neutrally as `resolved`. Timeout maps to `expired`, interruption/teardown to `cancelled`. Reconnect/restart use the existing durable reconciliation; old native waiters cannot be recreated. Feature detection keeps the text fallback, which decides nothing, on older Hermes or bridges. [Pinned source findings](research/hermes-command-approvals.md) record the required APIs and their compatibility limits.

Client fallback does not imply binary downgrade compatibility: once a bridge stores an `approval` answer or `resolved` state, the preceding question-only binary cannot deserialize those linked records during history sync. Retained approval data needs an approval-aware bridge reader; an operational rollback needs a compatible reader or a pre-feature database restore. No down-conversion or history deletion is automatic.

Structured approval controls bypass a running group's queue of ordinary messages and work for a member's exact request; older group clients need a supporting app and bridge.

### Sandbox creation and runtime installation

Only the host's person, authenticated on a still-paired device, may use these messages. Authority uses the stored host identity established by the first pairing accepted at the terminal or changed with `enclos app host`; it is checked on every request. Until the host has a confirmed person, provisioning is unavailable. `authenticated.capabilities` includes `sandboxes` for eligible devices; older bridges omit it.

| `type` | From | Fields | Meaning |
| --- | --- | --- | --- |
| `sandboxes` | device | (none) | List the host's sandboxes, including those without a runtime or app channel |
| `sandboxes.list` | bridge | `sandboxes`: `[{"sandbox":"lab","runtime":null,"state":"created"}]`, a sandbox with a runtime also `runtime_version`?, `runtime_release`? (`{version, checked}`) and `runtime_outdated`? | Runtime is its identifier or `null`; state is `created`, `running`, `stopped` or `failed`; versions as below |
| `runtimes` | device | (none) | List runtimes this host knows how to install |
| `runtimes.list` | bridge | `runtimes`: `[{"runtime":"hermes","name":"Hermes","description":"…"}]` | The runtime catalog; currently Hermes |
| `sandbox.create` | device | `sandbox`, `template` (required: `minimal` or `assistant`) | Create with the backend `sandbox create` takes when none is named (the configured default, else the first available) and the existing engine checks |
| `runtime.install` | device | `sandbox`, `runtime` | Install using the runtime's own noninteractive installer, inside the sandbox |
| `operation.progress` | bridge | `of`, `operation` (`sandbox.create` or `runtime.install`), `sandbox`, `message` | The request identified by `of` is running; milestones only, no raw installer output |
| `sandbox.created` | bridge | `of`, `sandbox` | Creation completed |
| `runtime.installed` | bridge | `of`, `sandbox`, `runtime`, `login` | Installation completed; `login` is the remaining host setup command, e.g. `enclos connect lab -- hermes setup` |

**Runtime versions** (proposed, [ADR 0074](adr/0074-a-sandboxs-runtime-is-updated-on-request-and-restarts-at-once.md), issue #335). `runtime_version` is the version of the sandbox's runtime installed, as `enclos status` shows it, left out when the host does not know it. `runtime_release` is the runtime's latest release, the one its installer installs by default, the same for every sandbox of that runtime: `version` and `checked` (this host's enclos was checked with it). It is left out when the host has no release to tell: none kept, its lookups failed with none found before, or lookups are off. A failed lookup keeps the release found before. `runtime_outdated` says whether that release is newer than `runtime_version`, left out when the host cannot tell, such as when it does not know either. The bridge answers `sandboxes` at once with what it has kept of each runtime's latest release, however old; when that is missing or older than its keep time, it looks the releases up on a thread of its own, one lookup at a time, which can take up to 10 seconds a runtime, then reads the sandboxes and sends a fresh `sandboxes.list`, with no `of`, to the host's person's connected devices, unless it does not fit one message. A lookup that fails, or releases it cannot keep, are written to the bridge's log (`enclos app log`), and the device keeps the list it has. A device shows a newer release next to the version installed, with whether this enclos was checked with it. Older devices ignore these fields.

The bridge sends completion or an `error` with the request's `of`, then a fresh `sandboxes.list` to the host's person's connected devices. Only one provisioning operation per sandbox runs at once (`busy` otherwise). Operations continue if the phone disconnects; they are not replayed on reconnect. A new `sandboxes` request reads the resulting host state. Requests with invalid names, runtimes or templates get `bad_message`; engine and installer failures get `operation_failed`, in their own words, on one line and cut to 2,000 characters so the error fits one device-leg message. No installed runtime is recorded until its installer succeeds. Existing engine checks still refuse pending policies, another installed runtime, and unrelated policy edits that require host review. Runtime login, app channel setup and service startup remain host operations, and the app says so. Existing mobile policy review and editing are unchanged.

Each request and its completion is logged with its device and person in `enclos app log`, with a failure's reason as the phone was told it. The engine's audit log names the person and device behind each creation and installation, as every audit entry the bridge causes does: `<person> (device <id>)`, on the host's name (a policy request's decision adds `, request <id>`). The installation's CLI child is told whom with `runtime install --requested-by=<who>`, a hidden option, so its entry does not name the host's user, who runs the bridge. A runtime install has no terminal or stdin; stdout is a bounded CLI JSON result and installer stderr is discarded, never forwarded to the phone. An install still running after an hour is stopped by the CLI child itself, which the bridge runs with `runtime install --time-limit=3600`, a hidden option: every process of the installer's session, whatever its process group, is sent TERM, then KILL 30 seconds later, and so is what they left running; the session's end is recorded, and the install is undone as after an installer that fails. The `operation_failed` error says so, in the CLI's words. A CLI child that has not exited 5 minutes after that hour is sent TERM, then KILL 30 seconds later, with its process group: what the installer started may then still run, its session stay open and the runtime's destinations stay in the sandbox's policy with no runtime recorded, and the error says to check the sandbox on the host. Once a new agent's app channel is set up on the host, a running bridge lists it within seconds, with no restart.

### Host audit

The bridge advertises `audit` only to the host's person, as recorded by pairing or `enclos app host`. Each request rereads that identity and the device's paired identity and keys; another person, unknown ownership or a revoked device receives `not_allowed`. A read failure returns a correlated `internal` error with fixed guidance; database details and host paths are logged only on the host.

| `type` | From | Fields | Meaning |
| --- | --- | --- | --- |
| `audit` | device | `before`? (entry sequence) | Newest audit entries first; only entries with a smaller sequence when `before` is given |
| `audit.list` | bridge | `of`, `entries`, `next_before` (sequence or `null`) | Up to 25 entries, bounded to fit one Noise message; use `next_before` to request older entries |

Each entry has `seq`, `time` (Unix seconds), `user`, `host`, `command`, `target` (or `null`), `result` (`ok`, `failed`, `unfinished`), `message` (or `null`) and `finished` (Unix seconds or `null`). Unfinished means no outcome was recorded, including a command still running. Text fields over 1 KiB are shortened with an ellipsis for display; full entries remain on the host. `of` correlates the page with its request. Reading entries does not verify the hash chain; `enclos audit verify` remains the integrity check. Older bridges advertise no `audit` capability and are not sent these requests.

### Notifications

The bridge sends through FCM's HTTP v1 API with a service-account key its host's user gives it with `enclos app push key` ([ADR 0065](adr/0065-each-host-sends-push-through-fcm-with-a-key-its-user-gives-it.md), proposed). Without one it sends no push, and a device gets what came at its next sync.

A device gives its FCM token at pairing (`pair.request`'s `push`), and with `push.token` at each connection and whenever it changes. The bridge keeps only a token of kind `fcm`, of at most 4,096 letters, digits and `-_:.`, given either way; it logs any other as `push token refused`. The same token given again keeps why the last push to it failed; a new one clears it.

When an agent's message is stored for a conversation whose owner has no device connected, or a question or a runtime approval is asked there while it waits for them, the bridge sends a push to each of the owner's devices that gave a token. A runtime's `status` line is not pushed, nor its [task event](#task-events): each waits, quiet, for the next sync. A device counts as connected until its session ends, so a device that goes to the background closes its connection, or nothing is pushed to it for up to the bridge's silence limit (75 s). A device unpaired, or that gave another token, while its push waited gets none. It is a high-priority data message, with no notification part of Google's, whose data are, all strings as FCM requires:

```json
{"v":"1","host":"<host name>","seq":"1234","preview":"<base64url: nonce ‖ ciphertext>"}
```

`host` is the name `enclos app serve` reads from its transport's address as it starts, as `enclos app pair` names the host in its links when given no `--url`; `host` when the address cannot be read, which `app serve` says. A device need not know the name: it opens a preview under the push's own `host`. `seq` is the message's (the last piece's, for a message stored in several). Pushes waiting together go once per device, the newest.

`preview` is XChaCha20-Poly1305 under the device's `push_key`, over `{"agent":"lab/main","conversation":…,"text":"<at most 120 characters>"}`, padded to 2,048 bytes (the byte `0x80`, then zeros) so its length does not tell the text's. The text is the message on one line, without hidden characters and with its markdown marks, which the app takes out. Its associated data are `v`, `host` and `seq`, so a preview opens only with the ones it was sealed with: one kept by the push service cannot come back under another `seq`. Google sees the host's name, a number and ciphertext of one size. The Android app (enclos-app; not yet tried on a phone, design §14) opens it with the `push_key` of each host it paired with, under the push's own `host`; it shows no notification for a preview that opens under none, and drops a `seq` it has already shown. It shows the notification, and fetches the message with `sync` over the tailnet when it can.

The bridge keeps what became of the last push to each device. When FCM no longer knows a token (`UNREGISTERED`), the bridge forgets it until the device gives a new one and logs `push token dropped`. When a push fails, `enclos app status` shows why for that device, until one goes through or the key is replaced or removed; the bridge logs `push failed` when the reason changes, and `push working` once one goes through again. Google's token endpoint refusing the key (400, 401 or 403) reads as a refused key; one that is unavailable (429, 5xx) says so, and nothing of the key.

Sending on its own (`kind: notify`) is not a capability: every runtime may, and a device shows such a message whichever runtime sent it. ## Usage

What an agent's model calls consume, as its runtime counts them ([glossary](../GLOSSARY.md): Usage), so the person can see an agent use a lot and look into why: a context that keeps growing, a cache that rarely hits, many calls for one answer. The record is the same whatever the runtime: token counts `input` (not read from or written to the provider's cache), `output`, `cache_read`, `cache_write` and `reasoning` (part of `output`), each a whole number, and each left out when the runtime does not count it, which is not 0. `enclos usage` reads the same counts from the runtime's own records on the host (design §11, Usage).

**In an app conversation.** A plugin that reports usage names `usage` in its `hello`, and sends a `usage` message only to a bridge whose own `hello` names it, so an older bridge never gets one it would answer `unknown_type`. One message is one model call of the agent's turn, or a few (`calls`), in an app conversation; `background` marks a call the runtime made on its own, such as a title or a summary of a long context. An app call whose conversation the plugin cannot tell is not sent. The bridge keeps a report only for a conversation of the plugin's own agent, or a group it is a member of, whose calls count under that member: it bounds each count to 2⁴⁰ and `calls` to 1,000, cuts `model` to one line of 120 characters with its hidden characters written out, adds the report to the hour it arrived in, for that conversation and agent, in its database, and passes the call and the conversation's new total on, live, to the owner's devices. Past a burst of 1,000 reports, it reads an agent's at 600 a minute, in a bucket apart from its messages', so a plugin in a loop fills neither the database nor the devices' queues and a long run of calls holds up no reply. A total it cannot read is logged on the host and left out of the `conversation` it sends, so a device keeps the one it has. The total reaches a device with the `conversation` at every sync, and the hours go when the conversation is deleted or its agent forgotten; the calls themselves are not kept. Sums never overflow: each stops at the most it can hold, and a window's sum past what the database holds is an error, never a wrapped number.

**Outside the app.** An app conversation is not all an agent does: a routine runs on its own, a person talks to it in the sandbox, another channel brings it chats. A plugin that names `agent_usage` reports the calls of these it sees too, as `usage.agent`, with where they came from (`source`, which the bridge does not keep yet) and no conversation, to a bridge whose `hello` names it, and only on the connection of the agent the call is for. The bridge keeps them by the hour under that agent, one row an agent an hour in a table of their own, at the same pace as `usage`, for 35 days, past the longest window, and forgets them with the agent; they reach no device live. It records which agents' plugins said they report them, as their last `hello` said. Only the host's person sees these calls, as they see the host: their windows count them (`outside`), and each agent's total says whether its calls outside the app are counted (`outside` on the agent), so that an agent whose plugin does not report them (an older plugin, another runtime) does not read as all it used.

**From the runtime's records** (issue #366). A plugin sees only the calls made in its runtime's gateway, and Hermes's board workers are processes of their own that the dispatcher starts (`hermes -p <profile>`): their calls never reach the plugin, so an agent busy on the board showed 0 calls in the app while `enclos usage` counted hundreds. For the host's person, the bridge therefore reads what `enclos usage` reads: the runtime's usage reader, run in each running sandbox as an exec session (recorded and audited as `usage session`, as the requesting device's person), over the last 35 days. It reads once at a time, and serves windows from that read for 2 minutes; a read that fails keeps the last one, and while one runs, another device's window gets the last read, or the plugins' reports, rather than wait. A sandbox's reader is stopped past 30 seconds, and that sandbox's agents count from their plugins' reports. A TERM, INT, HUP or QUIT the bridge receives during a read is passed on to the reader and, once the session's end is recorded, ends the bridge as it would have. A sandbox that is not running is not read, so that a usage page starts no proxy. Each agent whose records the reader read, and that lists hours (Hermes's reader does; OpenClaw's does not yet), counts from its records alone, in place of every row the plugin reported for it: its app conversations' calls included, which its records hold too, so nothing is counted twice, and that agent's total is marked `outside`. An agent the runtime has no records of is read too, and used nothing. Any other agent (its sandbox not running, its records unreadable, OpenClaw) counts as before, from its plugin's reports. Hermes keeps no time per call, only each native chat's last activity, so its reader lists an agent's usage by the hour that holds each chat's last activity, model and model provider, each chat counted whole there, as `enclos usage` counts a chat whole when its last activity is in its window: series place a long chat at its end, and a window, which starts on the hour, holds the chats `enclos usage --since` holds from that hour. Past 2,000 rows an agent, the reader sums each of the oldest hours in one row naming no model, whose cost is then unknown. Other persons' windows count their own conversations only, from the plugin's live reports, as before; live per-conversation usage is unchanged.

**Windows.** A device asks for a window with `usage.get`, `since` a time: the last 24 hours, 7 days or 30 days, say. The bridge answers `usage.report` with what each agent used in the person's own conversations, and for the host's person each agent's calls outside the app it counts, from the start of the hour that holds `since`, which it says, so a window is exact to the hour. Every person may ask, about their own conversations; the bridge names `usage` in `authenticated` once it answers.

**Series.** A device that wants to see when an agent used what asks for a series too: `bucket` an hour or a day, and `offset` its distance from UTC, at most 14 hours, so its days start at its midnight; hours are the hours whatever the offset, as the bridge keeps usage by the UTC hour. The bridge answers with the 8 agents that used the most in the window, each with its buckets that saw a call, oldest first, a point's `tokens` left out when the runtime counted none: a bar chart's worth for the last day by the hour, or the last month by the day. A bucket other than an hour or a day, an offset past 14 hours, or a window of more than 62 buckets (a week by the hour) is refused (`bad_message`), rather than answered in part. With series, the `agents` totals are cut to the 50 that used the most, still in name order, so that the whole report fits one device message; without, to 190 by name. A report with costs, whose rows are longer, is cut to 20 and 100. The bridge names `usage.series` in `authenticated` once it answers series.

**Cost.** A bridge that names `usage.cost` in `authenticated` prices what it reports (issue #343, design §11, Cost), to a device that asks with `cost`, or for one sandbox or agent: each agent's total has a `cost`, and `sandboxes` gives each sandbox's total and cost, every agent of it summed, listed or not, those of the 20 that used the most. A device that does not ask gets the report it always did, with as many rows. A cost is `usd_micros`, millionths of a US dollar for the paid tokens it has a price for, `included`?, the tokens on a subscription, `included_usd_micros`?, what those of them with a list price would cost if paid, `included_unpriced`?, those of them with no list price, and `unpriced`?, the paid tokens of a model the price list has no price for (never a subscription's, as before `included_usd_micros`), each left out when 0, which add up across agents, sandboxes and buckets. A device shows `usd_micros` and `included_usd_micros` together as the cost, saying what of it is included; a cost with `unpriced` or `included_unpriced` as at least that, or as unknown when nothing is priced, never as $0; and a subscription's tokens alone with no list price as included. A device that knows only the first three parts reads them as before. The bridge keeps each hour of usage by the model and model provider the plugin named (`model` and `model_provider` on `usage` and `usage.agent`), at most 8 of them an agent an hour, the rest under neither, and prices each hour as the host's price list says when the device asks: a price corrected later applies to past hours too, and an hour kept before the bridge kept models, or by an older bridge, or of a model the list has no price for, is unpriced. A device asks for one sandbox (`sandbox`) or one agent of it (`agent` too): the report then lists only those agents, the series of the 4 that used the most, the sandbox's total (not for one agent, whose hours are not its sandbox's), and, with a `bucket`, `sum`, the scope's usage over time with each bucket's cost, which a device charts as the cost of that sandbox or agent by day. An agent named without its sandbox, or a name empty or longer than 128 characters, is refused (`bad_message`). Like the counts, a cost guides and bills nothing.

**Hermes.** The Hermes plugin reports the calls of Hermes's `post_api_request` hook (the agent's own) and `post_auxiliary_call` hook (`background`), with the counts Hermes normalizes for every provider (`input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`). A call's conversation is found in the turn's session context, as for `tool`; outside the app, its agent is the profile whose home Hermes runs it in (`profile_name_for_home(get_hermes_home())`, Hermes running every agent of a sandbox in its one gateway), and its source the session's platform (`cron` for a routine). The plugin registers each hook only when the Hermes it runs in lists it (`VALID_HOOKS`), since Hermes takes a name it does not know with only a warning: without `post_api_request` it registers neither and does not name `usage`, and without `post_auxiliary_call` it reports the agent's own calls alone; it names `agent_usage` only when this Hermes has the helpers that name a call's agent. What goes wrong in a hook is logged as a warning the first time, a call whose agent Hermes cannot name included, and never fails the agent's turn. It sees only the calls made in the gateway: board workers run outside it, so the host's person's windows read the agents' own records instead (above), which hold every native chat whatever ran it; whether a talk in the sandbox runs its calls in the gateway, which only the plugin's live reports and other persons' windows depend on now, is to verify, as is whether a background call made off the turn's context carries its conversation and its agent's home (design §14).

**OpenClaw.** The OpenClaw plugin reports the calls of OpenClaw's `llm_output` hook, which, as read in OpenClaw 2026.11.5's source, fires once per attempt of a run of its own agent loop with the tokens of all the attempt's calls summed and normalized for every model provider (`input` uncached, `output`, `cacheRead`, `cacheWrite`; no reasoning count apart from `output`, so `reasoning` is left out) and no count of them: the plugin counts the run's calls since its last report, those `model_call_ended` says completed and those `model_call_started` named that have not ended yet, whose end it then ignores (OpenClaw runs both hooks through a bounded background queue, so an end can come after the report or never; design §14), and sends one report of that many (`calls`); a run through a CLI backend or another harness fires no `model_call_ended`, so its report counts as one call. The model and model provider are OpenClaw's (`anthropic`, `openai`). A call whose native session key is an app conversation's, its turn's or that of the conversation's saved route, goes as `usage`; one in an app conversation's native chat it cannot match to its conversation is not sent; any other call goes as `usage.agent` on the connection of the agent the hook names, with its source (`cron`, `heartbeat`, or the channel). OpenClaw lets a plugin outside its bundle register `llm_output` only with `plugins.entries.enclos.hooks.allowConversationAccess`, which enclos sets for the app channel; the plugin reads the setting and, without it, registers none of its hooks, names neither capability and logs why once. What goes wrong in a hook is logged as a warning, by its kind, the first time, as is an app call it cannot match, and never fails the agent's turn. In that source, titles and other utility completions fire no hook and incognito native chats no `llm_output`, so neither is reported, and nothing marks a call `background`; that the hook fires as read, and which calls it sees, is to verify on a running gateway (design §14).

The counts come from inside the sandbox, which the agent writes: they guide the person, and bill nothing.

## Versions

`v` is the protocol's version, not enclos's or the app's. A change that an older peer would misread raises it; adding an optional field, `type` or capability does not. A new value of a field with a fixed set, such as a `message.out` `kind`, is a change an older peer would misread: a `kind` the receiver does not know is a version mismatch, not an optional addition. The bridge answers such a message `bad_message` and the plugin keeps it until an `ack`, so it would come back after every `hello`. `status` joined version 1 before its first release, in enclos 0.5.0; the plugin and the bridge come in the same enclos binary. From 0.5.0 on, such a change raises the version, unless a capability keeps the new value from every peer that did not ask for it, on both legs: `task_event` reaches only a bridge whose `hello` names `task_events` and a device whose `auth` does, and every other peer gets the same message as a `notify`. This exception follows from [ADR 0071](adr/0071-a-runtimes-task-events-reach-the-app-as-task-lines.md) (proposed), the first value added this way. A bridge speaks its version and the one before it for at least one release, and a device that receives `error` of code `version` tells the person to update the app.

## Sandbox policy requests

[ADR 0046](adr/0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md), proposed. `access.kind` is `network` (one exact host:port, optional private-address opt-in), `write` (one absolute path and everything beneath it), or `read` (shown for review, never removes a read denial). `action` is an agent-supplied label, at most 240 characters; it is data, never executed, and the bridge drops its hidden characters (control, bidirectional, zero-width and other default-ignorable characters, line separators and blank fillers; a joiner between two non-ASCII characters is ordinary text). A target is at most 4,096 bytes and contains no hidden characters. The plugin's connection supplies its sandbox and agent; the bridge accepts only that agent's own conversation or a group it belongs to. It answers every request with `ack`, after an `error` (`not_allowed`) when it refused it, so the plugin's outbox does not send it again; an access already decided (denied or approved) under the active policy is refused that way too, and the plugin's tool waits for that answer before it tells the agent whether the request is in the inbox. A sandbox has at most 50 pending requests; past that an agent's request is refused and a proxy refusal waits. A proxy refusal is per sandbox, with no requesting agent or conversation claimed.

The host generates `change`, `scope`, `restart`, `available`, `reason` and the opaque `revision`. `scope` is the entry approval writes: the normalized destination, or the writable path with its symlinks resolved, which the app shows apart from `access.target` when they differ. It refuses wildcards, blocked destinations, protected filesystem paths, pending policy changes, unrelated policy edits and stale previews. A writable request names one absolute non-root path, without `.` or `..`, and passes at least the manual policy editor's validation: hidden folders, executable and settings folders, and paths outside the user's home may be approved by the host's person, but the user's home folder itself and the folders holding it may not. The preview warns that the grant permits every sandbox agent to create, change or delete contents, including files the host's tools may run outside the sandbox. `change` opens with `Warning:` and the reason when the path is, holds or is inside a hidden file or folder in the home, `~/Library`, `~/Applications`, `~/bin`, `~/go/bin` or a folder on the host's `PATH`, whose contents the host runs outside the sandbox. A private opt-in is per host, including its other ports that the policy already allows, which the preview discloses; from the phone it is for an IP address or a local name (`.local`, `.home.arpa`, `.internal`, `.lan`) only. Write grants store and show the resolved destination, so a changed symlink invalidates the preview and cannot redirect a saved grant. A write change restarts all running sessions; services restart, interactive work ends. An unsupported request stays visible, with Deny and its reason but no approval. The device submits only the stored request id, the preview revision and its decision. The device's person must be the host's person, as the bridge records it (ADR 0044), and the device must still be paired. While none is recorded, or for another person, the answer is `not_allowed`.

States: `pending`, `applying`, `approved`, `denied`, `failed`, `closed` (final: put aside without a decision, below), and `diagnostic`, final: a proxy notification retired because only diagnostic probes caused it (below), which a device hides. A database claim serializes two devices' decisions. Requests deduplicate by sandbox, access (as `scope` writes it, so two spellings of one destination or path are one request) and active policy; a pending request is not duplicated when the policy changes. A resolved access may be requested again after a later policy change. A proxy refusal counts once: one older than the bridge's first collection is never collected. A pending or applying request covers every retry for the same access until its decision, closure or failure completes; the bridge records that cutoff atomically with the resulting state. The cutoff and persisted network-log timestamps are compared in milliseconds: a refusal at or before the cutoff belongs to that request, and only a strictly later millisecond is a new attempt, even within the same second. These checks supplement the existing per-policy request identities, so an unrelated policy change alone cannot recreate an old proxy request. The cutoff is internal metadata in an additive `app.db` table; `approval.time` remains the creation time, and the wire format and `state.db` schema are unchanged. Legacy requests with no recorded cutoff retain creation time as a lower bound: their pending-period retries cannot be reconstructed, so later attempts are not assumed to be handled. They are independent of message `seq` and are included at every sync. A stale preview is refreshed and must be reviewed again. `approved` follows the engine's successful application; failure may leave a pending or active change, so `failed` says to review the host's policy. An explicit authenticated agent request may reopen a `failed` request with a fresh preview under the same active policy; the proxy collector waits for a refusal strictly after the recorded failure cutoff before reopening it. A bridge restart makes an interrupted `applying` request `failed`, never replays it. Denial changes no policy. Both decisions have audit entries naming the device and request; an approval's also names the entry written.

[ADR 0054](adr/0054-closing-a-policy-request-is-not-a-denial.md), proposed: `approval.close` names only the stored request, with no preview revision or policy edits. It atomically changes `pending` or `failed` to terminal `closed`, even when `available` is false, and records `approval.closed` with the person, device and request in the same transaction, in the bridge's log (not enclos's audit log, as closing changes no enclos state). A `failed` request whose sandbox has a pending policy change is refused (`not_allowed`, naming `enclos policy apply` and `enclos policy discard`) until the host settles that change; the bridge checks for that change and closes under enclos's state lock, so none appears in between, and refuses the close when it cannot read whether one waits. The bridge closes a request only from the state it checked, so one that failed just after the check is checked again. The scope stays closed under the policy active at the close, even when the request was made under an earlier one. Duplicate closure is idempotent. If closure wins a race, an approval cannot claim that request; if approval already claimed `applying`, closure cannot interrupt it. Completed approvals, denials and diagnostic notifications remain unchanged: closing one is refused (`not_allowed`), and the device receives its current state. A pending request from a host diagnostic run is marked `diagnostic`, as a decision would mark it, not closed.

Closure changes only the request lifecycle: it does not call policy approval or denial, alter grants, restart the sandbox, retry or resume the attempted action, or undo work left by a failed application. `closed` is delivered through the usual `approval` update and sync to the host's paired devices. It survives bridge restart and stays out of the inbox; polling, a repeated agent request, reconnect or cache clearing cannot recreate the same scope under the same active policy. An agent that asks again for a closed or decided scope under the same policy gets `not_allowed` saying so before the `ack`, and the plugin's tool waits for that answer before telling the agent whether the request is in the inbox. Clients preserve `closed` for that request id when a delayed nonterminal update arrives, rather than reopening it. A sync sends every `pending`, `applying` and `failed` request, but closed and decided ones only among the latest 200: so once a sync completes, a client drops a cached `pending`, `applying` or `failed` request the sync did not send, which another device closed or decided while this one was offline. A different later policy snapshot may create a new explicit agent request with a different id; a new proxy request additionally requires a refusal after the closure cutoff. This contract concerns sandbox policy requests, not native runtime approval waiters.

Android and iOS require a connected host, completed fresh sync and the `approval.close` capability before enabling Close request. They never queue closure offline or hide it optimistically: the host's `approval` update with `state:"closed"` is the receipt, not a transport acknowledgment. Errors leave it visible. Closing from the detail page returns to the inbox after that receipt; a detail page already open when another device closes it says **Closed · no new decision**.

The bridge sends the active policy as `policy.context` (its grants, and only the number of read denials) after a supporting plugin's hello and after a decision, for every connected agent of the sandbox. Hermes persists it beside the channel socket and supplies it through `pre_llm_call`; a newly connected plugin gets a fresh description. It does not modify user-authored memory or imply that an inactive grant is available. The agent can use approved grants in later work. Neither side automatically repeats an attempted action.

The Hermes plugin reports concrete `read_file`, `write_file` and `patch` permission errors when their absolute path is known, and registers `enclos_request_access` for explicit requests, including file operations attempted through a shell; both only in an enclos conversation, through the agents that conversation reached. Against a running gateway this is to verify (design §14). A proxy's recorded allowlist/private-address refusals are collected while the bridge runs. There is no attempt to infer a policy from arbitrary shell strings or to observe every backend refusal. Rerun `runtime configure <sandbox>/<agent> --channel app` for existing agents to install the updated plugin.

## Sandbox policy management

Proposed in [ADR 0047](adr/0047-the-hosts-person-manages-sandbox-policy-from-the-phone.md). Only the host's person ([ADR 0044](adr/0044-each-agent-has-a-home-conversation.md)), on a still-paired device, may read or edit a sandbox policy through this surface. The bridge must list an agent of the sandbox. A page shows the active resolved filesystem, network, resource and secret-reference policy. Accepted access comes from all approved records, independent of the inbox history limit, and labels only entries still present in the active policy. Secret contents are never sent; secret grant management remains on the host.

An edit adds, replaces or removes one entry or replaces one scalar. The host validates it, supplies its exact policy differences and whether it stops running work, and binds the preview to both the active snapshot and policy file. Apply repeats the preview under the state lock; changed sessions can also invalidate a restart-free preview. A pending policy or unapplied file edits disables editing. Removing the last destination for a private host also removes its unused private opt-in, shown in the preview. Public network mode still permits public web ports after an explicit destination is removed, which the preview discloses. Inherited settings are overridden only for that sandbox, and a list edit never copies what the sandbox inherits into its file: an added entry goes to the list's `_add` (or into the list the file already replaces), an entry of the file's own comes out of its list, and an inherited one is named in the list's `_remove`, so the template's, the runtime adapter's and the built-in defaults' other entries stay inherited and later versions of them still reach the sandbox. Its audit entry names the field and the entry before and after. Protected built-in read-deny entries cannot be edited or dropped. Normal compiler, path and backend validations remain authoritative.

Edits are audited with the host's person and device. Network-only changes go live; launch-time changes explicitly require Save & restart and use the existing restart path. After an application attempt, the host's person's devices get the current policy and every capable agent plugin gets active policy context. Nothing is automatically replayed after interruption. Cached policy data on the phone is read-only until a fresh host response; clear cache and forgetting a host remove it.

A `sandbox.policy` or `sandbox.policy.preview` that would not fit one device-leg message is not sent: the request is answered with an `error` (`unsupported`, its `of`) naming the host command that shows the policy or makes the change, and a broadcast of it is left out. `sandboxes.list` is bounded the same way. A `sandbox.policy.apply` is measured before it is applied: when the policy it would make might not fit (the policy it was reviewed on, with the added value and room for a source label and a reason), it is refused with `unsupported`, naming `enclos policy edit`, and nothing is changed. An apply that was saved but whose policy cannot then be sent or read back is answered with `operation_failed`, its message saying the edit was saved.

### Diagnostic probe notifications

The reserved `probe.enclos.invalid` network destination is used by the built-in policy probes, not an actionable resource. The bridge never creates access requests for that exact host, on any port, and refuses explicit agent requests for it. Existing pending notifications are atomically reclassified as terminal `diagnostic`, with approval unavailable and no policy change, then delivered so connected devices hide them. Startup and sync perform this cleanup too; a stale phone decision cannot approve the old notification. Network logs remain intact. Other destinations, including private addresses and other `.invalid` names, are never excluded by address alone.

Each policy-test run registers a random, sandbox-scoped, expiring marker in host-only diagnostic metadata (`probe-sources.db`, mode 0600, a side database beside the state database: [ADR 0059](adr/0059-diagnostic-provenance-lives-in-a-side-database.md), proposed). Its curl requests and host controls carry that marker to the proxy; the marker is stripped from forwarded HTTP requests. The proxy still makes exactly the same policy decision. At log insertion, it verifies the marker against an active host registration and atomically records diagnostic provenance beside the unchanged network log. Unregistered, expired or wrong-sandbox markers do not suppress requests. The regular network log and `enclos net denied` retain all refused test connections; the approval collector reads only non-diagnostic refusals. Existing proxy processes must be refreshed once after this host upgrade to record markers.

Pending proxy notifications whose matching refusal history is entirely verified diagnostic traffic are retired without changing policy. A genuine refusal to the same host keeps the notification eligible. An explicit authenticated agent request retains its identity and is not retired by this test-source filter; if it supplies identity after a proxy-only request, the existing pending row is enriched. A later genuine request after a diagnostic notification was closed gets a different id, preserving both stale-decision protection and denial deduplication. Historical untagged log rows are not guessed to be diagnostics; only individually verified legacy probe events can be backfilled.


## Routines

An agent's optional `routines` capability exposes its runtime's scheduler ([ADR 0050](adr/0050-routines-stay-with-the-runtime.md), proposed). These are live controls: the bridge keeps neither definitions nor a second scheduler. They require the transport-identified host's person on a still-paired device, even for a list; a conversation share alone confers no routine-management authority. `agents.list` says so for each person with `can_manage_routines` (true for the host's person only; absent from an older host, meaning false), so an app offers routines only to the person who may manage them. A runtime without the capability keeps the ordinary conversation channel.

Both legs use `routine.request` and `routine.response`. The device request names `agent` (`<sandbox>/<agent>`); the bridge's authenticated plugin connection already identifies it. A response carries `of`, the original request id, and the same device-side `agent`. An `error` uses the same correlation. The bridge uses a separate plugin request id, binds pending work to the requesting device and plugin connection, and accepts only a matching response of the expected result kind. A routine response is not a conversation message and is never placed in its message outbox. The plugin request also carries `person` and `device`, the requester as the bridge authenticated them, never as a device claims.

A routine runs unattended, long after the request that made it, and outlives the device: unpairing a device removes none of the routines it made. So the bridge's log records every change it forwards (`routine.create`, `routine.update`, `routine.delete`, `routine.run`, `routine.pause`, `routine.resume`) with the device, the person, the agent and the routine, once when it is sent and once with its outcome: `confirmed` (with the new routine's id for a creation), the runtime's error code, or `unknown` after a timeout, a disconnection, an unreadable answer or a bridge database it could not read. A list or a read is not recorded. A routine id is the runtime's choice, so the bridge takes only one of at most 128 bytes with no control or hidden character (the shared rule of `enclos_protocol::visible`), from a device as from the runtime: a creation answered with another id is `unknown: invalid response`, and a list leaves such a routine out. `enclos app log` escapes every field it prints. The Hermes adapter also keeps the person and device on the routine it creates (`_enclos_person`, `_enclos_device` in its native origin), and refuses a creation once 50 live routines of the agent were made from the app (`not_allowed`); routines the agent made itself do not count.

| `action` | Request fields | Successful `result` |
| --- | --- | --- |
| `list` | optional `cursor` | `list`: bounded `routines` summaries, optional `next_cursor`, runtime `options`, bridge-authorized `deliveries`, `deliveries_limited` |
| `get` | `routine` id | `routine`: one complete definition and summary |
| `create` | `definition` | `routine`: the saved routine |
| `update` | `routine`, `revision`, `definition` | `routine`: the saved routine |
| `set_enabled` | `routine`, `revision`, explicit `enabled` boolean | `routine`: its confirmed state |
| `run` | `routine`, `revision` | `run`: accepted routine id; acceptance is not completion |
| `delete` | `routine`, `revision` | `deleted`: removed routine id; this does not promise cancellation of running work |

Fields are flat beside the envelope, for example `{"v":1,"id":"r1","type":"routine.request","agent":"lab/main","action":"list"}` and `{"v":1,"id":"r2","type":"routine.response","agent":"lab/main","of":"r1","result":"list","routines":[],"options":{"timezone":"Europe/Paris","features":[],"skills":[],"models":[],"toolsets":[]},"deliveries":[],"deliveries_limited":false}`.

`schedule` is typed: `{kind:"cron",expression:"0 9 * * *"}`, `{kind:"interval",minutes:60}` or `{kind:"once",at:"2026-12-01T09:00:00+01:00"}`. Daily, Weekly and Monthly are editor presets for five-field cron. The Hermes adapter takes a cron expression only as five fields of numbers, `*`, ranges, steps and lists, with three-letter names only for the month and the day of the week. The adapter validates native syntax and computes actual run times. `options.timezone` describes the runtime's effective timezone; it is not an editable per-routine timezone. `features` names supported controls: `skills`, `model`, `provider`, `toolsets`, `script`, `script_only`, `working_directory` and `run`; unknown names are ignored. Skill/toolset choices have `id` and `label`. Model choices additionally have optional `provider`: selecting one changes the model/provider pair together, even if two providers use the same model id. Saved values absent from a catalog remain unchanged.

Optional `options.operations` names the available live controls: `get`, `create`, `update`, `delete`, `set_enabled` and `run`. An explicit list permits only its named operations; `[]` exposes inventory alone, and `["get"]` permits read-only details. Unknown names grant no operation. When absent, the preceding behavior remains: ordinary controls are available and `features` must contain `run` for manual execution. Apps hide unavailable actions, including New for an empty read-only inventory, and refuse to submit unavailable operations. The adapter still independently enforces these limits.

A `definition` has optional `name`, `prompt`, `schedule`, optional `delivery` conversation id, `skills`, optional `model`/`provider`, optional `toolsets`, optional `script`, `script_only`, and optional `working_directory`. Missing/null toolsets means runtime defaults; `[]` deliberately selects none. Missing delivery means save output without sending it. Scripts name relative files under the agent's scripts directory, including resolved symlink containment; a script a native routine already had is kept as saved when an update leaves it unchanged; script-only requires a script. A working directory is an existing absolute directory and conveys no additional sandbox access. Definitions are bounded (including an 8 KiB prompt); oversized existing native definitions produce an explicit error rather than a truncated editable prompt. Native fields outside this interface survive updates.

Summaries contain opaque `id` and editable-definition `revision`, name, schedule, enabled state, bounded prompt preview, `delivery_label`, `editable`, and optional observed `state`, `paused_reason`, `last_error`, `next_run_at`, `last_run_at` and `last_status`. A disabled routine may be completed rather than paused. A revision covers the definition, not scheduler progress; the adapter compares it under the runtime's lock before changing an existing routine. Native jobs whose targets or settings cannot safely be edited may be shown read-only. This includes external channel destinations rather than making the app rewrite them into an app conversation. A native job the app's format cannot carry at all (no schedule, another kind of schedule, a null field, an id the bridge refuses) is left out of a list, and the Hermes adapter logs that it was, so one such job does not stop the others from being listed. A full definition is loaded only on request; lists paginate at most 25 summaries rather than sending every prompt in one Noise frame. The adapter reads its skill, toolset and model catalogues at most every 30 seconds, not for each page. Plugin results are bounded to 44 KiB before bridge enrichment; device results stay within 60 KiB.

The bridge supplies delivery choices, never trusting a plugin-supplied catalog: only the host person's direct/Home conversations with this exact agent, including archived ones. Groups, another agent's conversations, and another person's conversations are refused. To bound a response it offers Home plus at most 50 recently created conversations and sets `deliveries_limited` when more exist; a full definition preserves its authorized saved target even when that target falls outside the picker. Its internal plugin request carries the allowed conversation ids so the adapter can also check an existing target before a mutation. That list is not accepted from a device. The bridge does not execute scripts, change policy or run a host shell command.

Requests are not queued when the agent is unavailable, and mutations are not automatically replayed after timeout or disconnect. A lost reply after dispatch can leave the outcome unknown; refresh before retrying. When the bridge cannot read its own database, it says why in its own output: before dispatch it answers `internal`, as nothing was sent; after the runtime answered it answers `unknown`, as the outcome is unknown, and that answer is not kept, so a retry once the database reads again gets the runtime's replayed answer. The Hermes adapter deduplicates creation using trusted request identity stored with the native job, without writing the jobs file itself. A scheduler-registration failure after a job was saved reports that outcome and does not invite another create. Bounded live replay handling protects repeated requests; it does not promise exactly-once execution across every crash.

Hermes keeps a versioned receipt of at most 4 KiB beside its channel socket for each app-created routine (request fingerprint and native id only), retaining that receipt after deletion so retrying an old create cannot recreate it: the receipts grow by one small file per creation from the app, and none is removed. The native job's origin marker recovers a create interrupted before its receipt was written. `run` claims a native manual attempt before returning acceptance, then dispatches the exact claimed snapshot asynchronously; a paused routine must be resumed first. Native manual execution may advance the next interval occurrence; the app shows the scheduler's resulting next-run time.

Hermes revision comparison and mutation share its native reentrant jobs lock. Its normal cross-process file lock can fall back to in-process locking after a native timeout or locking failure; protection against concurrent native CLI changes inherits that documented limitation ([source evidence](research/hermes-routines.md)). The plugin does not replace its scheduler's locking implementation.

The OpenClaw adapter exposes only inventory and read-only details through its public, lifecycle-scoped Gateway service scheduler. It filters explicit native agent ownership and advertises `["get"]`; it refuses every mutation before scheduler access. Unsupported native schedule kinds, per-job time zones differing from the Gateway's effective time zone, or incomplete full definitions report `unsupported`. Native external destinations remain read-only observations. The current public service facade has no definition compare-and-swap or complete agent-targeted creation contract. This is M5's agreed read-only scope; mutation parity is tracked in [enclos#226](https://github.com/victorbonnet/enclos/issues/226) ([source evidence](research/openclaw-routines.md)).

## An agent's model

An agent's optional `model` capability lets the host's person see and change the [agent model](../GLOSSARY.md): the model provider and model its runtime uses for all the agent's conversations ([ADR 0069](adr/0069-an-agents-model-is-changed-through-its-runtimes-channel.md), proposed; issue #325). The runtime keeps the setting and the catalogue of model providers and models; the bridge stores neither. As for [routines](#routines), only the host's person on a still-paired device may ask, even to read, and `agents.list` says so with `can_manage_model` (absent from an older host, meaning false). A person an agent is shared with gets no model control: the model decides what the host's accounts are charged and which logins and secrets are used.

Both legs use `model.request` and `model.response`, flat beside the envelope, correlated as routine controls are: the device names `agent`; the bridge sends the plugin its own request id with `person` and `device` as it authenticated them, binds the request to the device and to the plugin connection it went out on, accepts only an answer of the kind asked, and answers the device under its original id. Requests are live, never queued or retried; one unanswered after 60 seconds, or cut by a disconnection, answers `unknown`.

| Action | Request fields | Successful result |
| --- | --- | --- |
| `options` | none | `options`: optional `current` (`model`, and `provider` when the settings name one), an opaque `revision`, `applies`, `providers` (`id`, `label`, `usable`, and `setup` exactly for one not usable), `custom_models` |
| `models` | `provider` | `models`: the `provider` asked for, its `models` (`id`, `label`), at most 300, and `limited` when it offers more than are listed |
| `set` | `provider`, `model`, `revision` | `set`: optional `previous`, `current` as the runtime saved it (the model's id may be in the runtime's own form, under the same model provider), the new `revision`, `applies` |

For example `{"v":1,"id":"m1","type":"model.request","agent":"lab/main","action":"set","provider":"openrouter","model":"some/model","revision":"9f2c…"}` and `{"v":1,"id":"m2","type":"model.response","agent":"lab/main","of":"m1","result":"set","current":{"provider":"openrouter","model":"some/model"},"revision":"41aa…","applies":"live"}`.

`options` lists the model providers the runtime knows, at most 100, without their models, so that it fits one Noise frame; the app asks for one model provider's models once it is picked. A model provider the agent cannot use yet is listed with `usable: false` and `setup`, what to do on the host; the app shows it disabled, and a `set` naming it is refused `not_allowed`. No secret travels this protocol. `custom_models` says whether the runtime takes a model id its lists do not name. `revision` changes whenever the agent's model setting does: the plugin refuses a `set` against another one (`conflict`), whether the change came from another phone or from the host. `applies` says how a change takes effect: `live`, on the agent's next turn, or `restart`, once the runtime's service restarts, with every agent it serves; the app says so before saving.

The plugin answers a request it cannot serve with an `error`: `not_found` for a model provider the runtime does not list, and for a model it does not list when `custom_models` is false; `not_allowed` for a model provider the agent cannot use yet, or a model the runtime refuses, with its reason; `unsupported` when its answer would be too large; `agent_unavailable` when it could not read the runtime, and nothing changed; `unknown` once a change may have been written but was not confirmed. The bridge passes these codes on and turns any other into `unknown` for a `set`, so that a change is never answered as one safe to try again; it strips hidden characters from the message.

Every id and label passes the shared rule of `enclos_protocol::visible` (no control or hidden character); an id is at most 200 bytes, a label 200, a `setup` 500; no two model providers, nor two models of a list, share an id; and a `set`'s `current` names the model provider asked for. A plugin keeps each answer under 44 KiB (`enclos_protocol::model::MAX_REPLY_BYTES`), listing fewer models (`limited`) or answering `unsupported`. An answer the bridge cannot take is `unknown: invalid response` for a `set`, and `agent_unavailable` for a read, which changed nothing; a read too large for one device-leg message is `unsupported`. The bridge's log records each `set` with the device, the person, the agent and the model and model provider asked for (`agent.model.set`), written `model (provider)`, once when it is sent and once with its outcome: `confirmed` with the model before and after, the runtime's error code, or `unknown`. A change the log cannot record is refused (`internal`) before it is sent. When the runtime answers a change after it ended `unknown` (a timeout, a disconnection), the log records that late answer too. A read is not recorded.

**Hermes.** The plugin lists model providers with Hermes's own inventory (`hermes_cli.inventory.build_models_payload`, with those not set up), in the agent's own Hermes home, which it checks is the agent's (`profile_name_for_home`): one Hermes marks `authenticated: false`, or lists only as a setup skeleton, is not usable. A `set` runs Hermes's own `/model --global` path, `switch_model` then `persist_model_selection` into the agent's `config.yaml`. The revision is a hash of the `model` block as Hermes loads it; the plugin compares it before checking the model and again just before saving, since Hermes's save merges a change made meanwhile rather than refusing it. A change made by another process in the moment between that last check and the write is still merged: Hermes has no lock across processes. `custom_models` is true: Hermes checks an id its catalogue does not list with the model provider, and refuses it as `not_allowed`. `applies` is `live` unless the agent's `config.yaml` uses YAML enclos's settings watch compares whole (below), when it is `restart`: the plugin follows the same rules as the Hermes adapter's `restart_relevant`, which tells the watch that a change of the top-level `model` block alone needs no restart (ADR 0031, as ADR 0069 amends it). Read in Hermes's source, its gateway loads `config.yaml` for each turn and rebuilds an agent whose model changed; that it does so on a host is to verify (design §14). The plugin turns the capability off, and logs why, when the Hermes it runs in lacks one of these functions.

**OpenClaw.** The plugin lists model providers and models with OpenClaw's own `/models` catalogue (`buildModelsProviderData` from `openclaw/plugin-sdk/models-provider-runtime`) for the agent: `view: "all"` for every model provider; one is usable when OpenClaw's own `/models` menu counts models available for it (signed in, and within the agent's model allowlist), and the notice that menu gives for one that is not becomes its `setup`. Shown with the installed SDK 2026.11.5: with no login, OpenClaw lists the agent's default model provider with its default model and none available. It takes only a model the catalogue lists (`custom_models` is false). A `set` writes the agent's primary model through the plugin runtime's own config write (`mutateConfigFile`, `afterWrite: auto`), which validates the config: in the agent's `agents.entries` entry, or in its `agents.list` entry when the config uses that older roster (an agent missing from the list is refused `unsupported`); the agent's fallbacks are kept, and an agent that used the shared default keeps that default's fallbacks. The revision, a hash of the agent's and the shared default's model references, is compared again on the draft the write edits. `applies` is `live`: OpenClaw 2026.11.5's reload rules hot-apply `agents.entries` and need no reload for the rest of `agents`, and with `afterWrite: auto` its write asks for no restart; the plugin would answer `restart` if one did.

## Held tasks

A held task is background work an agent's runtime started that has stopped and waits for a person before it runs again, such as a blocked task on Hermes's kanban board ([ADR 0066](adr/0066-held-tasks-stay-with-the-runtime.md), proposed). The runtime keeps the task: its definition, state, retries and history. enclos keeps no second board and never runs or retries the work; the bridge keeps a card for each held task, not the task. An optional `held_tasks` capability, in both the bridge's and the plugin's `hello`, carries them; the types are `enclos_protocol::held_task`. What is built so far, and what is still to verify, is in [design §14](design.md#14-awaiting-prototype-verification).

**The plugin's report.** A plugin that announces `held_tasks` to a bridge that announced it sends `held_tasks` with `tasks`: every task held now that its own agent started, less those its runtime wakes that agent for and that the agent has not handed to the person ([ADR 0072](adr/0072-a-held-task-asks-the-person-only-when-its-agent-says-so.md), proposed; Hermes below), after the `hello`, and again whenever one is held, changes or is no longer held. It reads them from the runtime's own state, prompted by the runtime's events or a periodic read, never from the text of the runtime's notifications. The message is the whole list, not a change: a task absent from it is no longer held. So it is not kept in the plugin's outbox: the bridge acknowledges it once stored, and one lost or refused is replaced by the next, or by the one after the next `hello`. Each task has:

| Field | Meaning |
| --- | --- |
| `task` | The runtime's id for it: the id rule, and no hidden character |
| `title` | One line |
| `assignee`? | The agent doing the work, as the runtime names it, when it is not the one that started it |
| `reason` | Why it is held, in the runtime's words (Hermes: the block's reason, or the last failure when its retry limit tripped) |
| `last_error`? | The last failure's text |
| `since` | Since when it is held, in seconds since the Unix epoch |
| `revision` | The runtime's opaque revision of this hold, which a resume names: the id rule, and no hidden character |
| `resume` | What resuming does for this runtime, one line ("Runs it again with a fresh retry budget."); for a task that is not `resumable`, what a person does instead, or empty |
| `resumable`? | A JSON boolean: whether the app may offer to resume it. Absent, as from an older plugin, it reads as `true`; any non-boolean value present (`null`, a string, a number, an array, an object) refuses the whole message. `false` is information for the card: the task stays held and visible, and the bridge refuses its resume (below) |
| `waits_on`? | A JSON string, `person` or `team`. Absent or any value that is not exactly `"team"` reads as `person` (never refuses the message). `team` means the team's own schedule resolves the hold: it is still reported on the plugin leg and its card stays held and resumable. A hold the agent handed to the person with an ask always reads `person`, whatever its block kind; the bridge reads its `held_task` open item the same way, `person` whatever the stored value says |
| `ask`? | What the agent that started the task wrote for the person when it handed the hold to them ([ADR 0073](adr/0073-the-person-answers-a-held-task-from-its-card.md), proposed), kept by the plugin for this hold only: `decision`, the decision as one question; `blocked`, what is stopped and why, in plain words; `choices`, up to 4 answers, each one line saying what happens, or none for a free answer; `recommended`?, the index of the choice the agent recommends; `settled`?, a JSON boolean, true once the agent says the person answered (absent reads as `false`); `asked`?, an opaque integer the plugin gives each time the agent asks, so the same words asked again are another question |

A list holds at most 32 tasks (the newest, when more are held), each once; the bridge refuses a longer one or one that names a task twice (`bad_message`) and changes nothing, and refuses (`not_allowed`) the report of an agent forgotten on the host until it is set up again ([ADR 0067](adr/0067-the-hosts-person-can-forget-a-removed-agent.md)), whose cards forgetting removed. A resumed card that a report still lists at the revision it was resumed at is a report read before the resume, and changes nothing. The plugin's cut runs in the sandbox, so the bridge makes its own before it stores a card (`HeldTask::normalized`): hidden characters dropped (enclos-protocol's `visible` rule), the title, the assignee and `resume` on one line (a line break or a run of white space read as one space), the title cut to 200 characters, the reason to 1,000, the last error to 2,000, `resume` to 200 and the assignee to 64; a blank title reads as the task's id and a blank reason as "Waiting for a person." An `ask`'s `decision` and each choice are made one line, the decision cut to 120 characters and each choice to 80, and `blocked` cut to 400 with its line breaks kept. A choice left blank, or reading as one before it, is dropped, and only the first 4 are kept. `recommended` follows its choice, and is dropped when that choice was. An `ask` whose decision is blank is dropped whole: the card reads as one the agent did not write.

**The card.** The bridge keeps one card per task of each agent, in the Home of the agent whose plugin reported it, so the host's person alone sees it. `held_task` sends a device its metadata: `agent` (`sandbox/agent`), `conversation` (that Home), `task`, `title`, `assignee`?, `reason`, `last_error`?, `since` and `resume` as the bridge cut them, and `resumable`, without the runtime's revision or `waits_on`; `ask`?, the agent's as the bridge cut it, without `settled` or `asked`; `answer`?, on an `answered` card, what the person answered (one line, at most 200 characters); then `state` and the bridge's `revision`, a nonnegative integer advanced on every change. The card carries no `waits_on`, so a card read from its conversation is drawn and acts as today. The bridge always writes `resumable`, live, at `sync` and in `held_task.result`; a device reads one without it, from an older bridge, as `true`, and refuses any other value present as it does on the plugin leg. A device keeps the highest revision it saw for a card (its host, agent and task) and ignores a lower one.

| `state` | Meaning |
| --- | --- |
| `held` | The runtime holds it: the only state with a Resume, offered only when `resumable`, and the only one under "Needs you" when it waits on the person (`waits_on`) |
| `answered` | The runtime still holds it, and the person answered: from the app (below), or in the conversation, as the agent says (`settled`). It waits on the agent, not the person: no Resume and no answer, but its details and board stay open |
| `resumed` | A paired device resumed it, and the runtime confirmed |
| `released` | The runtime no longer lists it: it runs again, finished or went away, wherever that happened |
| `expired` | The agent's channel connected without `held_tasks`, so the card can no longer tell |

A device reads a state it does not know as one with no Resume.

When a task is first held, or held again after its card left `held`, the bridge stores the card as `held` and, in the same transaction, a message in that Home: `kind: notify`, from the agent, with readable text (the title, the reason, the last error and what resuming does, after `Resume:`; for a task that is not `resumable`, its `resume` as a plain line, or "This task cannot be resumed from the app." when that is empty) and `held_task`, the task's id. So the person is notified, the card survives an app restart, and an older app shows the text. When a card leaves `held`, or a resume is confirmed for a card already released, the bridge appends a quiet `kind: status` message linked the same way ("Resumed from the app: …", "No longer held: …", "No longer tracked: …"). New fields on a card still held (another reason, a new error, `resumable` alone turning either way) update it, advancing its revision once, with no new message; the same task reported again, or a card an older bridge stored without `resumable` reported again as `true`, changes nothing. An `ask` that is new on a held card, or another than the card had (another `asked` included), and not `settled`, updates it and adds a `kind: notify` message linked the same way, which reads on its own: the decision, what is blocked, the choices (the recommended one marked) and the task's title. So the person is told when the agent hands the task to them. A `settled` ask makes a held card `answered` ("Answered in the conversation."), with a quiet line. An `answered` card stays so while its task is listed with the same `since` and an ask that is the same or `settled`, its other fields updated with no message. It is held again, with a new message, when the task is listed with another `since` (a new hold) or with another ask that is not `settled` (the agent asks again), and released as a held card is when the task is not listed. The bridge sends a card's `held_task` before every live or synced message linked to it, and at every `sync` each card still `held` or `answered`, whatever `since`, as for [questions](#questions): a device that lost an answer's reply learns it was taken. Only `held` cards are open items. The largest card fits one device message.

**Resume.** A device sends `held_task.resume` with `agent`, `task` and the card's `revision`. Only the host's person on a still-paired device may: a runtime's background work is shared by the sandbox's agents rather than owned by a conversation, as for [routines](#routines). Before sending anything to the plugin, the bridge answers `not_allowed` to anyone else; `not_found` for a card it does not have (another agent's or an unknown one alike); `conflict` when the revision is not the card's or the card is not `held`; then `unsupported` when the card is not `resumable`, before the agent's plugin is opened or anything is logged or sent; `agent_unavailable` when the agent's plugin cannot be reached; and `unsupported` when it is connected without `held_tasks`. So a card that is not `resumable` is said to be so only to whoever may resume it as it is. An older app may still show Resume for such a card; the bridge refuses it all the same. An older bridge does not know the field and sends such a resume to the plugin, which must refuse it itself (Hermes does, below). A bridge that does not keep held tasks answers every `held_task.resume` with `unsupported`.

Otherwise it writes an audit entry (`held_task.resume`, with the device, the person, the agent and the task), and only once that is written (else `internal`, nothing sent) sends the plugin `held_task.resume` with `task`, the runtime's `revision` from the card, and `person` and `device` as it authenticated them. The plugin checks that the task is still held at that revision, then calls the runtime's own resume operation, which changes the task only while it is still held; a runtime that cannot check the revision and resume in one step says so (Hermes, below). It answers `held_task.resumed` (`of`: its id) or an `error`: `conflict` when the task was no longer held at that revision when it checked, `not_found` when the runtime has no such task, `unsupported` when the runtime holds it but does not resume it this way, `internal` when the runtime failed. Then it sends a fresh `held_tasks`. On `held_task.resumed` the bridge marks the card `resumed`, appends its status message and sends the card and that message to the person's devices, the asking one included, then answers the asking device `held_task.result` (`of`: the device's request; `held_task`: the card). A plugin's `error` reaches the device with its code. No reply within 25 seconds, or a connection that ends after sending, answers `unconfirmed`: the task may have resumed. A confirmation that comes after the timeout still marks the card `resumed`, and is logged (`confirmed late`); a confirmation the bridge cannot store yet is answered with the card as `resumed` and recorded at the next chance. The answer to a device's request, whatever it was, `unconfirmed` included, is kept: the same request sent again gets it, and never reaches the runtime twice. Each answer, a kept one included, goes only to the asking device while it is still paired to its person, and one still waiting for the runtime goes only to the pairing that asked, with the keys it asked with; each is `unconfirmed` with the fixed text alone, nothing of the card or the runtime's answer, when that person is no longer the host's, the card no longer theirs, or the bridge cannot read either. Each outcome is a second audit entry: `confirmed`, the plugin's code, or `unknown`. A resume is never queued or sent again on its own; after a lost reply, the app syncs before the person decides again.

**What a resume authorizes.** The plugin leg's rule holds: no message from the bridge carries authority the agent lacks. A Hermes agent with the kanban toolset can unblock a task itself (`kanban_unblock`), and anything in the sandbox can write the board, so `held_task.resume` needs no proof like a [runtime approval's](#runtime-approvals) signature: the bridge's checks decide who may tap Resume in the app, not what the sandbox can do. Resuming widens nothing: the work runs again under the sandbox's existing policy, and a task held for missing access needs a policy request, not a resume. A runtime may reset its retry budget on resume (Hermes does), and `resume` says so.

**Answer** ([ADR 0073](adr/0073-the-person-answers-a-held-task-from-its-card.md), proposed). A bridge that announces `held_task.answer` in `authenticated` lets the host's person answer a held card from the app.
- **The request.** A device sends `held_task.answer` with `agent`, `task`, the card's `revision` and `answer`, which is one of:
  - `{kind:"choice",index}`: one of the card's `ask` choices, by its zero-based index;
  - `{kind:"text",text}`: a typed answer, nonblank, at most 2,000 characters, with no hidden character other than a newline;
  - `{kind:"agent"}`: ask the agent to look into the task and say what it needs.
- **The checks.** The bridge checks as for a resume: `not_allowed` to anyone but the host's person on a still-paired device, `not_found` for a card it does not have, and `conflict` when the revision is not the card's or the card is not `held`. It answers `bad_message` for a choice the card's `ask` does not have (or a card with no `ask`) and for a text outside its rule. It answers `conflict` too while a resume of that card is on its way to the runtime, and when the card's conversation cannot take a message (gone, another person's, or being deleted). A resume the runtime confirms for a card answered meanwhile still marks it `resumed`.
- **Logging and delivery.** It then writes an audit entry (`held_task.answer`, with the device, the person, the agent, the task and the answer's kind; else `internal`, nothing sent), and a second one with its outcome: `taken`, `conflict`, `not sent` or `unknown`. It stores the person's message in the card's conversation, the agent's Home, and gives it to the agent as `message.in`, as it does a `message.send`: now, or once the agent's plugin can be reached. The message reads on its own:
  - `About held task <task> "<title>": <decision>`, then `My answer: <label or text>` on a second line;
  - for `agent`, `About held task <task> "<title>": look into it and tell me what you need from me.`;
  - a card with no `ask` puts its title alone before the colon's text.
- **The result.** The bridge marks the card `answered`, with the choice's label, the text's first line or "Asked the agent to look into it." as `answer`. It sends the card to the person's devices and answers the asking device `held_task.result`.
- **What it starts.** The answer is the agent's turn, nothing more. The agent decides what it means, with its own tools (resume, comment, specify, end the task), and it grants nothing the same message typed in the conversation would not.
- **Repeats.** The same request sent again finds the card `answered` and is answered `conflict`, and the message is stored once per device request.
- **Plugins.** Plugins need no capability for it.

**Expiry.** A plugin that connects without `held_tasks` can neither report nor resume: the bridge expires that agent's held and answered cards at once, each with its status message. A runtime with no such state does not announce the capability. Other actions (cancel, reassign, edit) are not part of this contract.

**Hermes.** Its kanban board is shared by the sandbox's profiles, and an enclos agent is the Hermes profile of its name. The plugin (`channels/hermes/enclos/held_tasks.py`) announces `held_tasks` when the Hermes it runs in has the parts of its board it reads (listed in `channels/README.md`), and logs what is missing otherwise. It reads every live board Hermes lists, read-only (a `mode=ro` URI, never Hermes's `connect()`, which creates and migrates the database), each database once through Hermes's own pins, as its gateway notifier does; a board with no database yet is skipped. It reads the `blocked` tasks whose creator (`created_by`) is its own profile, and reports those that are the person's (below): a task of the `default` board by its id, one of another board as `<board>/<id>`, since two boards can hold the same id (a `default`-board id holding `/` is left out). `reason` is that of the task's latest `blocked` event (its reason, else its kind), or "Gave up after N consecutive failures." for a `gave_up` one, and empty when an `unblocked` or `created` event is newer than both; `last_error` is the task's last failure, else the `gave_up` event's error; `since` is that event's time, or the task's `created_at` when there is none or it is out of range; `revision` is `e:` and the id of the task's latest event, so any event on the task, a comment included, moves it. Text from the board is made valid UTF-8, and a task whose id or revision breaks the rule is left out and logged once. When more than 32 are held, the oldest are left out, and the bridge reads them as no longer held: the plugin logs a warning naming them each time that set changes. A board that cannot be read keeps its tasks as last read, with a warning, while the others are reported; when the boards cannot be listed, nothing is sent, so a list missing a board's tasks never releases their cards. Hermes's plugin hooks are not a complete source ([source findings](research/hermes-tasks.md#hooks-are-not-a-complete-source)): a block fires `kanban_task_blocked` in whichever process blocks the task (a worker's, not the gateway's), and giving up and `unblock_task` fire none. So the plugin reads the board again after each board hook and dispatcher tick (`on_kanban_dispatch_tick`) it sees, and every 30 seconds, off the gateway's loop, and sends the list after each `hello` and resume, and otherwise only when it differs from the last one sent on that connection. A resume reads the task, read-only: `not_found` unless it is this profile's, `conflict` unless it is still `blocked` at `revision`. Only then does the plugin open Hermes's writer for `unblock_task`, which changes only a still-blocked task and resets its retry count, and answers `conflict` when it changed nothing. `unblock_task` takes no revision and opens its own transaction: the adapter compares the task's latest event with `revision` first, so a task unblocked and blocked again between that check and the unblock is resumed at its newer hold. When Hermes raises, the plugin reads the task again and answers `held_task.resumed` if it is no longer blocked or was unblocked since `revision` (Hermes checks its file after committing), `internal` otherwise. It logs the person and device that asked.

Hermes's loop breaker moves a task blocked again for the same kind after an unblock, `BLOCK_RECURRENCE_LIMIT` times, to `triage` with a `block_loop_detected` event, not to `blocked`. Such a task is held too, while that event is its latest move into or out of triage (a creation, an import, a status set by hand, a specify, an unblock, a promotion, a completion or an archive): a task proposed in triage, or put back there by hand, is not held, and Hermes's `block_kind`, which outlives an unblock, is not read for it. Its `reason` and `since` are that event's, its `revision` the task's latest event (of any kind), as above. The plugin reads `triage` only from a Hermes whose `kanban_db.VALID_STATUSES` names it; one without that list is read as having no triage, and its `blocked` tasks are still read and reported as they change.

Such a task is not resumed from the app: it is reported `resumable: false`, with `resume` "Decide on the agent's task board.", and the bridge refuses its resume before the plugin. A resume of it that reaches the plugin anyway (from an older bridge) is checked as above (`not_found` unless it is this profile's, `conflict` unless it is still held there at `revision`), then answered `unsupported` before Hermes's writer opens, whether or not Hermes has `specify_triage_task`. That call, Hermes's way out of triage, takes no revision and changes any task in `triage`, and Hermes offers none that checks the revision, the creator or the hold in its own transaction: a task changed, held again or moved back to triage by hand between the plugin's check and the specify would be specified all the same, and could run again. Once specified on the board, the task waits for its parents as any other and leaves the list. The inherited limits of a blocked task's resume, above, are unchanged.

Hermes's agent hands a held task to the person with the tool `enclos_ask_person`, which the plugin registers (toolset `enclos`). It takes the task as reported (`<board>/<id>` off the `default` board), `decision`, `blocked`, `choices` and `recommended`, and is refused unless the task is held now and created by the calling agent's profile (the profile Hermes runs the call for, `profile_name_for_home`). `enclos_person_answered` takes a task and marks the agent's ask on it `settled`; for a task the agent never asked about, the task's title and reason stand as its decision and what is blocked. Each ask is stamped `asked` (milliseconds since the Unix epoch) when the agent gives it. A list read before an ask was kept never forgets it, and a file of asks that cannot be read sends no list at all, rather than one that would withdraw them. The plugin keeps each ask with the hold it was given for, the task and its `since`, in a file beside its socket (`<socket>.held-asks.json`), so it survives a gateway restart. It attaches the ask to that task in each `held_tasks` while the hold is the same, and forgets it once the task is no longer held or is held again. Where held tasks are on, the plugin tells the agent of the tool in each turn (a `pre_llm_call` context, `asks.HINT`), in plain words for the person, without run numbers, hashes or the board's own terms. The hint and the tool's schema ask for a card the person can decide from alone: `blocked` says what was tried, why it stopped and whether another attempt would go differently, each choice says what it costs (time, attempts), and a request for more time or attempts offers more than one amount.

A hold goes to the agent first ([ADR 0072](adr/0072-a-held-task-asks-the-person-only-when-its-agent-says-so.md), proposed). Hermes's gateway notifier wakes a profile with a task's `blocked`, `gave_up` and `block_loop_detected` events when the task's board has a subscription for it (`kanban_notify_subs`) whose `delivery_mode` is `wake` or `notify+wake` and whose `notifier_profile` is that profile; Hermes's kanban tool makes one, `notify+wake`, for a task an agent creates from a gateway conversation, unless its `kanban.auto_subscribe_on_create` setting is off. The plugin reads those columns, read-only, with each held task, and leaves a task held that way for its own profile out of `held_tasks` until the agent hands it to the person: it is listed once the agent asked with `enclos_ask_person`, `settled` or not. An answer the agent reports with `enclos_person_answered` for a hold it never handed over lists nothing, since the person never saw that hold. Every other held task is listed at once, since its agent is not told of it: one with no subscription (asked for outside a conversation, by a routine or another task's run), or only with one that does not wake (`notify`), names another profile, or names none (a blank or missing `notifier_profile` is not read as this profile's), and every held task of a board without those columns (an older Hermes). Hermes drops a subscription whose wakes keep failing, and the task is then listed. A task that becomes woken leaves the list, which releases its card. The tools still find a woken task, since they look up every hold. The agent's hint says so: a task it created that stops is its to act on (answer the assignee, resume it, end it), and the person sees it only once the agent calls `enclos_ask_person`. A hold listed at once still goes to the Home of the agent that created the task, and a held task no agent created (Hermes: `user`, `dashboard`) is still reported by no agent: sending such holds to the built-in agent's Home, as ADR 0072 decides, is not built.

## Tasks and agent activity

[ADR 0068](adr/0068-tasks-and-agent-activity-are-reported-not-controlled.md), proposed. Two optional capabilities, each announced in both the bridge's and the plugin's `hello`: a plugin sends neither message to a bridge that does not list the capability, and the bridge reads neither from a plugin that did not announce it. Neither carries authority: like a `tool` step, they are what the runtime reports, and no control comes back.

**Agent activity** (`activity`). `agent.activity` says what the agent is doing, whole: `doing` is a list, empty when it is idle, of at most 16 entries, each one of

- `{kind: "answering", conversation}`: it is working on an answer in that conversation;
- `{kind: "routine", routine}`: one of its [routines](#routines) runs, by the runtime's id;
- `{kind: "task", task}`: it works on that [task](#tasks), by the runtime's id;

and `since` is when that list began, in seconds since the Unix epoch. A list because an agent can answer a chat while it runs a task. An entry of a `kind` the receiver does not know is left out, so a later version can add one. The bridge keeps an entry only when its conversation is one of the agent's own (a group it is a member of included) and its routine or task id passes the routine id rule (at most 128 bytes, not blank, no hidden character), and keeps `since` no later than its own clock. It is passed on live and not stored in history: the bridge holds each agent's current state with the connection that reported it, sends it to a device after `agents.list` for each agent not idle, and makes the agent idle (an empty list, sent to devices) when that connection closes, however it closes, and when a plugin connects without the capability. The plugin sends its state after every `hello`, so that a gateway restart or a lost "idle" is meant not to leave an indicator on (to verify, design §14). The host's person gets every entry; another person only the `answering` entries of their own conversations, and is sent an update only when that part changes. `enclos status` shows the same state while a bridge runs: the bridge writes it to its database, holds a lock beside it while it runs and clears it when it starts, and `status` shows nothing when no bridge holds the lock, and says when it cannot read the state.

### Tasks

A task (`tasks`) is work an agent does outside a conversation's answer, which its runtime tracks from the moment it is asked for until it ends: Hermes's kanban board is one. The plugin sends `task.update` when one changes and `tasks`, every task of the agent's that the runtime still has, less those that ended more than 3 days ago (at most 100, the newest first), after each `hello` and whenever it needs to reconcile.

| Field | Meaning |
| --- | --- |
| `id` | The runtime's id for it, unique in the sandbox (agents of one sandbox can share a board) |
| `title` | What it is, one line |
| `assignee` | The agent doing it: on the plugin leg its name in its runtime, which must be the plugin's own agent; on the device leg `sandbox/agent` |
| `asked_by`? | The agent that asked for it, as the runtime claims it: its name in the runtime on the plugin leg, `sandbox/agent` on the device leg |
| `conversation`? | Where it was asked for, when the runtime knows |
| `state` | `queued`, `running`, `blocked`, `done`, `failed` or `cancelled`; the last three have ended |
| `since` | When it entered its current state, in seconds since the Unix epoch |
| `summary`? | A short result, once it has ended |
| `comments`? | How many comments it has, from a runtime that keeps them: a change tells a device that shows the task's [detail](#task-details) to ask for it again |

**Only the assignee's own plugin reports a task.** The plugin's connection proves which agent it is, so a task whose `assignee` is another agent is refused: agents sharing one board do not report a task several times, and no plugin posts another agent's work. **Every field is untrusted text from the sandbox**, cleaned by the bridge itself: `title`, `summary` and `asked_by` on one line (line breaks made spaces) without hidden characters (`enclos_protocol::visible`), the title cut to 120 characters, the summary to 500; `asked_by` is dropped when, written `sandbox/agent`, it would break the id rule or hold another `/`; the `id` follows the routine id rule. A task whose title is blank once cleaned, or whose id the bridge does not take, is refused (`bad_message`), and in a `tasks` list the others are kept. A `state` outside the six fails the whole message, as any field a receiver cannot read does: it is answered `bad_message` and not acknowledged, and for a `tasks` list nothing is replaced. Its `conversation` is kept only when it is a conversation of the same sandbox (one of its agents' or one of its groups) owned by the host's person; otherwise the task is kept without it. `since` is kept no later than the bridge's clock.

**The bridge keeps tasks**, unlike `tool` steps, so a device that was away gets them at `sync`, regardless of `since`. It keeps at most 100 per sandbox, and an ended task for 3 days after the bridge saw it end: one past its 3 days is dropped at the next write or sync. A task past the 100 makes room by dropping the ended task that ended first; when every kept task is still going, the new one is refused (`bad_message`), and the plugin sends it again with its next change, when there may be room. A `tasks` list replaces what the bridge keeps of that agent's: a kept task of that agent's missing from the list is dropped (the runtime no longer has it, or it ended more than 3 days ago; Hermes: archived). A plugin that connects without the `tasks` capability has its agent's kept tasks dropped, and so does an agent the host's person forgets once it is removed. Each drop is a `task.removed` to devices. The bridge acknowledges `task.update` and `tasks` once stored (after an `error` when it refused one); when its database fails it does not acknowledge, and ends the connection, so the plugin sends its list again on the next `hello`. A plugin therefore keeps no outbox for tasks.

**Only the host's person sees them**, live and at `sync`, as with [policy requests](#sandbox-policy-requests): a task can hold repository paths and internal plans. One task is one device message; its bounds keep it far within 65,519 bytes. After a sync, a device drops the tasks it kept for that host that the sync did not send. Sharing agents ([ADR 0043](adr/0043-sharing-an-agent-is-not-hosting-it.md), proposed) is outside this.

**Hermes.** The task's turn runs in the assignee's own gateway, where its plugin is loaded, but Hermes's board hooks fire in whichever process wrote the board and several changes fire none ([source findings](research/hermes-tasks.md)). So the adapter reads the board itself, read-only, for the tasks assigned to its profile, and watches its event log every few seconds, a hook being only a cue to read sooner. `triage`, `todo`, `scheduled` and `ready` are `queued` (a retry after a crash or a timeout goes back to `ready`); `running` is `running`; `blocked` and `review` are `blocked`; `done` is `done`, its result the summary; an archived task is left out of the next `tasks`. The conversation is the `enclos` subscription Hermes records for the chat that created the task. The plugin announces `tasks` only when the Hermes it runs in has the board's functions, and `activity` always: answering from its turns in enclos conversations, and a task from the board's running tasks assigned to it. It reports no routine yet: Hermes gives plugins no hook around a scheduled run, and whether its session hooks fire for one is to verify (design §14).

**Held tasks.** A task that waits for a person is reported as `blocked`, like any other. Resuming it is not part of this capability: that is the `held_tasks` card of [ADR 0066](adr/0066-held-tasks-stay-with-the-runtime.md), proposed.

**OpenClaw** announces `activity` for authenticated enclos ingresses while its public native dispatch and delivery settle. It reports each active conversation once, retains overlapping ingresses independently, and sends its current snapshot after every hello to a bridge that negotiated `activity`. Typing idle and abort acknowledgement do not clear another active ingress. This is a transient view of this channel's dispatches, not a complete inventory of Gateway runs, CLI work or scheduled activity; native dispatch can defer ingress to existing work. It announces no `tasks` or `held_tasks`: its 2026.11.2 release has no task board (its Tasks and TaskFlow registry was removed), and whether its background subagents fit a task is to verify. Nothing in these messages names a Hermes concept.

### Task details

Issue #318. When the person opens a task, the app asks for its detail: what the runtime holds of it beyond the fields above. An optional `task_details` capability, announced in both the bridge's and the plugin's `hello` and listed among the agent's capabilities in `agents.list`, says the agent's runtime answers. It is a read, like the rest of this section: nothing here changes a task, and commenting from the app is not part of it (commenting on a Hermes task steers its running worker, so it would need its own decision).

| `type` | From | Fields | Meaning |
| --- | --- | --- | --- |
| `task.get` | device | `agent` (`sandbox/agent`), `task` | The detail of a task the bridge keeps |
| `task.get` | bridge (plugin leg) | `task` | The same, to the assignee's plugin, under the bridge's own id |
| `task.detail` | plugin | `of`, `detail` | The plugin's answer, or an `error` naming `of` |
| `task.detail` | bridge (device leg) | `of`, `agent`, `task`, `detail` | The answer, to the device that asked |

`detail` holds, each part left out when empty:

- `body`: what the task asks, its lines kept, at most 4,000 characters;
- `related`: the tasks it waits for (`relation: "parent"`) and that wait for it (`"child"`), at most 20, each `{id, title, relation, state?, assignee?}`; `state` is left out when the runtime's says nothing the protocol knows (Hermes: archived);
- `comments`: the newest 20, oldest first, each `{author, agent?, time, text}`, the text's lines kept, at most 1,000 characters; `author` is the runtime's name for who wrote it, and on the device leg `agent` is `sandbox/agent` when that name is an agent the host serves, so the app shows its name and photo; a person's name or any other stays text;
- `comments_total`: how many comments the task has;
- `history`: what happened to it, oldest first, the newest 30 entries, each `{kind, time, until?, outcome?, by?, text?}`. `kind` is `created`, `attempt` (from `time` to `until` once it ended, with its `outcome`: `completed`, `blocked`, `crashed`, `timed_out`, `gave_up`, `failed` or `stopped`), `blocked`, `unblocked`, `review` or `done`; `by` names the agent as `asked_by` does; `text` is one line of at most 300 characters (an attempt's summary or error, why it blocked). A device leaves out an entry of a kind it does not know and reads an outcome it does not know as ended.

**Only the host's person asks**, on a still-paired device, for a task the bridge keeps for that agent: a task's detail can hold what its title does and more. Anyone else is refused `not_allowed`, a task the bridge does not keep `not_found`, an agent it does not serve `unknown_agent`, and an agent whose channel does not announce `task_details` `unsupported`; nothing reaches the plugin then. The plugin answers `not_found` for a task that is not its agent's.

**It is live and kept by no one.** The bridge sends the plugin the request at once, on the agent's current connection, opening it if it can (`agent_unavailable` otherwise), and passes the answer to the device that asked only, once it checked the device is still paired to the same person. A request the runtime leaves unanswered for 15 seconds, or whose connection closes first, is answered `agent_unavailable`; one that comes later is dropped. At most 64 are in flight (`busy` beyond). Nothing is stored, queued or logged: a device asks again, when the person opens the task again or when a `task` for it arrives with another state or comment count.

**Every field is untrusted text from the sandbox**, cleaned by the bridge itself: the body and comments keep their lines but lose hidden characters (`enclos_protocol::visible`), their carriage returns and line and paragraph separators made newlines, tabs spaces (so markdown nested with tabs loses its nesting, and an agent indents with spaces), line ends trimmed and blank lines in a row made one; every other text is on one line, as a task's title is; ids follow the routine id rule (a related task with another id is left out), times are kept no later than the bridge's clock, and an attempt's `until` no earlier than its `time`. The bridge cuts every part to its bounds itself, then gives up the oldest history entries, then the oldest comments, related tasks and finally the body's end until the detail encodes within 56 KiB, so that a `task.detail` stays within one Noise message. The body and each comment are markdown, drawn as what the agent says is (What the agent says is markdown, under [Files](#files)): a device fetches and runs nothing in them, and a link opens only on a tap, as in a message. Every other text, the title, names, related tasks and history, is plain text, never markdown or links.

**Hermes.** The adapter reads the task on every board, read-only, as it reads its tasks: `body`; `task_links` for parents and children, their statuses mapped as above; `task_comments` for the newest comments and their count; and `task_runs` for the attempts, their `outcome` mapped (`spawn_failed` is `failed`, `reclaimed` is `stopped`) and their error or summary as text. Of the event log it shows only `created`, `blocked`, `dependency_wait` and `block_loop_detected` (each `blocked`, with its reason), `gave_up` (`blocked` too, saying that retries stopped, with the failure count and error of its payload: when retries run out, the failed run keeps its own outcome and this event is the only trace of the block), `unblocked`, `review_requested` (`review`) and `completed` (`done`); claims, spawns, heartbeats and the rest are the board's own workings. Each attempt takes its place in the history at its run's first event, so that things that happened within one second keep their order. Hermes keeps a task's text as its writer wrote it, so where tasks are on, the plugin tells the agent in each turn (a `pre_llm_call` context added to the turn's user message, `tasks.WRITING_HINT`) that the app draws a body and comments as markdown, and a title and a task's result as one plain line each. Every turn gets it wherever Hermes runs it, a conversation, a cron run or a task's turn in the assignee's gateway, so it reaches whoever writes a task: the agent that asks for it or the one doing it. Hermes adds every plugin's `pre_llm_call` context to the turn, this one beside the sandbox policy's (design §4, Sandbox policy requests, for what a running Hermes showed).

### Task events

[ADR 0071](adr/0071-a-runtimes-task-events-reach-the-app-as-task-lines.md), proposed. A **task event** is a change of a task that its runtime announces to a conversation: Hermes's kanban notifier pings the conversation that asked for a task when it is done, ready for review, sent back with changes, blocked, given up, crashed, timed out, sent to triage, or changes status otherwise. It is not the agent talking, so the app draws it as one line about the task, such as "t_3f9a12bc S2a · reviewer · sent to triage", with **Open task**, and never as a message from the agent. The agent's own answer to the event, in the turn its runtime wakes it for, is its message as before.

The plugin sends it as a `message.out` of `kind: "task_event"`, with the runtime's text, kept for a peer that does not draw the line, and `task_event`:

| Field | Meaning |
| --- | --- |
| `task` | The runtime's id of the task, as `tasks` and `task.get` name it |
| `title` | What it is, one line |
| `assignee`? | The agent doing it: on the plugin leg its name in its runtime, on the device leg `sandbox/agent` |
| `event` | What happened: `blocked`, `gave_up` (its runtime stopped retrying), `crashed`, `timed_out`, `done`, `review` (ready for review), `changes_requested`, `triage` (sent to triage), or `changed` (another change of its status) |
| `state`? | Where it is now, one of the [task](#tasks) states |

Each field is read from the runtime's state, never cut from its text. A receiver reads an `event` it does not know as `changed`, and a `state` it does not know as none.

```
{"v":1,"type":"message.out","id":"…","conversation":"home.lab.main","kind":"task_event",
 "text":"🛑 [enclos-org] @reviewer Kanban t_a09759c7 routed to TRIAGE — needs a human decision …",
 "task_event":{"task":"t_a09759c7","title":"S2a","assignee":"reviewer","event":"triage","state":"queued"}}
```

**Older peers get the text.** A plugin sends `kind: task_event` only to a bridge whose `hello` names `task_events`, and to any other the same message, under the same id, as a `notify` without `task_event`, as before task events: an older bridge would refuse the kind (`bad_message`), and the plugin keeps a message until its `ack`, so it decides again for the bridge each `hello` brings. The bridge passes `kind: "task_event"` and `task_event` only to a device whose `auth` names `task_events`; any other device gets the message as a `notify`, its text alone, live and at sync.

**The bridge keeps it as a line.** Every field comes from the sandbox, and the agent can send `kind: task_event` itself, so the line is trusted no more than any text from the agent: the bridge cleans it itself. The task id follows the routine id rule; the title is put on one line without hidden characters and cut to 120 characters; the assignee is written `sandbox/agent` and dropped when it would break the id rule or hold another `/`. A `kind: task_event` whose `task_event` is missing or does not parse, or has a task id or a blank title the bridge does not take, is kept as its text, a `notify`. A `task_event` on another kind is ignored, and the message keeps its kind. It stores the line with its message, so a sync carries it. A task event is not pushed and carries no suggested replies: like a `status` line, it waits, quiet, for the next sync. In a group, it ends no member's turn, and no member is given it as something said. Its text is one device message at most: the rest is left out rather than repeat the line.

**Open task** opens the task's sheet as a task card does: `task.get` with the `assignee` as `agent` and `task` ([Task details](#task-details)), for the host's person, when the device has that task from `tasks`. The line itself grants nothing: a device offers no other action on it.

**Hermes.** The plugin tells a ping from the agent's message by its wording and the board together. The wording: the text begins as one of Hermes's ping templates (`gateway.kanban.ping.completed`, `review_requested`, `changes_requested`, `triage`, `gave_up`, `timed_out`, `blocked`, `crashed` and `status`), read from Hermes's own translations (`agent.i18n.t`) in the language of the context `send()` runs in (that this is the ping's language is to verify, design §14), and in English when they cannot be read: an emoji, an optional `[board]` (`board_tag`) and `@assignee` (`assignee_tag`), then `Kanban <task id>` (`head`) and the words of that kind of event. The board: on that board, one of the sandbox's (`list_boards`, read-only), a subscription of this platform and chat to that task (`kanban_notify_subs`), not `wake` alone, which sends no text, and an event of that kind (`task_events`) that Hermes has claimed for it (at most its `last_event_id`, which Hermes advances before it pings) and not yet recorded as pinged (above its `last_ping_event_id`, which Hermes writes only once `send()` has returned). The ping is about the oldest such event: Hermes sends a batch's pings oldest first, recording each, so two events of one kind in a batch are two lines, and the agent's answer in its wake turn, which comes after the record, finds none. A Hermes without `last_ping_event_id` gives the newest claimed event of that kind instead. The plugin also remembers the events it told as lines, and a second text matching one is the agent's. The line's title, assignee and state are the task's (`tasks`), its `changed` state the status that chosen event announced. Anything else stays the agent's message: an agent's sentence that begins like a ping, a ping for another chat, and every ping when the board cannot be read, said in the gateway's log once for each failure, and again when the board reads. A Hermes with no kanban board (`hermes_cli.kanban_db` without `list_boards`) has no task events, and the plugin does not announce `task_events`. Hermes passes a ping to `send()` with only its subscription's routing keys in the metadata; enclos asks Hermes to mark its pings there, and the plugin is to read that mark first once a Hermes release has it.

## Agent display names

The bridge owns one optional human-readable name for each listed `<sandbox>/<agent>` ([ADR 0051](adr/0051-agent-display-names-belong-to-the-bridge.md), proposed). `agents.list` adds optional `display_name`, nonnegative `name_revision` (absent means 0), and `can_edit_name`. Supporting hosts always include `can_edit_name`, false for a person other than the host's; its presence signals support so an app does not send name controls to an older host. At the newest accepted revision, a missing/null display name means show the stable agent identifier.

Ordinary inventories inline names in `agents.list`. If their names would make that message too large for a Noise frame, the bridge omits all inline display names and sends `name_revision: 0` while retaining support/permission flags, then follows the list with individual `agent.name` messages with empty `of` for every non-default name state. Cleared names with a nonzero revision are included, so a tombstone still replaces an older cached label. Each emitted envelope stays within a 60 KiB budget. If the inventory is still too large without names, the bridge sends a correlated `bad_message` error; this change adds no inventory pagination.

| `type` | From | Fields | Meaning |
| --- | --- | --- | --- |
| `agent.name.get` | device | `agent` | Fetch the current display name and revision |
| `agent.name.set` | device | `agent`, required `revision`, required nullable `display_name` | Set the shared display name, or explicitly clear it with null |
| `agent.name` | bridge | `agent`, `revision`, `display_name`, `of` | Current canonical name, correlated to a request or broadcast with empty `of` |

Names are trimmed Unicode text, at most 100 Unicode scalar values and 400 UTF-8 bytes. Blank names, control characters, line and paragraph separators and characters that change how text reads without showing (bidirectional overrides, embeddings, isolates and marks, zero-width and other default-ignorable characters such as the soft hyphen, the byte-order mark, tags, variation selectors and the combining grapheme joiner, and blank fillers such as U+3164 and U+2800; enclos-protocol's `visible` module) are refused, so `"\u202Eniam"` cannot read as "main" and a name of fillers cannot look empty. The joiners U+200C and U+200D and the emoji selectors U+FE0E and U+FE0F are ordinary text between two non-ASCII characters, so joined emoji and Persian spelling are accepted, and refused next to ASCII or at an edge. Clearing requires explicit null, not an omitted field. Names need not be unique, but a name that reads as another listed agent's handle or address is refused with `bad_message`: compared ignoring ASCII case, the joiners, a leading `@` and whatever comes before a last `/`, so `main`, `@main`, `lab/main` and `prod/main` all read as the agent `lab/main`. A look-alike is not caught: Cyrillic `а` for `a`, fullwidth letters or a space after `@` pass. The check is made when a name is set and again whenever it is sent: a saved name that reads as an agent listed since then is sent as absent, so the agent shows as its stable address, until the name is changed or that agent is gone. The host's person (ADR 0044) on a still-paired device may edit them; paired people who can see the agent, that is to whom `agents.list` lists it, may read them and receive their changes; today that is every paired person, until sharing narrows the list. A revision is a nonnegative integer: a negative one does not decode. A storage failure answers `internal` with a generic message, the database's own error staying in the host's log. Unknown or unauthorized targets are refused. The bridge compares the revision and commits the new name and device/person log entry atomically. Clearing retains an increasing revision. An unchanged confirmed value need not advance it.

A successful edit sends the canonical `agent.name` with the request id in `of` and broadcasts it to eligible connected devices with empty `of`. A stale edit changes nothing: the requester receives current metadata with empty `of`, followed by a correlated `conflict` error. The metadata refresh therefore cannot be mistaken for a successful edit. Devices keep the highest observed name revision for the full host/sandbox/agent address across agent lists, broadcasts and their local cache. Reconnecting and fresh lists restore the shared value; clearing the phone cache removes no host name. Like conversation revisions, name revisions assume the bridge's database is never reset or restored from an older copy: a device that kept a higher revision for an agent's address ignores the new database's name until the person clears the app's cache.

App names are confirmed host metadata, never optimistic local aliases or offline-queued edits. A timeout or disconnect requires refreshing before retrying. This adds no plugin message and calls no runtime rename command. An agent named `comptoir-dev` can display **Gégé Commit** while its canonical address, `@comptoir-dev` routing handle, runtime paths, configuration and messages stay intact. Native channels and the runtime's own identity are unchanged.

## Shared agent photos

The bridge owns one optional photo for each listed `<sandbox>/<agent>` in its private database. `agents.list` adds optional `avatar: {revision, version}` and `can_edit_avatar` fields. New hosts always include `can_edit_avatar` (false for a person other than the host's). A device decoding with `enclos-protocol` reads an absent field as false and absent metadata as no photo, so it cannot tell an older host from another person's view of a new one; it sends `agent.avatar.set` only when `can_edit_avatar` is true, which an older host never sends, and an older host answers `agent.avatar.get` with `unknown_type`, which reads as no photo. Revision zero with no version means no photo has been set; a removal retains its increasing revision. `version` is the SHA-256 hex digest of the canonical JPEG, or null. The host's person (ADR 0044) on a still-paired device may change photos. Currently paired people shown the agent (the same rule as `agents.list`) may fetch its photo; an agent they are not shown is refused with `unknown_agent`. A photo belongs to the agent's name: an agent made again under that name shows it until it is changed.

- `agent.avatar.get`: `agent`. Replies with `agent.avatar`.
- `agent.avatar.set`: `agent`, `revision` (the last observed revision), `image` (base64url raster bytes, or null to remove). The host compares the revision atomically, commits the photo and device audit entry, then returns `agent.avatar` with the request id in `of`. A refusal changes nothing; when the person may still read the photo, the host sends the current one first, then the error: `conflict` for a stale revision, `not_allowed` for a person other than the host's or a device no longer paired, `unknown_agent`, `bad_message` for an image it does not take, `internal` when its database fails.
- `agent.avatar`: `agent`, `revision`, `version`, `image`, `of`. An update or removal is broadcast, with empty `of`, to every other connected device that is still paired and shown the agent; the device that made it gets the reply instead. Devices ignore older revisions. Reconnecting devices learn the latest metadata through `agents.list` and fetch a missing/different photo; images are transferred only through the authenticated Noise connection, without public URLs.

Uploads are JPEG or PNG, at most 32 KiB and 512 × 512 pixels with bounded decoding allocation. The host crops and re-encodes a 256 × 256 JPEG, stripping source metadata and bounding the result to 32 KiB. Base64 plus the envelope fits one Noise transport frame. The host applies a JPEG's orientation tag before it re-encodes. The app is meant to resize and compress a selected photo before upload, show only confirmed host data and keep the coloured initial when no photo exists, and to keep cached photos private to it, scoped to the full host/sandbox/agent address, hash-checked and removed by Clear cache / Forget this host: that is the app's contract, not shown in this repository. Removing a cached copy does not remove the shared host asset.
