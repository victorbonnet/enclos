How a policy compiles

You write one small file. enclos checks it when it changes, and compiles it each time a program starts in the sandbox.

1. Layers become one policy

A sandbox’s policy.toml only says what differs. enclos applies four layers in order:

  1. Built-in defaults: writes only to the sandbox’s home, and the list of sensitive paths it may not read.
  2. The template: minimal or assistant, which the file names with extends.
  3. The runtime’s needs: the hosts it lists for its install, login and model calls.
  4. Your policy.toml: what you add.

A list written write_add adds to the layers below, one written write_remove takes out of them only the entries it names, and one written write replaces them. In one file the replacement comes first, then the removals, then the additions. The runtime’s layer only adds. Unknown keys are errors, so a misspelling cannot pass unnoticed.

2. The policy is checked and stored

enclos checks the result before keeping it. It refuses what it will not grant, such as dropping an entry from the sensitive list, writing to enclos’s own folders, or allowing localhost. It rejects what it cannot read, such as a malformed address.

A policy that passes is stored as an immutable version. enclos policy history lists them, and enclos policy rollback brings an earlier one back as a new version.

3. The backend compiles it

Each time a program starts in the sandbox, enclos takes the active version as stored, checks the sandbox’s paths as they are now, and hands the policy to the sandbox’s backend. If that backend cannot run on this computer, the command fails, with no fallback.

On macOS, the Seatbelt backend writes a file named after its content, compiled/<hash>.sb, and the program runs under it through sandbox-exec. Rules start from (deny default), and later rules decide:

On Linux, the bubblewrap backend writes compiled/<hash>.json: bubblewrap’s arguments, Landlock rules and a seccomp filter. At each launch enclos reads it, masks what your home holds at that moment, and runs the program under bubblewrap. Inside, enclos runs first, applies Landlock where the kernel has it and the seccomp filter, then runs the program:

4. The network stays with the proxy

Your allowed hosts are not in the compiled policy. It only sends every connection to the sandbox’s proxy, which reads the active policy for each new connection. So a change to the network applies at once, without a restart.

A compiled policy is fixed for the life of a program. So a change to what a sandbox may write waits as the pending policy while sessions run:

You changeNew sessionsRunning sessions
Network hosts or modeUse itUse it at once
Files, listening, secrets or limitsUse it, once it is activeWait for enclos policy apply

What a backend cannot enforce is refused

enclos refuses what a backend cannot enforce, rather than keep it and ignore it. Seatbelt holds a process to its open files only, so limits on CPU time, memory, file size and CPU share are refused. bubblewrap also holds memory and a CPU share, on the sandbox as a whole, and refuses CPU time and file size. No backend enforces rules on programs yet, so an [exec] section is an error.

A Linux host can lack a control bubblewrap relies on: Landlock, or the memory controller, which Raspberry Pi OS turns off. The sandbox still runs without it, and enclos doctor says what is not enforced, the risk and the fix. A memory limit the host cannot hold runs not applied, and only once you accept it with --accept-unenforced memory, which the audit log records.

One exception: on bubblewrap, listen = false is declared, not held. A listener in one session is reached by the sandbox’s other sessions, never by your network, and each session’s start says so.

The same policy.toml is meant for every backend, each with a compiler of its own. Moving a Mac’s policy to Linux is not yet shown.

The templates

A sandbox starts from a template, named when it is created and kept in extends. Change extends with enclos policy edit lab to move it to another. The two differ only in what the sandbox reaches on the network:

Can it…minimalassistant
Write to its own homeYesYes
Write to other foldersIf addedIf added
Read your files, except sensitive pathsYesYes
Read sensitive paths, such as SSH keysNoNo
Run programs, and install them in its homeYesYes
Reach what its runtime needs, once installedYesYes
Reach the public webIf listedYes, ports 80 and 443
Reach other portsIf listedIf listed
Reach a host on your local networkIf you opt inIf you opt in
Reach your computer’s own services or cloud metadataNoNo
Use your computer’s services, such as Apple Events or the session bus, or signal other processesNoNo
  • minimal reaches nothing until a runtime is installed, then only what that runtime needs and what you list. For Hermes, that is its install sources and the ChatGPT subscription’s hosts; another model provider’s hosts need enclos policy allow. Use it when an agent should reach only what you name, such as one working on outside data through remote MCP servers: allow each server’s host, then tell the runtime of it with its own commands.
  • assistant adds any public address on ports 80 and 443, so any model provider works without a grant. Use it for personal agents that browse, research and call public APIs. It can send what it reads to a public website: for sensitive work, use an allowlist.

Under every template, each connection goes through the sandbox’s proxy and is logged, as long as enclos can write its state. A runtime may also ask to listen on TCP, as Hermes does. On macOS, anything in the sandbox can then serve your network; on Linux, only the sandbox’s own sessions reach it, and you, through enclos dashboard. A runtime’s hosts can be broad: Hermes’s include github.com and storage.googleapis.com, which could carry data out.

Every setting

A policy.toml holds what differs from its template. These are all the keys there are: any other key or section is an error. Change a sandbox’s file with enclos policy edit lab.

extends = "assistant"

[filesystem]
write_add = ["~/Documents/notes"]
read_deny_add = ["~/work"]

[network]
mode = "allowlist"
allow_add = ["api.example.com", "*.example.org", "printer.lan"]
private_add = ["printer.lan"]
log = "metadata"

[resources]
open_files = 1024

[secrets]
env_add = { API_TOKEN = "secret:lab/api" }

[secrets.agents.main]
env_add = { TELEGRAM_BOT_TOKEN = "secret:lab/main-telegram" }

[filesystem]

A path starts with /, ~, {home} or {tmp}. While sessions run, a change waits as the pending policy until enclos policy apply restarts the sandbox into it.

SettingAcceptsNotes
writepathsReplaces the folders the sandbox may write. Its home stays writable either way.
write_addpathsAdds folders. Each must exist before the sandbox uses it. enclos’s own folders and folders inside the home are refused.
write_removepathsTakes out folders the layers below set, only those named; a name not there changes nothing. The home stays writable.
read_denypathsReplaces the sensitive list, and must keep every built-in entry, so use read_deny_add.
read_deny_addpathsAdds paths the sandbox may neither read nor write.
read_deny_removepathsTakes out paths the template set. A built-in entry cannot be taken out: the policy is refused.

There is no read list and no write_deny. Reads are open except read_deny, since agents and the tools they install read paths nobody can list upfront. Writes are closed except write, so there is nothing to deny, and a read_deny path refuses writes too.

[network]

A destination is a full domain name or an IP address, or *.domain for its subdomains, with :port when it is not 443. *, *.com, localhost and loopback addresses are refused, and a private address needs private. A change applies at once, unless it touches listen or the same edit changes files, secrets or limits: then it all waits as the pending policy while sessions run.

See it for yourself

# the active policy: version, writes, deny list, network
enclos policy show lab

# what the active policy compiles to, for the sandbox’s backend
enclos policy show lab --compiled

# compile it, then try known ways out from inside
enclos policy test lab
